オペレーティング システムの仕事は、複数のプログラム間でコンピュータを共有し、ハードウェアだけがサポートするよりも便利なサービス セットを提供することです。オペレーティング システムは低レベルのハードウェアを管理および抽象化するため、たとえば、ワード プロセッサは、どのタイプのディスク ハードウェアが使用されているかを気にする必要がありません。オペレーティング システムは、複数のプログラム間でハードウェアを共有し、同時に実行される (または実行されているように見える) ようにします。最後に、オペレーティング システムは、プログラムが対話するための制御された方法を提供し、プログラムがデータを共有したり連携したりできるようにします。

オペレーティング システムは、インターフェイスを通じてユーザー プログラムにサービスを提供します。

優れたインターフェイスを設計するのは難しいことがわかりました。一方で、実装を正しく行うのが容易になるため、インターフェースはシンプルで狭いものにしたいと考えています。その一方で、アプリケーションに多くの高度な機能を提供したくなるかもしれません。この緊張を解決するコツは、組み合わせて汎用性を高めることができるいくつかのメカニズムに依存するインターフェイスを設計することです。

この本では、オペレーティング システムの概念を説明するための具体例として単一のオペレーティング システムを使用します。そのオペレーティング システムである xv6 は、Ken Thompson と Dennis Ritchie の Unix オペレーティング システム (Ritchie and Thompson 1974) によって導入された基本インターフェイスを提供するだけでなく、Unix の内部設計を模倣しています。 Unix は、メカニズムがうまく組み合わされた狭いインターフェイスを提供し、驚くほどの汎用性を提供します。このインターフェイスは非常に成功しており、最新のオペレーティング システム (BSD、Linux、macOS、Solaris、および程度は低いものの Microsoft Windows でさえ) が Unix に似たインターフェイスを備えています。 xv6 を理解することは、これらのシステムや他の多くのシステムを理解するための良いスタートとなります。

図 [1.1](#fig:os) が示すように、xv6 は、実行中のプログラムにサービスを提供する特別なプログラムである *カーネル* の伝統的な形式をとります。 *プロセス*と呼ばれる実行中の各プログラムには、命令、データ、スタックを含むメモリがあります。命令はプログラムの計算を実装します。データは、計算の対象となる変数です。スタックはプログラムのプロシージャ呼び出しを編成します。通常、特定のコンピュータには多くのプロセスがありますが、カーネルは 1 つだけです。

プロセスがカーネル サービスを呼び出す必要がある場合、オペレーティング システムのインターフェイスの呼び出しの 1 つである *システム コール* を呼び出します。システムコールがカーネルに入ります。カーネルはサービスを実行して戻ります。したがって、プロセスは *ユーザー空間* と *カーネル空間* で交互に実行されます。

後続の章で詳しく説明するように、カーネルは CPU[^1] によって提供されるハードウェア保護メカニズムを使用して、ユーザー空間で実行されている各プロセスが自身のメモリのみにアクセスできるようにします。カーネルは、これらの保護を実装するために必要なハードウェア権限で実行されます。ユーザープログラムはそれらの権限なしで実行されます。ユーザープログラムがシステムコールを呼び出すと、ハードウェアは特権レベルを上げ、カーネル内であらかじめ用意された関数の実行を開始します。

カーネルが提供するシステム コールのコレクションは、ユーザー プログラムが見るインターフェイスです。 xv6 カーネルは、Unix カーネルが従来提供していたサービスとシステム コールのサブセットを提供します。図 [1.2](#fig:api) は、xv6 のすべてのシステム コールをリストしています。

この章の残りの部分では、xv6 のサービス (プロセス、メモリ、ファイル記述子、パイプ、ファイル システム) の概要を説明し、コード スニペットを使って説明し、Unix のコマンド ライン ユーザー インターフェイスである *シェル* がそれらをどのように使用するかについて説明します。シェルによるシステム コールの使用は、シェルがいかに慎重に設計されているかを示しています。

シェルは、ユーザーからコマンドを読み取り、実行する通常のプログラムです。シェルがユーザー プログラムであり、カーネルの一部ではないという事実は、システム コール インターフェイスの能力を示しています。シェルには特別なことは何もありません。これは、シェルの交換が簡単であることも意味します。その結果、最新の Unix システムにはさまざまなシェルがあり、それぞれに独自のユーザー インターフェイスとスクリプト機能が備わっています。 xv6 シェルは、Unix Bourne シェルの本質を単純に実装したものです。

xv6 シェルの実装は [`user/sh.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/sh.c) にあります。 [リンク] は、<https://github.com/mit-pdos/xv6-riscv/> にある関連する xv6 ソース コードへのハイパーリンクであり、特定の番号は、ライオンズ解説 UNIX 第 6 版 (ライオンズ 2000) のように、[xv6-src-booklet.pdf](https://pdos.csail.mit.edu/6.1810/2026/xv6/xv6-src-booklet.pdf) のシートと行番号を参照しています。良い習慣としては、まず自分で (お気に入りの開発環境、github、または PDF ビューアで) ソース コードを読んでから、この本に戻ってくることです。この本を読み終える頃には、この本を参照しなくても、xv6 ソース コードのすべての行を理解できるようになっているはずです。

## プロセスとメモリ

xv6 プロセスは、ユーザー空間メモリ (命令、データ、スタック) とカーネルにプライベートなプロセスごとの状態で構成されます。 Xv6 *タイムシェア* プロセス: 実行を待機している一連のプロセス間で利用可能な CPU を透過的に切り替えます。プロセスが実行されていないとき、xv6 はプロセスの CPU レジスタを保存し、次回プロセスを実行するときにそれらを復元します。カーネルは、プロセス識別子 (`PID`) を各プロセスに関連付けます。

プロセスは、`fork` システム コールを使用して新しいプロセスを作成できます。 `fork` は、呼び出しプロセスのメモリの正確なコピーを新しいプロセスに提供します。`fork` は、呼び出しプロセスの命令、データ、およびスタックを新しいプロセスのメモリにコピーします。 `fork` は、元のプロセスと新しいプロセスの両方で戻ります。元のプロセスでは、`fork` は新しいプロセスの PID を返します。新しいプロセスでは、`fork` はゼロを返します。元のプロセスと新しいプロセスは、多くの場合、*親* および *子* と呼ばれます。

たとえば、C プログラミング言語で書かれた次のプログラムの一部について考えてみましょう (Kernighan 1988)。

    int pid = fork();
    if(pid > 0){
      printf("parent: child=%d\n", pid);
      pid = wait((int *) 0);
      printf("child %d is done\n", pid);
    } else if(pid == 0){
      printf("child: exiting\n");
      exit(0);
    } else {
      printf("fork error\n");
    }

`exit` システム コールにより、呼び出しプロセスの実行が停止され、メモリやオープン ファイルなどのリソースが解放されます。 Exit は整数のステータス引数を受け取ります。通常、0 は成功を示し、1 は失敗を示します。 `wait` システム コールは、現在のプロセスの終了した (または強制終了された) 子の PID を返し、待機するために渡されたアドレスに子の終了ステータスをコピーします。呼び出し元の子のいずれも終了していない場合、`wait` は子が終了するまで待機します。呼び出し元に子がない場合、`wait` はすぐに -1 を返します。親が子の終了ステータスを気にしない場合は、0 アドレスを `wait` に渡すことができます。

この例では、出力行は

    parent: child=1234
    child: exiting

親または子が最初に `printf` 呼び出しに到達するかどうかに応じて、いずれかの順序 (または混合) で出力される可能性があります。子が終了すると、親の `wait` が戻り、親が出力します。

    parent: child 1234 is done

子は親のメモリのコピーから開始しますが、親と子は別々のメモリと別々のレジスタで実行されます。一方の変数を変更しても、もう一方には影響しません。たとえば、`wait` の戻り値が親プロセスの `pid` に格納される場合、子プロセスの変数 `pid` は変更されません。子の `pid` の値はゼロのままです。

`exec` システム コールは、呼び出しプロセスのメモリを、ファイル システムに格納されているファイルからロードされた新しいメモリ イメージに置き換えます。ファイルは、ファイルのどの部分が命令を保持するか、どの部分がデータであるか、どの命令から開始するかなどを指定する特定の形式を持つ必要があります。Xv6 は ELF 形式を使用します。これについては、[3] 章 (/book/chapter-3/#CH:MEM) で詳しく説明します。通常、ファイルはプログラムのソース コードをコンパイルした結果です。 `exec` が成功しても、呼び出し元のプログラムには戻りません。代わりに、ファイルからロードされた命令は、ELF ヘッダーで宣言されたエントリ ポイントで実行を開始します。 `exec` は、実行可能ファイルを含むファイルの名前と文字列引数の配列の 2 つの引数を取ります。たとえば:

    char *argv[3];

    argv[0] = "echo";
    argv[1] = "hello";
    argv[2] = 0;
    exec("/bin/echo", argv);
    printf("exec error\n");

このフラグメントは、呼び出し側プログラムを、引数リスト `echo` `hello` で実行されるプログラム `/bin/echo` のインスタンスに置き換えます。ほとんどのプログラムは、引数配列の最初の要素 (通常はプログラムの名前) を無視します。

xv6 シェルは上記の呼び出しを使用して、ユーザーに代わってプログラムを実行します。シェルの主な構造は単純です。 [`main`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/sh.c#L146) を参照してください。メインループは、`getcmd` を使用してユーザーからの入力行を読み取ります。次に、`fork` を呼び出し、シェル プロセスのコピーを作成します。親は `wait` を呼び出し、子はコマンドを実行します。たとえば、ユーザーがシェルに「`echo hello`」と入力した場合、引数として「`echo hello`」を使用して `runcmd` が呼び出されます。 [`runcmd`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/sh.c#L59) は実際のコマンドを実行します。 「`echo hello`」の場合、[`exec`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/sh.c#L79) を呼び出します。 `exec` が成功すると、子は `runcmd` ではなく `echo` からの命令を実行します。ある時点で、`echo` は `exit` を呼び出します。これにより、親が [`main`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/sh.c#L146) の `wait` から戻ります。

なぜ `fork` と `exec` が 1 つの呼び出しで結合されないのか疑問に思われるかもしれません。シェルが I/O リダイレクトの実装で分離を利用していることが後でわかります。重複したプロセスを作成してすぐに (`exec` に) 置き換えるという無駄を避けるために、オペレーティング カーネルは、コピー オン ライトなどの仮想メモリ技術を使用して、このユースケースの `fork` の実装を最適化します ([5] 章 (/book/chapter-5/#CH:PGFAULTS) を参照)。

Xv6 はほとんどのユーザー空間メモリを暗黙的に割り当てます。`fork` は親のメモリの子コピーに必要なメモリを割り当て、`exec` は実行可能ファイルを保持するのに十分なメモリを割り当てます。実行時により多くのメモリを必要とするプロセス (おそらく `malloc`) は、`sbrk(n)` を呼び出して、そのデータ メモリを `n` ゼロ バイトずつ増やすことができます。 `sbrk` は新しいメモリの場所を返します。

## I/O およびファイル記述子

*ファイル記述子* は、プロセスが読み取りまたは書き込みできるカーネル管理のオブジェクトを表す小さな整数です。プロセスは、ファイル、ディレクトリ、またはデバイスを開くか、パイプを作成するか、既存の記述子を複製することによって、ファイル記述子を取得できます。簡単にするために、ファイル記述子が参照するオブジェクトを「ファイル」と呼ぶことがよくあります。ファイル記述子インターフェイスは、ファイル、パイプ、デバイス間の違いを抽象化し、それらをすべてバイトのストリームのように見せます。入力と出力を *I/O* と呼びます。

内部的には、xv6 カーネルはファイル記述子をプロセスごとのテーブルへのインデックスとして使用するため、すべてのプロセスがゼロから始まるファイル記述子のプライベート領域を持ちます。慣例により、プロセスはファイル記述子 0 (標準入力) から読み取り、出力をファイル記述子 1 (標準出力) に書き込み、エラー メッセージをファイル記述子 2 (標準エラー) に書き込みます。後で説明するように、シェルはこの規則を利用して I/O リダイレクトとパイプラインを実装します。シェルは、常に 3 つのファイル記述子をオープン [(sh.c:152)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/sh.c#L152) するようにします。これらは、デフォルトでコンソールのファイル記述子です。

`read` および `write` システムは、ファイル記述子で指定されたファイルを開くためにバイトの読み取りと書き込みを呼び出します。 `read(fd`、`buf`、`n)` 呼び出しは、ファイル記述子 `fd` から最大 `n` バイトを読み取り、それらを `buf` にコピーし、読み取られたバイト数を返します。ファイルを参照する各ファイル記述子には、それに関連付けられたオフセットがあります。 `read` は、現在のファイル オフセットからデータを読み取り、そのオフセットを読み取ったバイト数だけ進めます。後続の `read` は、最初の `read` によって返されたバイトに続くバイトを返します。読み取るバイトがなくなると、`read` はファイルの終わりを示すゼロを返します。

`write(fd`、`buf`、`n)` の呼び出しは、`buf` から `n` バイトをファイル記述子 `fd` に書き込み、書き込まれたバイト数を返します。 `n` バイト未満は、エラーが発生した場合にのみ書き込まれます。 `read` と同様に、`write` は現在のファイル オフセットにデータを書き込み、書き込まれたバイト数だけそのオフセットを進めます。各 `write` は前のファイル オフセットから再開します。

次のプログラム部分 (プログラム `cat` の本質を形成します) は、標準入力から標準出力にデータをコピーします。エラーが発生した場合は、標準エラーにメッセージを書き込みます。

    char buf[512];
    int n;

    for(;;){
      n = read(0, buf, sizeof buf);
      if(n == 0)
        break;
      if(n < 0){
        fprintf(2, "read error\n");
        exit(1);
      }
      if(write(1, buf, n) != n){
        fprintf(2, "write error\n");
        exit(1);
      }
    }

コード部分で注意すべき重要な点は、`cat` がファイル、コンソール、パイプのいずれから読み取っているかを認識していないということです。同様に、`cat` は、コンソール、ファイル、その他に出力しているかどうかを知りません。ファイル記述子と、ファイル記述子 0 が入力でファイル記述子 1 が出力である規則を使用すると、`cat` を簡単に実装できます。

`close` システム コールはファイル記述子を解放し、将来の `open`、`pipe`、または `dup` システム コールで自由に再利用できるようにします (下記を参照)。新しく割り当てられたファイル記述子は常に、現在のプロセスの最も小さい番号の未使用の記述子になります。

ファイル記述子と `fork` は相互作用して、I/O リダイレクトの実装を容易にします。 `fork` は、親のファイル記述子テーブルをそのメモリとともにコピーするため、子は親とまったく同じ開いているファイルから開始します。システム コール `exec` は呼び出しプロセスのメモリを置き換えますが、そのファイル テーブルは保持します。この動作により、シェルは、子の中で選択したファイル記述子をフォーク、クローズ、および再度オープンし、`exec` を呼び出して新しいプログラムを実行することにより、*I/O リダイレクト* を実装できます。以下は、コマンド `cat` `<` `input.txt` に対してシェルが実行するコードの簡略版です。

    char *argv[2];

    argv[0] = "cat";
    argv[1] = 0;
    if(fork() == 0) {
      close(0);
      open("input.txt", O_RDONLY);
      exec("cat", argv);
    }

子がファイル記述子 0 を閉じた後、`open` は新しく開かれた `input.txt` にそのファイル記述子を使用することが保証されます。0 は使用可能な最小のファイル記述子になります。次に、`cat` は、`input.txt` を参照するファイル記述子 0 (標準入力) で実行されます。このシーケンスは子の記述子のみを変更するため、親プロセスのファイル記述子はこのシーケンスによって変更されません。

xv6 シェルの I/O リダイレクトのコードは、まさにこのように動作します [(sh.c:83)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/sh.c#L83)。コードのこの時点で、シェルはすでに子シェルをフォークしており、`runcmd` が `exec` を呼び出して新しいプログラムをロードしていることを思い出してください。

`open` の 2 番目の引数は、`open` の動作を制御するビットで表されるフラグのセットで構成されます。可能な値はファイル コントロール (fcntl) ヘッダー [(fcntl.h:1-5)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/fcntl.h#L1-L5) で定義されています: `O_RDONLY`、`O_WRONLY`、`O_RDWR`、`O_CREATE`、および `O_TRUNC`。これらは `open` に、ファイルを読み取り、書き込み、または読み取りと書き込みの両方で開くように指示し、ファイルが開かない場合はファイルを作成します。存在し、ファイルの長さをゼロに切り詰めます。

`fork` と `exec` が別々の呼び出しであることがなぜ役立つかは明らかです。この 2 つの呼び出しの間では、シェルはメイン シェルの I/O セットアップを妨げることなく子の I/O をリダイレクトする機会があります。代わりに、架空の `forkexec` システム コールを組み合わせて想像することもできますが、そのような呼び出しで I/O リダイレクトを実行するためのオプションは扱いにくいように思えます。シェルは、`forkexec` を呼び出す前に自身の I/O 設定を変更することができます (その後、それらの変更を元に戻します)。または、`forkexec` は I/O リダイレクトの命令を引数として受け取ることができます。または、(あまり魅力的ではありませんが) `cat` のようなすべてのプログラムに、独自の I/O リダイレクトを実行するように教えることもできます。

`fork` はファイル記述子テーブルをコピーしますが、基礎となる各ファイル オフセットは親と子の間で共有されます。次の例を考えてみましょう。

    if(fork() == 0) {
      write(1, "hello ", 6);
      exit(0);
    } else {
      wait(0);
      write(1, "world\n", 6);
    }

このフラグメントの最後で、ファイル記述子 1 に添付されたファイルにはデータ `hello` `world` が含まれます。親の `write` (`wait` のおかげで、子の終了後にのみ実行されます) は、子の `write` が中断したところから再開します。この動作は、`(echo` `hello` などのシェル コマンドのシーケンスから順次出力を生成するのに役立ちます。 `echo` `world)` `>output.txt`。

`dup` システム コールは、既存のファイル記述子を複製し、同じ基礎となる I/O オブジェクトを参照する新しいファイル記述子を返します。 `fork` によって複製されたファイル記述子と同様に、両方のファイル記述子はオフセットを共有します。これは、`hello` `world` をファイルに書き込む別の方法です。

    fd = dup(1);
    write(1, "hello ", 6);
    write(fd, "world\n", 6);

2 つのファイル記述子が、一連の `fork` および `dup` 呼び出しによって同じ元のファイル記述子から派生された場合、オフセットを共有します。それ以外の場合、ファイル記述子は、同じファイルに対する `open` 呼び出しの結果であっても、オフセットを共有しません。 `dup` を使用すると、シェルで次のようなコマンドを実装できます: `ls` `existing-file` `non-existing-file` `>` `tmp1` `2>&1`。 `2>&1` は、記述子 1 の複製であるファイル記述子 2 をコマンドに与えるようにシェルに指示します。既存のファイルの名前と、存在しないファイルのエラー メッセージの両方が、ファイル `tmp1` に表示されます。 xv6 シェルはエラー ファイル記述子の I/O リダイレクトをサポートしていませんが、実装方法はわかりました。

ファイル記述子は、接続先の詳細を隠すため、強力な抽象化です。ファイル記述子 1 に書き込むプロセスは、ファイル、コンソールなどのデバイス、またはパイプに書き込む可能性があります。

## パイプ

*パイプ*は、読み取り用と書き込み用のファイル記述子のペアとしてプロセスに公開される小さなカーネル バッファーです。パイプの一端にデータを書き込むと、そのデータをパイプの他端から読み取ることができるようになります。パイプはプロセスが通信する方法を提供します。

次のコード例では、パイプの読み取り端に接続された標準入力を使用してプログラム `wc` を実行します。

    int p[2];
    char *argv[2];

    argv[0] = "wc";
    argv[1] = 0;

    pipe(p);
    if(fork() == 0) {
      close(0);
      dup(p[0]);
      close(p[0]);
      close(p[1]);
      exec("/bin/wc", argv);
    } else {
      close(p[0]);
      write(p[1], "hello world\n", 12);
      close(p[1]);
    }

プログラムは `pipe` を呼び出します。これにより、新しいパイプが作成され、読み取りおよび書き込みファイル記述子が配列 `p` に記録されます。 `fork` 以降は、親と子の両方にパイプを参照するファイル記述子があります。子は、`close` および `dup` を呼び出して、ファイル記述子ゼロがパイプの読み取り端を参照するようにし、`p` のファイル記述子を閉じ、`exec` を呼び出して `wc` を実行します。 `wc` が標準入力から読み取るときは、パイプから読み取ります。親はパイプの読み取り側を閉じ、パイプに書き込み、その後書き込み側を閉じます。

利用可能なデータがない場合、パイプ上の `read` は、データが書き込まれるか、書き込み端を参照するすべてのファイル記述子が閉じられるまで待機します。後者の場合、`read` はデータ ファイルの終わりに達したかのように 0 を返します。新しいデータの到着が不可能になるまで `read` がブロックするという事実は、上記の `wc` を実行する前に子がパイプの書き込み端を閉じることが重要である理由の 1 つです。 `wc` のファイル記述子の 1 つがパイプの書き込み端を参照していた場合、 `wc` はファイルの終わりを決して認識しません。

xv6 シェルは、上記のコード [(sh.c:101)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/sh.c#L101) と同様の方法で `grep fork sh.c | wc -l` などのパイプラインを実装します。子プロセスは、パイプラインの左端と右端を接続するパイプを作成します。次に、パイプラインの左端に対して `fork` と `runcmd` を呼び出し、右端に対して `fork` と `runcmd` を呼び出し、両方が終了するのを待ちます。パイプラインの右端は、それ自体がパイプを含むコマンド (例: `a` `|` `b` `|` `c`) であり、それ自体が 2 つの新しい子プロセス (`b` 用と `c` 用) をフォークします。したがって、シェルはプロセスのツリーを作成する場合があります。このツリーの葉はコマンドであり、内部ノードは左右の子が完了するまで待機するプロセスです。

パイプは一時ファイルよりも強力ではないように見えるかもしれません: パイプライン

    echo hello world | wc

次のようにパイプなしで実装できます

    echo hello world >/tmp/xyz; wc </tmp/xyz

この状況では、パイプには一時ファイルに比べて少なくとも 3 つの利点があります。まず、パイプは自動的にクリーンアップされます。ファイル リダイレクトの場合、シェルは完了時に `/tmp/xyz` を削除するように注意する必要があります。第 2 に、パイプは任意の長さのデータ ストリームを渡すことができますが、ファイル リダイレクトにはすべてのデータを保存するのに十分な空き領域がディスク上に必要です。第三に、パイプを使用するとパイプライン ステージの並列実行が可能になりますが、ファイル アプローチでは、2 番目のプログラムが開始される前に最初のプログラムが終了する必要があります。

## ファイルシステム

xv6 ファイル システムは、解釈されないバイト配列を含むデータ ファイルと、データ ファイルや他のディレクトリへの名前付き参照を含むディレクトリを提供します。ディレクトリは、*root* と呼ばれる特別なディレクトリから始まるツリーを形成します。 `/a/b/c` のような *パス* は、ルート ディレクトリ `/` の `a` という名前のディレクトリ内の `b` という名前のディレクトリ内の `c` という名前のファイルまたはディレクトリを指します。 `/` で始まらないパスは、呼び出しプロセスの *現在のディレクトリ* を基準にして評価されます。これは `chdir` システム コールで変更できます。これらのコード フラグメントはどちらも同じファイルを開きます (関連するすべてのディレクトリが存在すると仮定します)。

    chdir("/a");
    chdir("b");
    open("c", O_RDONLY);

    open("/a/b/c", O_RDONLY);

最初のフラグメントは、プロセスの現在のディレクトリを `/a/b` に変更します。 2 番目のメソッドは、プロセスの現在のディレクトリを参照したり変更したりしません。

新しいファイルとディレクトリを作成するシステム コールがあります。`mkdir` は新しいディレクトリを作成し、`O_CREATE` フラグを指定した `open` は新しいデータ ファイルを作成し、`mknod` は新しいデバイス ファイルを作成します。この例では、次の 3 つすべてを示します。

    mkdir("/dir");
    fd = open("/dir/file", O_CREATE|O_WRONLY);
    close(fd);
    mknod("/console", 1, 1);

`mknod` は、デバイスを参照する特別なファイルを作成します。デバイス ファイルには、カーネル デバイスを一意に識別するメジャー デバイス番号とマイナー デバイス番号 (`mknod` への 2 つの引数) が関連付けられています。後でプロセスがデバイス ファイルを開くと、カーネルは `read` および `write` システム コールをファイル システムに渡すのではなく、カーネル デバイス実装に転送します。

ファイルの名前は、ファイル自体とは異なります。 *inode* と呼ばれる同じ基礎となるファイルは、*links* と呼ばれる複数の名前を持つことができます。各リンクはディレクトリ内のエントリで構成されます。エントリにはファイル名と i ノードへの参照が含まれます。 inode は、ファイルのタイプ (ファイル、ディレクトリ、またはデバイス)、長さ、ディスク上のファイル内容の場所、ファイルへのリンクの数など、ファイルに関する *メタデータ* を保持します。

`fstat` システム コールは、ファイル記述子が参照する i ノードから情報を取得します。 [`stat.h`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/stat.h) で次のように定義されている `struct` `stat` を埋めます。

    #define T_DIR     1   // ディレクトリ
    #define T_FILE    2   // ファイル
    #define T_DEVICE  3   // デバイス

    struct stat {
      int dev;     // ファイルシステムのディスクデバイス
      uint ino;    // i ノード番号
      short type;  // ファイルの種類
      short nlink; // ファイルへのリンクの数
      uint64 size; // ファイルのサイズ (バイト単位)
    };

`link` システム コールは、既存のファイルと同じ i ノードを参照する別のファイル システム名を作成します。このフラグメントは、`a` と `b` の両方という名前の新しいファイルを作成します。

    open("a", O_CREATE|O_WRONLY);
    link("a", "b");

`a` に対する読み取りまたは書き込みは、`b` に対する読み取りまたは書き込みと同じです。各 i ノードは、一意の *inode* *番号* によって識別されます。上記のコード シーケンスの後、`fstat` の結果を検査することで、`a` と `b` が同じ基になるコンテンツを参照していることを判断できます。両方とも同じ i ノード番号 (`ino`) を返し、`nlink` カウントは 2 に設定されます。

`unlink` システム コールは、ファイル システムから名前を削除します。ファイルの i ノードとそのコンテンツを保持するディスク領域は、ファイルのリンク数が 0 で、ファイル記述子がそれを参照していない場合にのみ解放されます。したがって、追加

    unlink("a");

最後のコード シーケンスでは、inode とファイルのコンテンツは `b` としてアクセス可能なままになります。さらに、

    fd = open("/tmp/xyz", O_CREATE|O_RDWR);
    unlink("/tmp/xyz");

これは、プロセスが `fd` を閉じるか終了するときにクリーンアップされる名前のない一時 i ノードを作成する慣用的な方法です。

Unix では、`mkdir`、`ln`、`rm` などのユーザーレベルのプログラムとしてシェルから呼び出し可能なファイル ユーティリティが提供されています。この設計により、誰でも新しいユーザーレベルのプログラムを追加してコマンドライン インターフェイスを拡張できます。今になって考えると、この計画は明白に思えますが、Unix の時代に設計された他のシステムでは、そのようなコマンドがシェルに組み込まれている (そしてシェルがカーネルに組み込まれている) ことがよくありました。

1 つの例外は `cd` で、これはシェル [(sh.c:166)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/sh.c#L166) に組み込まれています。 `cd` は、シェル自体の現在の作業ディレクトリを変更する必要があります。 `cd` が通常のコマンドとして実行された場合、シェルは子プロセスをフォークし、子プロセスは `cd` を実行し、 `cd` は *child* の作業ディレクトリを変更します。親 (つまり、シェル) の作業ディレクトリは変更されません。

## 現実世界

Unix の「標準」ファイル記述子、パイプ、およびそれらを操作するための便利なシェル構文の組み合わせは、汎用の再利用可能なプログラムの作成において大きな進歩でした。このアイデアは、Unix の力と人気の多くを担った「ソフトウェア ツール」の文化を引き起こし、シェルは最初のいわゆる「スクリプト言語」となりました。 Unix システム コール インターフェイスは、現在でも BSD、Linux、macOS などのシステムに残っています。

Unix システム コール インターフェイスは、ポータブル オペレーティング システム インターフェイス (POSIX) 標準によって標準化されています。 Xv6 は POSIX 準拠ではありません。多くのシステム コール (`lseek` などの基本的なものを含む) が欠落しており、提供されるシステム コールの多くは標準とは異なります。 xv6 の主な目標は、シンプルな UNIX のようなシステム コール インターフェイスを提供しながら、単純さと明確さを実現することです。基本的な Unix プログラムを実行するために、いくつかのシステム コールと単純な C ライブラリを追加して xv6 を拡張した人もいます。ただし、最新のカーネルは、xv6 よりも多くのシステム コールと、より多くの種類のカーネル サービスを提供します。たとえば、ネットワーク、ウィンドウ システム、ユーザー レベルのスレッド、多くのデバイスのドライバーなどをサポートします。最新のカーネルは継続的かつ急速に進化し、POSIX を超える多くの機能を提供します。

Unix は、単一セットのファイル名およびファイル記述子インターフェイスを使用して、複数のタイプのリソース (ファイル、ディレクトリ、およびデバイス) への統合アクセスを実現します。このアイデアは、より多くの種類のリソースに拡張できます。良い例は、「リソースはファイルである」という概念をネットワーク、グラフィックスなどに適用した Plan 9 (Presotto et al. 1991) です。ただし、ほとんどの Unix 由来のオペレーティング システムはこの道をたどっていません。

ファイル システムとファイル記述子は強力な抽象化です。それでも、オペレーティング システム インターフェイスには他のモデルもあります。 Unix の前身である Multics は、ファイル ストレージをメモリのように見せる方法で抽象化し、非常に異なるフレーバーのインターフェイスを生み出しました。 Multics 設計の複雑さは、よりシンプルなものを構築することを目指した Unix の設計者に直接影響を与えました。

Xv6 は、ユーザーの概念や、あるユーザーを別のユーザーから保護するという概念を提供しません。 Unix 用語では、すべての xv6 プロセスは root として実行されます。

この本では、xv6 が Unix のようなインターフェイスをどのように実装するかを検証しますが、そのアイデアと概念は Unix 以外にも当てはまります。どのオペレーティング システムも、基盤となるハードウェア上でプロセスを多重化し、プロセスを相互に分離し、制御されたプロセス間通信のメカニズムを提供する必要があります。 xv6 を学習した後は、他のより複雑なオペレーティング システムにも目を向け、それらのシステムの xv6 の基礎となる概念も理解できるようになります。

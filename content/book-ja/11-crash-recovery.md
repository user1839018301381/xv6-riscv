ファイルシステム設計における最も興味深い問題の 1 つは、クラッシュからの回復です。この問題は、多くのファイルシステム操作でディスクへの複数回の書き込みが行われ、書き込みの一部が終了した後のクラッシュにより、ディスク上のファイルシステムが不整合な状態になる可能性があるために発生します。

たとえば、ファイルの切り捨て中にクラッシュが発生したとします。切り捨てには、(少なくとも) 2 つのディスクブロックへの書き込みが含まれます。1 つは inode を含み、もう 1 つは空きブロックビットマップの一部を含みます。inode の長さはゼロに設定され、inode 内のブロック番号はクリアされ、ファイルのブロックのビットマップビットはゼロに設定される (空きブロックとしてマークされる) 必要があります。

1 回の書き込み後、カーネルが 2 回目の書き込みを実行する前にクラッシュが発生すると、ディスク上のファイルシステムが不正な状態のままになります。ビットマップ書き込みのみが発生した場合、クラッシュと再起動後の結果は、フリーとマークされたブロックを参照するゼロ以外の長さの inode になります。inode への書き込みのみが発生した場合、その結果、どのファイルにも使用されていないが、空きとしてマークされていないブロックが作成されます。

後者は比較的問題はありませんが、解放されたブロックを参照する inode は再起動後に深刻な問題を引き起こす可能性があります。再起動後、カーネルがそのブロックを別のファイルに割り当てる可能性があり、現在、2 つの異なるファイルが意図せずに同じブロックを指していることになります。xv6 が複数のユーザーをサポートしている場合、古いファイルの所有者は、別のユーザーが所有する新しいファイルのブロックを読み書きできるため、この状況はセキュリティ上の問題になる可能性があります。

xv6 は、単純な形式のログを使用して、ファイルシステム操作中のクラッシュの問題を解決します。xv6 システムコールは、ディスク上のファイルシステムデータ構造を直接書き込みません。代わりに、実行したいすべてのディスク書き込みの説明をディスク上の *ログ* に記録します。システムコールがすべての書き込みをログに記録すると、ログに完全な操作が含まれていることを示す特別な *コミット* レコードがディスクに書き込まれます。

その時点で、システムコールは書き込み内容をディスク上のファイルシステムデータ構造にコピーします。これらの書き込みが完了すると、システムコールによってディスク上のログが消去されます。

システムがクラッシュして再起動した場合、ファイルシステムコードはプロセスを実行する前に次のようにクラッシュから回復します。ログに完全な操作が含まれているとマークされている場合、リカバリコードは書き込みをディスク上のファイルシステム内の属する場所にコピーします。ログが完全な操作を含むものとしてマークされていない場合、リカバリコードはログを無視します。リカバリーコードはログを消去することで終了します。

なぜ xv6 のログはファイルシステム操作中のクラッシュの問題を解決するのでしょうか?操作がコミットされる前にクラッシュが発生した場合、ディスク上のログには完了のマークが付けられず、リカバリコードはそれを無視し、ディスクの状態は操作がまだ開始されていないかのような状態になります。操作のコミット後にクラッシュが発生した場合、リカバリでは操作のすべての書き込みが再実行され、操作がディスク上のデータ構造への書き込みを開始していた場合は、おそらく書き込みが繰り返されます。

いずれの場合も、ログによりクラッシュに関して操作がアトミックになります。つまり、回復後、操作のすべての書き込みがディスク上に表示されるか、まったく表示されません。

## ログの設計

ログは、スーパーブロックで指定された既知の固定場所 (図 [10.2](#fig:fslayout) を参照) に存在します。これは、ヘッダーブロックとそれに続く一連の更新されたブロックコピー (「ログブロック」) で構成されます。ヘッダーブロックには、ログに記録されたブロックごとに 1 つずつブロック番号の配列とログブロックの数が含まれます。ディスク上のヘッダーブロックのカウントは、ログにトランザクションが存在しないことを示すゼロ、または指定された数のログ記録されたブロックを持つ完全にコミットされたトランザクションがログに含まれていることを示すゼロ以外のいずれかです。

xv6 は、トランザクションがコミットされる前ではなく、コミット時にヘッダーブロックを書き込み、ログに記録されたブロックをファイルシステムにコピーした後にカウントを 0 に設定します。したがって、トランザクションの途中でクラッシュが発生すると、ログのヘッダーブロックのカウントは 0 になります。コミット後にクラッシュすると、カウントはゼロ以外になります。

各システムコールのコードは、クラッシュに関してアトミックである必要がある一連の書き込みの開始と終了を示します。異なるプロセスによるファイルシステム操作の同時実行を可能にするために、ロギングシステムは複数のシステムコールの書き込みを 1 つのトランザクションに蓄積できます。したがって、1 つのコミットに複数の完全なシステムコールの書き込みが含まれる場合があります。

システムコールが複数のトランザクションに分割されるのを避けるため、ロギングシステムは、ファイルシステムのシステムコールが進行中でない場合にのみコミットします。

複数のトランザクションを一緒にコミットするという考え方は、*グループコミット*として知られています。グループコミットでは、コミットの固定コストが複数の操作で償却されるため、ディスク操作の数が削減されます。また、グループコミットは、ディスクシステムに同時により多くの同時書き込みを渡し、おそらく 1 回のディスクローテーション中にディスクがすべての書き込みを行えるようにします。xv6 の virtio ドライバーはこの種の *バッチ処理* をサポートしていませんが、xv6 のファイルシステム設計ではそれが可能です。

グループコミットの微妙な意味は、書き込みシステムコールの効果が非同期になることです。つまり、書き込みシステムコールがアプリケーションに戻った後でも、変更したブロックがディスク上にあるという保証はありません。たとえば、書き込みトランザクションが終了すると、別のトランザクションが開始されている可能性があり、その書き込みトランザクションは 2 番目のトランザクションとともに 1 つのグループとしてコミットされ、2 番目のトランザクションがコミットされるまでディスクへの書き込みの影響が遅れます。

アプリケーションが変更が永続化される (つまり、ディスク上にある) まで待機したい場合は、書き込みシステムコールの後に [`sync`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/log.c#L247) システムコールを呼び出すことができます。`sync` は、進行中のグループコミットがコミットされるまで待機します。

xv6 は、ログを保持するためにディスク上の固定量のスペースを専用に割り当てます。トランザクション内のシステムコールによって書き込まれるブロックの総数は、そのスペースに収まる必要があります。これには 2 つの影響があります。単一のシステムコールで、ログ内のスペース以上の個別のブロックを書き込むことはできません。これはほとんどのシステムコールでは問題になりませんが、そのうちの 2 つ (`write` と `unlink`) は多くのブロックを書き込む可能性があります。

大きなファイルの書き込みでは、inode ブロックだけでなく、多くのデータブロック、多くのビットマップブロックが書き込まれる可能性があります。大きなファイルのリンクを解除すると、多くのビットマップブロックと inode が書き込まれる可能性があります。xv6 の書き込みシステムコールは、大きな書き込みをログに収まる複数の小さな書き込みに分割します。実際には、xv6 ファイルシステムは 1 つのビットマップブロックのみを使用するため、`unlink` は問題を引き起こしません。

ログスペースが限られている場合のもう 1 つの影響は、システムコールの書き込みがログに残っているスペースに収まるということが確実でない限り、ロギングシステムはシステムコールの開始を許可できないことです。

## コード: ロギング
システムコールでのログの一般的な使用法は次のようになります。

      begin_op();
      ...
      bp = bread(...);
      bp->data[...] = ...;
      log_write(bp);
      ...
      end_op();

[`begin_op`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/log.c#L129) は、ロギングシステムが現在コミット中でなく、この呼び出しからの書き込みを保持するのに十分な未予約のログスペースが確保されるまで待機します。`log.outstanding` は、ログスペースを予約したシステムコールの数をカウントします。

予約スペースの合計は `log.outstanding` と `MAXOPBLOCKS` の積です。`log.outstanding` をインクリメントすると、スペースが確保され、このシステムコール中にコミットが発生するのが防止されます。コードは、各システムコールが最大 `MAXOPBLOCKS` の個別のブロックを書き込む可能性があることを控えめに想定しています。

[`log_write`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/log.c#L224) は `bwrite` のプロキシとして機能します。ブロックのブロック番号をメモリに記録し、それをディスク上のログのスロットに予約し、ブロックキャッシュがバッファを追い出すのを防ぐためにブロックキャッシュにバッファを固定します。

ブロックはコミットされるまでキャッシュ内に存在しなければなりません。それまでは、キャッシュされたコピーが変更の唯一の記録となります。コミットが完了するまで、ディスク上のその場所に書き込むことはできません。同じトランザクション内の他の読み取りでは変更が確認される必要があります。`log_write` は、単一トランザクション中にブロックが複数回書き込まれるとそれを認識し、そのブロックをログ内の同じスロットに割り当てます。

この最適化は、*吸収*と呼ばれることがよくあります。たとえば、複数のファイルの inode を含むディスクブロックがトランザクション内で複数回書き込まれるのは一般的です。複数のディスク書き込みを 1 つに吸収することで、ファイルシステムはログスペースを節約し、ディスクブロックのコピーを 1 つだけディスクに書き込むだけでよいため、パフォーマンスを向上させることができます。

[`end_op`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/log.c#L155) は、まず未処理のシステムコールの数をデクリメントします。カウントがゼロになった場合は、`commit().` を呼び出して現在のトランザクションをコミットします。このプロセスには 4 つの段階があります。

[`write_log()`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/log.c#L188) は、トランザクションで変更された各ブロックをバッファキャッシュからディスク上のログのスロットにコピーします。[`write_head()`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/log.c#L105) はヘッダーブロックをディスクに書き込みます。

これがコミットポイントで、書き込み後にクラッシュが発生すると、ログからトランザクションの書き込みを再生して回復することになります。[`install_trans`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/log.c#L68) は、ログから各ブロックを読み取り、ファイルシステム内の適切な場所に書き込みます。

最後に、`end_op` はログヘッダーをカウント 0 で書き込みます。これは、次のトランザクションがログに記録されたブロックの書き込みを開始する前に実行する必要があります。これにより、クラッシュによって、あるトランザクションのヘッダーと後続のトランザクションのログに記録されたブロックが使用されて回復することがなくなります。

`end_op` の実装における重要な前提は、`write_head` がヘッダーブロックをアトミックに (完全に、またはまったく更新せず) 更新するということです。第[10](/book/chapter-10/#CH:FS) を思い出してください。xv6 のブロックは 2 つのディスクセクターですが、ログヘッダーは最初のセクターに収まるため、ディスクが単一セクターの更新がアトミックであることのみを保証しても問題はありません。

[`recover_from_log`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/log.c#L119) は [`initlog`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/log.c#L55) から呼び出され、これは起動中に最初のユーザープロセス [(proc.c:526)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L526) が実行される前の [`fsinit`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/fs.c#L42) から呼び出されます。これはログヘッダーを読み取り、ヘッダーがログにコミットされたトランザクションが含まれていることを示している場合、`end_op` のアクションを模倣します。

ログの使用例は [`filewrite`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/file.c#L135) にあります。トランザクションは次のようになります。

          begin_op();
          ilock(f->ip);
          r = writei(f->ip, ...);
          iunlock(f->ip);
          end_op();

このコードは、ログのオーバーフローを避けるために、大規模な書き込みを一度に数ブロックずつの個別のトランザクションに分割するループでラップされています。`writei` を呼び出すと、このトランザクションの一部として多くのブロック (ファイルの inode、1 つ以上のビットマップブロック、およびいくつかのデータブロック) が書き込まれます。

## 現実世界

xv6 のログシステムは非効率的です。コミットは、ファイルシステムのシステムコールと同時に実行できません。ブロック内の数バイトだけが変更された場合でも、システムはブロック全体をログに記録します。同期ログ書き込みは一度に 1 ブロックずつ実行され、それぞれの書き込みにディスク全体の回転時間が必要になる可能性があります。実際のロギングシステムは、これらすべての問題に対処します。

- ログを記録することだけがクラッシュから回復する唯一の方法ではありません。初期のファイルシステムでは、再起動中にスカベンジャー (UNIX `fsck` プログラムなど) を使用して、すべてのファイルとディレクトリ、およびブロックと inode の空きリストを検査し、不整合を探して解決していました。大規模なファイルシステムでは清掃に数時間かかる場合があり、元のシステムコールがアトミックになるような方法で不整合を解決できない状況もあります。

ログからの回復ははるかに高速であり、クラッシュが発生した場合でもシステムコールがアトミックになります。

## 演習

1. ログがどのように使用されるかを理解するには、`kernel/fs.c` の関数 `writei()` の `log_write` ステートメントの前に次のコード行を挿入します。

        printk("log write %d: %d %d %d\n", addr, bp->blockno, off, n);

    Run make clean and then make qemu, and at the xv6 shell prompt run the following command:

        $ echo hi > f

    You should see output similar to this:

        log write 47: 47 368 16
        log write 936: 936 0 2
        log write 936: 936 2 1

    The output indicates that `log_write` is called three times for this shell command. Why is `log_write` called 3 times? What does each `log_write` write? Does the first write above correspond to updating the root directory and the other two writes correspond to writing file f?

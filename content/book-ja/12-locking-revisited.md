優れた並列パフォーマンス、同時実行にもかかわらず正確性、および理解可能なコードを同時に取得することは、カーネル設計における大きな課題です。ロックを単純に使用することが正確さを保つための最良の方法ですが、常に可能であるとは限りません。この章では、xv6 が複雑な方法でロックの使用を強制される例と、xv6 がロックに似た技術を使用するがロックは使用しない例を取り上げます。

## ロックパターン

キャッシュされたアイテムは、多くの場合、ロックが困難です。たとえば、ファイル システムのブロック キャッシュ [(bio.c:25)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/bio.c#L25) には、最大 `NBUF` ディスク ブロックのコピーが保存されます。特定のディスク ブロックのキャッシュ内にコピーが 1 つだけ存在することが重要です。そうしないと、異なるプロセスが、同じブロックであるべきものの異なるコピーに競合する変更を加える可能性があります。キャッシュされた各ブロックは [`struct buf`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/buf.h) に保存されます。 `struct buf` には、一度に 1 つのプロセスだけが特定のディスク ブロックを使用することを保証するロック フィールドがあります。しかし、そのロックだけでは十分ではありません。ブロックがキャッシュ内にまったく存在せず、2 つのプロセスがそれを同時に使用したい場合はどうなるでしょうか? `struct buf` は存在しないため (ブロックがまだキャッシュされていないため)、ロックするものは何もありません。 Xv6 は、追加のロック (`bcache.lock`) をキャッシュされたブロックの ID セットに関連付けることによって、この状況に対処します。ブロックがキャッシュされているかどうかを確認する必要があるコード (例: [`bget`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/bio.c#L58))、またはキャッシュされたブロックのセットを変更する必要があるコードは、`bcache.lock` を保持する必要があります。コードが必要なブロックと `struct buf` を見つけた後、`bcache.lock` を解放し、特定のブロックのみをロックできます。これは一般的なパターンです。アイテムのセットに対して 1 つのロックと、アイテムごとに 1 つのロックが追加されます。

通常、ロックを取得した同じ関数がロックを解放します。しかし、より正確に物事を捉える方法は、アトミックに見える必要があるシーケンスの開始時にロックが取得され、そのシーケンスが終了すると解放されるということです。シーケンスが異なる関数、異なるスレッド、または異なる CPU で開始および終了する場合、ロックの取得と解放は同じように行う必要があります。ロックの機能は、データの一部を特定のエージェントに固定することではなく、他の使用を強制的に待機させることです。一例は、[`yield`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L501) の `acquire` で、これは取得プロセスではなくスケジューラー スレッドで解放されます。別の例は、[`ilock`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/fs.c#L295) の `acquiresleep` です。このコードは、ディスクの読み取り中にスリープすることがよくあります。別の CPU でウェイクアップする可能性があります。これは、ロックが別の CPU で取得および解放される可能性があることを意味します。

オブジェクトに埋め込まれたロックによって保護されているオブジェクトを解放することは、ロックを所有しているだけでは解放が正しいかどうかを保証するのに十分ではないため、デリケートな作業です。問題のケースは、他のスレッドがオブジェクトの使用を `acquire` で待機しているときに発生します。オブジェクトを解放すると、埋め込まれたロックが暗黙的に解放され、待機中のスレッドが誤動作する原因になります。解決策の 1 つは、オブジェクトへの参照がいくつ存在するかを追跡し、最後の参照がなくなった場合にのみ解放されるようにすることです。例については、[`pipeclose`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L59) を参照してください。 `pi->readopen` および `pi->writeopen` は、パイプにそれを参照するファイル記述子があるかどうかを追跡します。

通常、関連する項目のセットに対する読み取りと書き込みのシーケンスの周りにロックが見られます。ロックにより、他のスレッドは完了した更新シーケンスのみを参照できるようになります (スレッドもロックしている限り)。更新が単一の共有変数への単純な書き込みである場合はどうなるでしょうか?たとえば、`setkilled` と [`killed`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L623) は、`p->killed` の単純な使用法を中心にロックされています。ロックがない場合、あるスレッドが `p->killed` を読み取ると同時に、別のスレッドが  を書き込む可能性があります。これはレースであり、C 言語仕様では、レースによって *未定義の動作*が生じると記載されており、これは、プログラムがクラッシュしたり、誤った結果が得られる可能性があることを意味します[^1]。ロックは競合を防止し、未定義の動作を回避します。

競合によってプログラムが破損する理由の 1 つは、ロックまたは同等の構造がない場合、コンパイラが元の C コードとはまったく異なる方法でメモリの読み取りおよび書き込みを行うマシン コードを生成する可能性があることです。たとえば、`killed` を呼び出すスレッドのマシン コードは、`p->killed` をレジスタにコピーし、そのキャッシュされた値のみを読み取ることができます。これは、スレッドが `p->killed` への書き込みをまったく認識しない可能性があることを意味します。ロックはそのようなキャッシュを防ぎます。

## ロックのようなパターン

多くの場所で、xv6 はロックのような方法で参照カウントまたはフラグを使用して、オブジェクトが割り当てられており、解放または再利用すべきではないことを示します。プロセスの `p->state` は、`file`、`inode`、および `buf` 構造体の参照カウントと同様に、このように動作します。いずれの場合も、ロックはフラグまたは参照カウントを保護しますが、オブジェクトが早期に解放されるのを防ぐのは後者です。

ファイル システムは、コードが通常のロックを使用した場合に発生するデッドロックを回避するために、複数のプロセスが保持できる一種の共有ロックとして `struct inode` 参照カウントを使用します。たとえば、[`namex`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/fs.c#L692) のループは、各パス名コンポーネントによって指定されたディレクトリを順番にロックします。ただし、`namex` はループの最後で各ロックを解放する必要があります。これは、 が複数のロックを保持している場合、パス名にドットが含まれている場合 (`a/./b` など)、 自体がデッドロックする可能性があるためです。また、ディレクトリと `..` を含む同時検索によりデッドロックが発生する可能性があります。 第[10](/book/chapter-10/#CH:FS) で説明されているように、解決策は、ループがディレクトリ i ノードを参照カウントをインクリメントしながら次の反復に持ち越しますが、ロックは行わないことです。

一部のデータ項目は、異なる時点で異なるメカニズムによって保護され、明示的なロックではなく、xv6 コードの構造によって暗黙的に同時アクセスから保護される場合があります。たとえば、物理ページが空いている場合、そのページは [`kmem.lock`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/kalloc.c#L24) によって保護されます。その後、ページがパイプ [(pipe.c:23)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L23) として割り当てられると、そのページは別のロック (埋め込み `pi->lock`) によって保護されます。ページが新しいプロセスのユーザー メモリに再割り当てされた場合、そのページはロックによってまったく保護されません。代わりに、アロケーターがそのページを (解放されるまで) 他のプロセスに与えないという事実により、同時アクセスからページが保護されます。新しいプロセスのメモリの所有権は複雑です。最初に親が `fork` でメモリを割り当てて操作し、次に子がそれを使用し、(子が終了した後) 親が再びメモリを所有して `kfree` に渡します。ここで得られる教訓は 2 つあります。データ オブジェクトは、存続期間のさまざまな時点でさまざまな方法で同時実行から保護される可能性があること、およびその保護は、明示的なロックではなく暗黙的な構造の形をとる可能性があることです。

最後のロックに似た例は、[`myproc()`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L83) のように、`mycpu()` への呼び出しに関する割り込みを無効にする必要があることです。割り込みを無効にすると、タイマー割り込みに関して呼び出しコードがアトミックになり、コンテキストの切り替えが強制されるため、プロセスが別の CPU に移動する可能性があります。

## ロックがまったくありません

xv6 には、ロックをまったく行わずに可変データを共有する場所がいくつかあります。 1 つはスピンロックの実装にありますが、RISC-V のアトミック命令はハードウェアに実装されたロックに依存していると見ることもできます。もう 1 つは [`main.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/main.c#L7) の `started` 変数で、CPU 0 が xv6 の初期化を完了するまで他の CPU が実行されないようにするために使用されます。 `volatile` は、コンパイラーが実際にロードおよびストア命令を生成することを保証します。

Xv6 には、1 つの CPU またはスレッドがデータを書き込み、別の CPU またはスレッドがデータを読み取るケースが含まれますが、そのデータを保護するための専用のロックはありません。たとえば、`fork` では、親が子のユーザー メモリ ページを書き込み、子 (おそらく別の CPU 上の別のスレッド) がそれらのページを読み取ります。ロックなしはそれらのページを明示的に保護します。親の書き込みが完了するまで子は実行を開始しないため、これは厳密にはロックの問題ではありません。これは潜在的なメモリ順序の問題です ([7] (/book/chapter-7/#CH:LOCK) 章を参照)。メモリバリアがなければ、ある CPU が別の CPU の書き込みを認識することを期待する理由がないからです。ただし、起動時に親がロックを解放し、子がロックを取得するため、`acquire` および `release` のメモリ バリアにより、子の CPU が親の書き込みを認識できるようになります。

## 並列処理

ロックは主に、正確さを保つために並列処理を抑制することを目的としています。パフォーマンスも重要であるため、カーネル設計者は多くの場合、正確性を実現し、並列処理を可能にする方法でロックを使用する方法を考える必要があります。 xv6 は高パフォーマンスを目指して体系的に設計されていませんが、どの xv6 操作が並列実行可能で、どの操作がロックで競合する可能性があるかを検討する価値はあります。

xv6 のパイプは、かなり優れた並列処理の例です。各パイプには独自のロックがあるため、異なるプロセスが異なる CPU 上で異なるパイプを並行して読み書きできます。ただし、特定のパイプについては、ライターとリーダーはお互いにロックを解放するのを待つ必要があります。同じパイプを同時に読み書きすることはできません。空のパイプからの読み取り (または満杯のパイプへの書き込み) をブロックする必要がある場合もありますが、これはロック スキームによるものではありません。

コンテキストの切り替えは、より複雑な例です。それぞれ独自の CPU で実行される 2 つのカーネル スレッドは、`yield`、`sched`、および `swtch` を同時に呼び出すことができ、呼び出しは並列に実行されます。スレッドはそれぞれロックを保持しますが、それらは異なるロックであるため、互いに待つ必要はありません。ただし、`scheduler` になると、プロセスのテーブルで `RUNNABLE` を検索しているときに、2 つの CPU がロックで競合する可能性があります。つまり、xv6 はコンテキストの切り替え中に複数の CPU からパフォーマンス上の利点を得る可能性がありますが、おそらくそれほどではありません。

もう 1 つの例は、異なる CPU 上の異なるプロセスからの `fork` への同時呼び出しです。 `pid_lock` と `kmem.lock` の呼び出し、および `UNUSED` プロセスのプロセス テーブルを検索するために必要なプロセスごとのロックを呼び出すために、相互に待機する必要がある場合があります。一方、2 つのフォーク プロセスは、ユーザー メモリ ページをコピーし、ページ テーブル ページを完全に並行してフォーマットできます。

上記の各例のロック方式では、場合によっては並列パフォーマンスが犠牲になります。いずれの場合も、より精巧な設計を使用することで、より多くの並列処理を実現できます。それが価値があるかどうかは、関連する操作が呼び出される頻度、競合したロックが保持された状態でコードが費やす時間、競合する操作を同時に実行している可能性のある CPU の数、コードの他の部分がより制限的なボトルネックになっているかどうかなどの詳細によって決まります。特定のロック スキームがパフォーマンス上の問題を引き起こす可能性があるかどうか、または新しい設計の方が大幅に優れているのかどうかを推測するのは難しい場合があるため、多くの場合、現実的なワークロードでの測定が必要になります。

## 演習

1. xv6 のパイプ実装を変更して、同じパイプへの読み取りと書き込みが異なる CPU 上で並行して実行できるようにします。

2. 異なる CPU が同時に実行可能なプロセスを探している場合のロック競合を減らすために、xv6 の `scheduler()` を変更します。

3. xv6 の `fork()` のシリアル化の一部を削除します。

xv6 を含むほとんどのカーネルは、複数のアクティビティの実行をインターリーブします。インターリーブの原因の 1 つはマルチプロセッサ ハードウェアです。つまり、xv6 の RISC-V など、独立して実行される複数の CPU を備えたコンピュータです。これらの複数の CPU は物理 RAM を共有し、xv6 はその共有を利用して、すべての CPU が読み書きできるカーネル データ構造を維持します。この共有により、1 つの CPU がデータ構造を読み取っている間に別の CPU がデータ構造の更新を行ったり、複数の CPU が同じデータを同時に更新したりする可能性が生じます。慎重に設計しないと、このような並列アクセスにより誤った結果が得られたり、データ構造が壊れたりする可能性があります。ユニプロセッサ上でも、カーネルが多数のスレッド間で CPU を切り替え、スレッドの実行がインターリーブされる場合があります。最後に、割り込み可能なコードと同じデータを変更するデバイス割り込みハンドラーは、割り込みされたコードがデータを変更しているときに割り込みが発生すると、データを損傷する可能性があります。 「同時実行性」という言葉は、マルチプロセッサの並列処理、スレッドの切り替え、または割り込みにより、複数の命令ストリームがインターリーブされる状況を指します。

カーネルには、同時にアクセスされるデータがたくさんあります。たとえば、2 つの CPU が同時に `kalloc` を呼び出すことができ、それによってフリー リストの先頭から同時にポップされます。カーネル設計者は、パフォーマンスと応答性を向上させることができるため、多くの同時実行を許可することを好みます。ただし、同時実行にもかかわらず、正しいことを自分自身に納得させる必要があります。同時実行下での正確性を目的とした戦略、およびそれをサポートする抽象化は、*同時実行制御* テクニックと呼ばれます。

この章では、広く使用されている同時実行制御手法である *ロック* に焦点を当てます。プレビューとして、xv6 カーネルでのロックの使用法は次のようになります。

    struct spinlock lk;
    ...;
    acquire(&lk);
    ... read or write some shared data ...
    release(&lk);

ロックは相互排他を提供し、一度に 1 つの CPU だけがロックを保持できるようにします。プログラマが各共有データ項目にロックを関連付け、項目を使用するときにコードが常に関連付けられたロックを保持する場合、その項目は一度に 1 つの CPU によってのみ使用されます。この状況では、ロックがデータ項目を保護すると言います。ロックは理解しやすい同時実行制御メカニズムですが、保護するデータに対する同時操作をシリアル化することでパフォーマンスを制限する可能性があります。

この章の残りの部分では、xv6 がロックを必要とする理由、xv6 がロックを実装する方法、およびロックを使用する方法について説明します。

ロックが必要な理由の例として、2 つの異なる CPU 上で `wait` システム コールを呼び出す、終了した子を持つ 2 つのプロセスを考えてみましょう。 `wait` は子供の記憶を解放します。したがって、各 CPU で、カーネルは `kfree` を呼び出して子のメモリ ページを解放します。カーネル アロケータは空きページのリンク リストを維持します。[`kalloc()`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/kalloc.c#L69) はリストからメモリのページをポップし、[`kfree()`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/kalloc.c#L47) はリストにページをプッシュします。最高のパフォーマンスを得るには、2 つの親プロセスの `kfree` が、どちらかを待たずに並行して実行されることを期待できますが、xv6 の `kfree` 実装を考えると、これは正しくありません。

図 [7.1](#fig:smp) は設定をより詳細に示しています。空きページのリンクされたリストは 2 つの CPU によって共有されるメモリ内にあり、ロードおよびストア命令を使用してリストを操作します。 (実際には、プロセッサにはキャッシュがありますが、概念的には、マルチプロセッサ システムは単一の共有メモリがあるかのように動作します。) 同時リクエストがない場合は、次のようにリスト `push` 操作を実装できます。

```c
    struct element {
      int data;
      struct element *next;
    };

    struct element *list = 0;

    void
    push(int data)
    {
      struct element *l;

      l = malloc(sizeof *l);
      l->data = data;
      l->next = list;
      list = l;
   }
```

この実装は、単独で実行した場合には正しく実行されます。ただし、複数のコピーが同時に実行される場合、コードは正しくありません。 2 つの CPU が同時に `push` を実行する場合、図 [7.1](#fig:smp) に示すように、どちらかが 16 行目を実行する前に両方が 15 行目を実行する可能性があり、図 [7.2](#fig:race) に示すように誤った結果が生じます。この場合、`next` が以前の同じ値 `list` に設定された 2 つのリスト要素が存在します。 `list` への 2 つの割り当てが 16 行目で行われると、2 番目の割り当てが最初の割り当てを上書きします。最初の割り当てに関係する要素は失われます。

16 行目で失われた更新は *レース* の例です。競合とは、メモリ位置が同時にアクセスされ、少なくとも 1 つのアクセスが書き込みである状況です。競合は多くの場合、更新の喪失 (アクセスが書き込みの場合) または不完全に更新されたデータ構造の読み取りのいずれかのバグの兆候です。競合の結果は、コンパイラーによって生成されたマシン コード、関連する 2 つの CPU のタイミング、およびそれらのメモリー操作がメモリー システムによってどのように順序付けされるかによって決まります。そのため、競合によって引き起こされるエラーの再現とデバッグが困難になる可能性があります。たとえば、`push` のデバッグ中に print ステートメントを追加すると、実行のタイミングが変化して競合がなくなる可能性があります。

競合を回避する通常の方法は、ロックを使用することです。ロックにより *相互排他 * が保証されるため、一度に 1 つの CPU だけが `push` の機密行を実行できます。これにより、上記のシナリオは不可能になります。上記のコードの正しくロックされたバージョンでは、ほんの数行が追加されます (黄色で強調表示されています)。

```c
   struct element *list = 0;
   struct lock listlock;

   void
   push(int data)
   {
     struct element *l;
     l = malloc(sizeof *l);
     l->data = data;

     acquire(&listlock);
     l->next = list;
     list = l;
     release(&listlock);
   }
```

`acquire` と `release` の間の一連の命令は、*クリティカル セクション*と呼ばれることがよくあります。ロックは`list`を保護していると言われています。

ロックがデータを保護すると言うとき、実際には、ロックがデータに適用される不変条件のコレクションを保護することを意味します。不変条件は、操作全体にわたって維持されるデータ構造のプロパティです。通常、操作の正しい動作は、操作の開始時に不変条件が true であるかどうかによって決まります。操作は一時的に不変条件に違反する可能性がありますが、終了する前に不変条件を再確立する必要があります。たとえば、リンク リストの場合、不変条件は、`list` がリストの最初の要素を指し、各要素の `next` フィールドが次の要素を指すことです。 `push` の実装は、この不変条件に一時的に違反します。17 行目で、`l` は次のリスト要素を指しますが、`list` はまだ `l` を指しません（18 行目で再確立）。上で調べた競合は、リストの不変条件が (一時的に) 違反されている間に、2 番目の CPU がリストの不変条件に依存するコードを実行したために発生しました。ロックを適切に使用すると、クリティカル セクションのデータ構造を一度に 1 つの CPU だけが操作できるようになり、データ構造の不変条件が保持されない場合には CPU がデータ構造操作を実行しなくなります。

ロックは、同時クリティカル セクションを *シリアル化* し、一度に 1 つずつ実行することで不変条件を保持すると考えることができます (クリティカル セクションが分離されていても正しいと仮定します)。同じロックで保護されているクリティカル セクションは相互にアトミックであると考えることもできます。そのため、各セクションでは以前のクリティカル セクションからの変更の完全なセットのみが表示され、部分的に完了した更新は表示されません。

ロックは正確さを保つために役立ちますが、本質的にパフォーマンスを制限します。たとえば、2 つのプロセスが `kfree` を同時に呼び出した場合、ロックによって 2 つのクリティカル セクションがシリアル化されるため、それらを異なる CPU で実行する利点はありません。複数のプロセスが同時に同じロックを必要とする場合、またはロックが *競合* する場合、複数のプロセスが *競合* すると言います。カーネル設計における大きな課題は、並列性を追求する際のロック競合の回避です。 Xv6 はそのようなことはほとんど行いませんが、洗練されたカーネルは、特にロックの競合を避けるためにデータ構造とアルゴリズムを編成します。リストの例では、カーネルは CPU ごとに個別のフリー リストを維持し、現在の CPU のリストが空で、別の CPU からメモリを盗む必要がある場合にのみ、別の CPU のフリー リストに触れます。他の使用例では、より複雑な設計が必要になる場合があります。

ロックの配置もパフォーマンスにとって重要です。たとえば、`acquire` を `push` 内の 13 行目より前に移動するのは正しいことになります。ただし、`malloc` への呼び出しがシリアル化されるため、パフォーマンスが低下する可能性があります。以下の「ロックの使用」セクションでは、`acquire` および `release` 呼び出しを挿入する場所に関するガイドラインを示します。

## コード: ロック

[`kernel/spinlock.h`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.h)と[`kernel/spinlock.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.c)をお読みください。

Xv6 には、スピンロックとスリープロックという 2 種類のロックがあります。スピンロックから始めます。 Xv6 はスピンロックを [`struct spinlock`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.h#L2) として表します。構造体の重要なフィールドは `locked` です。このワードは、ロックが使用可能な場合は 0 であり、ロックが保持されている場合は 0 以外になります。同時実行性がない場合、xv6 は次のようなコードでロックを取得できます。

```c
   void
   acquire(struct spinlock *lk) // 機能しません!
   {
     for(;;) {
       if(lk->locked == 0) {
         lk->locked = 1;
         break;
       }
     }
   }
```

残念ながら、この実装では同時実行時の相互排除は保証されません。 2 つの CPU が同時に 25 行目に到達し、`lk->locked` がゼロであることを確認し、26 行目を実行してロックを取得する可能性があります。この時点で、2 つの異なる CPU がロックを保持することになり、相互排他特性に違反します。必要なのは、行 25 と行 26 を *アトミック* (分割不可能な) ステップとして実行する方法です。

ロックは広く使用されているため、マルチコア プロセッサは通常、行 25 と行 26 をアトミックにするために使用できる命令を提供します。 RISC-V では、この命令は `amoswap r, r, a` です。 `amoswap` 命令は、メモリ アドレス `a` の値を読み取り、レジスタ `r` の内容をそのアドレスに書き込み、読み取った値を `r` に書き込みます。つまり、レジスタの内容とアドレス指定されたメモリ位置を交換します。特別なハードウェアを使用してこのシーケンスをアトミックに実行し、他の CPU が読み取りと書き込みの間にメモリ アドレスを使用するのを防ぎます。

C コンパイラは、アトミックな命令を生成する「アトミック」組み込み関数のファミリーを提供します。 Xv6 の `acquire()` は `__atomic_exchange_n(addr, value, ...)` を使用します。これは、要するに `amoswap` 命令になります。この関数は、`addr` の古い (スワップされた) 内容を返します。 `acquire` でループを記述する良い方法は次のとおりです。

      while (__atomic_exchange_n(&lk->locked, 1, __ATOMIC_ACQUIRE) != 0)
        ;

Xv6 の [`acquire`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.c#L22) は上記のループを使用します (セクション [7.6](/book/chapter-7/#SEC:MEMORDER) で `__ATOMIC_ACQUIRE` について説明します)。各反復では 1 つを `lk->locked` に交換し、前の値をチェックします。前の値が 0 の場合、ロックが取得されており、スワップによって `lk->locked` が 1 に設定されます。以前の値が 1 の場合、他の CPU がロックを保持しており、1 つを `lk->locked` にアトミックにスワップしてもその値は変わりません。

ロックが取得されると、`acquire` はデバッグのために、ロックを取得した CPU を記録します。 `lk->cpu` フィールドはロックによって保護されており、ロックを保持している間のみ変更する必要があります。

関数 [`release`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.c#L46) は `acquire` の逆で、`lk->cpu` フィールドをクリアしてからロックを解放します。概念的には、このリリースでは `lk->locked` にゼロが割り当てられるだけです。 C 標準では、コンパイラーが複数のストア命令を使用して代入を実装できるため、C の代入は同時実行コードに関して非アトミックになる可能性があります。代わりに、`release` は、単一の分割不可能な操作でアドレスに 0 を格納する C アトミック関数 `__atomic_store_n(addr, 0, ...)` を使用します。

## コード: ロックの使用

Xv6 は競合を避けるために多くの場所でロックを使用します。前述したように、[`kalloc`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/kalloc.c#L69) と [`kfree`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/kalloc.c#L47) が良い例です。演習 1 と 2 を試して、これらの関数がロックを省略した場合に何が起こるかを確認してください。おそらく、不正な動作を引き起こすのは難しいことがわかります。これは、コードにロック エラーや競合がないかどうかを確実にテストするのが難しいことを示唆しています。 Xv6 にはまだ発見されていない種族が存在する可能性があります。

ロックの使用で難しいのは、使用するロックの数と、各ロックでどのデータと不変条件を保護するかを決定することです。いくつかの基本原則があります。まず、ある CPU によるメモリ位置の書き込みと同時に、別の CPU による読み取りまたは書き込みが行われる可能性のあるコードでは、2 つの操作が重複しないようにロックを使用する必要があります。次に、ロックは不変条件を保護することに注意してください。不変条件に複数のメモリ位置が含まれる場合、通常、不変条件が維持されるようにするには、それらすべてを 1 つのロックで保護する必要があります。

上記のルールでは、ロックが必要な場合については述べていますが、ロックが不要な場合については何も述べていません。ロックは並列性を低下させるため、ロックしすぎないことが効率のために重要です。並列処理が重要でない場合は、スレッドを 1 つだけにして、ロックを気にしないようにすることもできます。単純なカーネルは、単一のロックを持つことでマルチプロセッサ上でこれを実行できます。カーネルは、システム コールまたは割り込みのためにユーザー空間からカーネルに入るたびにロックを取得します。カーネルはユーザー空間に戻るとロックを解放します。多くのユニプロセッサ オペレーティング システムは、「ビッグ カーネル ロック」とも呼ばれるこのアプローチを使用してマルチプロセッサで実行できるように変換されていますが、このアプローチでは並列性が犠牲になります。つまり、カーネル内で一度に実行できるのは 1 つの CPU だけです。カーネルが大量の CPU 時間を消費する場合、さまざまなロックでさまざまなオブジェクトまたはモジュールを保護することで、より多くの並列処理が得られるため、カーネルのさまざまな部分でさまざまな CPU が同時に実行される可能性があります。

粗粒ロックの例として、xv6 の `kalloc.c` アロケーターには、単一のロックで保護された単一のフリー リストがあります。異なる CPU 上の複数のプロセスが同時にページを割り当てようとすると、各プロセスは `acquire` でスピンして順番を待つ必要があります。スピンは有益な作業ではないため、CPU 時間を無駄にします。ロックの競合によって CPU 時間のかなりの部分が無駄になっている場合は、アロケータを変更して、CPU ごとに個別のフリー リストを持ち、それぞれに独自のロックがあり、真に並列割り当てができるようにすることで、パフォーマンスを改善できる可能性があります。

詳細なロックの例として、xv6 にはファイルごとに個別のロックがあるため、異なるファイルを操作するプロセスは、多くの場合、互いのロックを待たずに続行できます。プロセスが同じファイルの異なる領域に同時に書き込むことができるようにしたい場合は、ファイル ロック スキームをさらに細かくすることができます。最終的には、ロックの粒度の決定は、パフォーマンス要件と複雑さの考慮事項によって決定される必要があります。

## デッドロックとロックの順序付け

CPU C1 と C2 で実行されている関数がどちらも、ロック A とロック B の両方を保持する必要があるポイントがあり、それらを異なる順序で取得するとします。

::: センター
<figure><img src="/book/fig/order.svg" alt="image" loading="lazy"><figcaption>画像</figcaption></figure>

少し運が悪いと、C1 と C2 の両方がまったく同じ瞬間に最初の取得を実行する可能性があります。異なるロックを要求しているため、どちらも成功する可能性があります。ただし、両方のロックがすでに他の CPU によって保持されているため、C1 と C2 は両方とも `acquire()` への 2 回目の呼び出しで待機する必要があります。両方の CPU がお互いを待機しているため、どちらもロックを解放せず、両方とも永久に待機することになります。この状況は *デッドロック* と呼ばれます。

C1/C2 の例の主な問題は、2 つの CPU が異なる順序でロックを取得したことです。両者が最初に A を取得しようとした場合、一方が A を取得し、次に B を取得してから両方を解放し、その後、もう一方の CPU が続行する可能性があります。より一般的には、ロック コードはデッドロックを回避するためにこのルールに従う必要があります。複数のロックを保持するすべてのコード パスは、同じ順序でロックを取得する必要があります。このグローバルなロック取得順序の必要性は、ロックが実質的に各関数の仕様の一部であることを意味します。呼び出し元は、合意された順序でロックが取得されるように関数を呼び出す必要があります。

Xv6 には、`sleep`/`wakeup` メカニズムの動作方法により、プロセスごとのロック (各 `struct proc` のロック) を伴う長さ 2 のロック順序チェーンが多数あります ([9] 章 (/book/chapter-9/#CH:SLEEP) を参照)。たとえば、[`consoleintr`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/console.c#L147) は、入力された文字を処理する割り込みルーチンです。改行が到着すると、コンソール入力を待機しているプロセスが起動される必要があります。これを行うために、`consoleintr` は `cons.lock` を保持しながら `wakeup` を呼び出し、待機中のプロセスをウェイクアップするためにそのロックを取得します。その結果、グローバルなデッドロックを回避するロック順序には、プロセス ロックの前に `cons.lock` を取得する必要があるというルールが含まれます。ファイル システム コードには、xv6 の最長のロック チェーンが含まれています。たとえば、ファイルを作成するには、ディレクトリのロック、新しいファイルの i ノードのロック、ディスク ブロック バッファのロック、ディスク ドライバの `vdisk_lock`、および呼び出しプロセスの `p->lock` を同時に保持する必要があります。デッドロックを回避するために、ファイル システム コードは常に、前の文で説明した順序でロックを取得します。

グローバルなデッドロック回避命令を遵守することは、驚くほど難しい場合があります。場合によっては、ロック順序が論理プログラム構造と競合することがあります。たとえば、コード モジュール M1 がモジュール M2 を呼び出す可能性がありますが、ロック順序では M1 のロックの前に M2 のロックを取得する必要があります。場合によっては、次に取得するロックの ID を検出するために 1 つのロックを保持する必要があるため、ロックの ID が事前に分からないことがあります。この種の状況は、ファイル システムがパス名で連続するコンポーネントを検索するときに発生し、`wait` および `exit` システム コールのコードがプロセスのテーブルを検索して子プロセスを検索するときに発生します。最後に、ロックが増えるとデッドロックが発生する機会が増えることを意味するため、デッドロックの危険性が、ロック スキームをどの程度きめ細かく作成できるかについての制約となることがよくあります。デッドロックを回避する必要性は、多くの場合、カーネル実装における主要な要素です。

時々生じる疑問は、同じ CPU がすでに保持しているロックを CPU が取得しようとした場合に何が起こるかということです。他の CPU はロックを保持できないため、保護されたデータの使用を CPU が互いに干渉することを心配する必要はありません。 CPU がすでに保持しているロックを再取得できるようにするロック システムは、*リエントラント* または *再帰* と呼ばれます。一方、同じ CPU であってもロックがすでに保持されている場合は、操作が一時的に一部の不変条件に違反し、まだ復元されていない可能性があることを意味します。不変式が成立しないときに新しい操作を開始できるようにするのは、バグを招くように思えます。 Xv6 は後者の考え方を採用し、現在ロックを保持している CPU がロックを再取得することを禁止します。この状況を検出することが、`acquire` での `holding` への呼び出しの目的です。

## ロックと割り込み
一部の xv6 スピンロックは、スレッドと割り込みハンドラーの両方で使用されるデータを保護します。たとえば、カーネル スレッドが [`sys_pause`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/sysproc.c#L77) の `ticks` を読み取るのとほぼ同時に、`clockintr` タイマー割り込みハンドラーは [`ticks`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c#L167) をインクリメントする可能性があります。ロック `tickslock` は 2 つのアクセスをシリアル化します。

スピンロックと割り込みの相互作用により、潜在的な危険が生じます。 `sys_pause` が `tickslock` を保持し、その CPU がタイマー割り込みによって割り込まれたとします。 `clockintr` は `tickslock` を取得しようとし、それが保持されていることを確認し、解放されるのを待ちます。この状況では、`tickslock` は決して解放されません。`sys_pause` のみが解放できますが、`clockintr` が戻るまで `sys_pause` は実行を継続しません。そのため、CPU はデッドロックになり、ロックを必要とするコードもフリーズします。

この状況を回避するには、スピンロックが割り込みハンドラーによって使用されている場合、CPU は割り込みが有効な状態でそのロックを決して保持してはなりません。 Xv6 はより保守的です。CPU がロックを取得すると、xv6 は常にその CPU の割り込みを無効にします。他の CPU でも割り込みが発生する可能性があるため、割り込みの `acquire` はスレッドがスピンロックを解放するのを待つことができます。同じCPU上ではないだけです。

Xv6 は、CPU がスピンロックを保持していない場合に割り込みを再度有効にします。ネストされたクリティカルセクションに対処するために、少しの記録を行う必要があります。 `acquire` は [`push_off`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.c#L93) を呼び出し、`release` は [`pop_off`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.c#L106) を呼び出して、現在の CPU のロックのネスト レベルを追跡します。そのカウントがゼロに達すると、`pop_off` は最も外側のクリティカル セクションの開始時に存在していた割り込みイネーブル状態を復元します。 `push_off` および `pop_off` は、`intr_on` および `rc_sstatus(SSTATUS_SIE)` を使用して、`sstatus` (スーパーバイザー ステータス) レジスタの `SIE` (スーパーバイザー割り込みイネーブル) ビットを変更することによって、割り込みを有効または無効にするように CPU に指示します。後者は `SIE` ビットをクリアします。

[`lk->locked`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.c#L37) を設定する前に、`acquire` が `push_off` を厳密に呼び出すことが重要です。この 2 つが逆の場合、割り込みが有効になっている状態でロックが保持される時間が短くなり、残念なことにタイミングを合わせた割り込みによってシステムがデッドロックされてしまいます。同様に、`release` はロック [(spinlock.c:73)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.c#L73) を解放した後にのみ `pop_off` を呼び出すことが重要です。

## 命令とメモリの順序付け
ソース コードのステートメントが出現する順序でプログラムが実行されると考えるのは自然なことです。これはシングルスレッド コードの合理的なメンタル モデルですが、実際には起こりません。

理由の 1 つは、コンパイラがソース コードで暗示されている順序とは異なる順序でロードおよびストア命令を発行し、(たとえばデータをレジスタにキャッシュすることによって) それらを完全に省略する可能性があることです。もう 1 つの理由は、CPU がパフォーマンスを向上させるために命令を順不同で実行する可能性があることです。たとえば、CPU は、一連の命令 A と B が互いに依存していないことに気づく場合があります。 CPU は、その入力が A の入力よりも前に準備ができているため、または A と B の実行をオーバーラップするために、命令 B を最初に開始することがあります。

複数のスレッドが共有メモリを介して対話する場合、CPU とコンパイラによるメモリ アクセスの並べ替えにより問題が発生する可能性があります (Waterman and Asanovic 2024; Boehm 2005)。問題が発生する可能性のある例として、`push` のこのコードで、コンパイラまたは CPU が行 4 に対応するストアを行 6 の `release` の後のポイントに移動すると、大惨事になります。

```c
      l = malloc(sizeof *l);
      l->data = data;
      acquire(&listlock);
      l->next = list;
      list = l;
      release(&listlock);
```

このような並べ替えが発生した場合、別の CPU がロックを取得して更新された `list` を観察できる期間が存在しますが、初期化されていない `list->next` が表示されることになります。

良いニュースは、コンパイラーと CPU がプログラマーに再順序付けを防ぐ方法を提供することです。これらは、xv6 では、`acquire` および `release` で使用される C アトミック関数の `__ATOMIC_ACQUIRE` および `__ATOMIC_RELEASE` 引数として表示されます。それぞれに2つの効果があります。まず、それぞれがアトミック呼び出しを超えてメモリ参照を移動しないようにコンパイラに指示します。第 2 に、それぞれの関数は、アトミック呼び出し用に生成された命令を超えて実行時のメモリ参照を移動しないよう CPU に指示する命令を生成するようにコンパイラに指示します。このような「通過禁止」ポイントは、*記憶バリア* または *フェンス* と呼ばれます。

xv6 のスピンロック関数のバリアは、ロックを使用するコードに 2 つの重要な影響を与えます。まず、`release()` より前の C コード内で発生するすべてのメモリ参照 (読み取りおよび書き込み) は、`release()` が完了する前にメモリ システム上で有効になることが保証されます。これには、クリティカル セクション内のメモリ参照とクリティカル セクション前のメモリ参照の両方が含まれます。第 2 に、`acquire` 以降の C コード内のすべてのメモリ参照は、`acquire()` で `amoswap` が正常に完了するまでは有効にならないことが保証されています**。繰り返しますが、これにはクリティカル セクション内の参照と `release` 以降の参照の両方が含まれます。

これらのバリアは重要な推移的な効果を生み出します。たとえば、CPU が新しく割り当てられたデータ オブジェクトに (ロックを保持せずに) 書き込み、クリティカル セクションでそのオブジェクトをリストにリンクした場合、その後ロックを取得してリストからオブジェクトへのポインタを取得する CPU は、最初の CPU の書き込みを監視することが保証されます。

xv6 は共有データへのアクセスにロックを使用するため、xv6 の `acquire` および `release` のバリアは、重要なほぼすべてのケースで順序を強制します。 第[12](/book/chapter-12/#CH:LOCK2) では、いくつかの例外について説明します。

## アトミックスによるプログラミング

xv6 ではこれが行われませんが、ロックを使用せずにアトミック命令を直接使用することで、競合を回避しながら共有データを更新できる場合があります。ほとんどの CPU は、通常、メモリ位置を読み取り、値を変更し、新しい値を同じメモリ位置にアトミックに書き込むというパターンで、数十のアトミック命令を便利に提供します。 RISC-V `amoadd` 命令はその一例です。この命令は、レジスタの内容をメモリ内の場所にアトミックに追加します。 C コンパイラは、これらの命令に「アトミック」ラッパーを提供します。[^1] したがって、コードは次を使用してロックなしで共有カウンターをインクリメントできます。

      __atomic_fetch_add(&counter, 1, __ATOMIC_SEQ_CST);

ロックは CPU 時間を消費するため、またはデッドロック回避などの構造的な理由によりロックの使用が困難になるため、ロックを回避すると便利な場合があります。

## スリープロック

場合によっては、xv6 は長時間ロックを保持する必要があります。たとえば、ファイル システム (第[10](/book/chapter-10/#CH:FS)) は、ディスク上のコンテンツの読み取りおよび書き込み中にファイルをロックしたままにし、これらのディスク操作には数十ミリ秒かかる場合があります。スピンロックをそれほど長く保持すると、別のプロセスがスピンロックを取得しようとした場合に無駄が発生します。これは、取得プロセスがスピン中に長時間 CPU を浪費することになるためです。スピンロックのもう 1 つの欠点は、プロセスがスピンロックを保持したまま CPU を譲れないことです。ロックのあるプロセスがディスクを待機している間、他のプロセスが CPU を使用できるようにこれを行いたいと考えています。スピンロックを保持したまま放棄することは違法です。2 番目のスレッドがスピンロックを取得しようとした場合にデッドロックが発生する可能性があるためです。 `acquire` は CPU を解放しないため、2 番目のスレッドの回転により、最初のスレッドの実行とロックの解放が妨げられる可能性があります。ロックを保持している間に放棄すると、スピンロックが保持されている間は割り込みをオフにしなければならないという要件にも違反します。したがって、取得を待機している間は CPU を解放し、ロックが保持されている間は解放 (および割り込み) を許可するタイプのロックが必要です。

Xv6 は、このようなロックを *スリープロック* の形式で提供します。 [`acquiresleep`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/sleeplock.c#L22) は、[9](/book/chapter-9/#CH:SLEEP) 章で説明する手法を使用して、待機中に CPU を譲ります。高レベルでは、スリープ ロックにはスピンロックによって保護される `locked` フィールドがあります。スリープ ロックが保持されている場合、`acquiresleep` はスピンロックを解放し、`sleep` を呼び出します。これにより、`releasesleep` が `wakeup` を呼び出すまで CPU が解放されます。その結果、`acquiresleep` が待機している間に他のスレッドが実行できるようになります。

スリープ ロックは割り込みを有効にしたままにするため、割り込みハンドラーでは使用できません。 `acquiresleep` は CPU を解放する可能性があるため、スピンロック クリティカル セクション内でスリープ ロックを使用することはできません (ただし、スピンロックはスリープ ロック クリティカル セクション内で使用できます)。

スピンロックは、待機すると CPU 時間が無駄になるため、短いクリティカルセクションに最適です。スリープロックは長時間の操作に適しています。

## 現実世界

同時実行プリミティブと並列処理に関する長年の研究にもかかわらず、ロックを使用したプログラミングは依然として困難です。 xv6 ではこれを行いませんが、多くの場合、同期キューなどの上位レベルの構造内にロックを隠すことが最善です。ロックを使用してプログラムする場合は、ロックを必要とする不変式を見逃しやすいため、人種を識別するツールを使用することが賢明です。

ほとんどのオペレーティング システムは POSIX スレッド (Pthread) をサポートしており、ユーザー プロセスが異なる CPU 上で複数のスレッドを同時に実行できるようになります。 Pthreads は、ユーザーレベルのロック、バリアなどをサポートしています。Pthreads を使用すると、プログラマがオプションでロックを再入可能にすることを指定することもできます。

ユーザー レベルで Pthread をサポートするには、オペレーティング システムのサポートが必要です。たとえば、ある pthread がシステム コールでブロックされた場合でも、同じプロセスの別の pthread がその CPU 上で実行できるはずです。別の例として、pthread がそのプロセスのアドレス空間を変更した場合 (メモリのマップまたはマップ解除など)、カーネルは、同じプロセスのスレッドを実行する他の CPU がハードウェア ページ テーブルを更新して、アドレス空間の変更を反映するように調整する必要があります。

アトミック命令を使わずにロックを実装することも可能ですが (Lamport 1974)、コストがかかるため、ほとんどのオペレーティング システムはアトミック命令を使用します。

多くの CPU が同時に同じロックを取得しようとすると、ロックのコストが高くなる可能性があります。 1 つの CPU のローカル キャッシュにロックがキャッシュされており、別の CPU がそのロックを取得する必要がある場合、ロックを保持しているキャッシュ ラインを更新するアトミック命令により、そのラインを 1 つの CPU のキャッシュから他の CPU のキャッシュに移動し、場合によってはキャッシュ ラインの他のコピーを無効にする必要があります。別の CPU のキャッシュからキャッシュ ラインをフェッチすると、ローカル キャッシュからラインをフェッチするよりも桁違いにコストが高くなる可能性があります。

ロックに関連する費用を回避するために、多くのオペレーティング システムではロックフリーのデータ構造とアルゴリズムが使用されています（Herlihy and Shavit 2012; Mckenney et al. 2013）。たとえば、この章の冒頭にあるような、リスト検索中にロックを必要とせず、リストに項目を挿入するための 1 つのアトミック命令を必要とするリンク リストを実装することができます。ただし、ロックフリーのプログラミングは、ロックのプログラミングよりも複雑です。たとえば、命令とメモリの並べ替えについて心配する必要があります。ロックを使用したプログラミングはすでに難しいため、xv6 ではロックなしのプログラミングによるさらなる複雑さを回避します。

[`kalloc`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/kalloc.c#L69) 内の `acquire` および `release` への呼び出しをコメント化します。これは、`kalloc` を呼び出すカーネル コードに問題を引き起こす可能性があるようです。どのような症状が予想されますか? xv6 を実行すると、次のような症状が発生しますか? `usertests`を実行する場合はどうですか？問題が見つからない場合は、なぜ問題が発生しないのでしょうか? `kalloc` のクリティカル セクションにダミー ループを挿入して問題を引き起こすことができるかどうかを確認してください。

2. (`kalloc` でロックを復元した後) 代わりに、`kfree` のロックをコメントアウトしたとします。何が問題になる可能性がありますか? `kfree` にロックがないことは、`kalloc` よりも害が少ないでしょうか?

3. 2 つの CPU が同時に `kalloc` を呼び出すと、一方が他方を待つ必要があり、パフォーマンスが低下します。 `kalloc.c` を変更して並列性を高め、異なる CPU からの `kalloc` への同時呼び出しがお互いを待たずに処理できるようにします。

4. POSIX スレッドを使用して並列プログラムを作成します。これは、ほとんどのオペレーティング システムでサポートされています。たとえば、並列ハッシュ テーブルを実装し、CPU の数の増加に応じて put/get の数が増加するかどうかを測定します。

5. xv6 で Pthread のサブセットを実装します。つまり、ユーザー プロセスが複数のスレッドを持つことができるようにユーザー レベルのスレッド ライブラリを実装し、これらのスレッドが異なる CPU で並行して実行できるようにします。ブロッキング システム コールを実行し、その共有アドレス空間を変更するスレッドを正しく処理する設計を考え出してください。

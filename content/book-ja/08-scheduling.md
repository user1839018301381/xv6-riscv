どのオペレーティング システムも、コンピュータに搭載されている CPU よりも多くのプロセスで実行される可能性が高いため、プロセス間で CPU をタイムシェアする計画が必要です。理想的には、共有はユーザープロセスに対して透過的であることが望まれます。一般的なアプローチは、プロセスをハードウェア CPU 上に「多重化」することで、各プロセスに独自の仮想 CPU があるかのように錯覚させることです。この章では、xv6 がこの多重化を実現する方法について説明します。

この章に進む前に、[`kernel/proc.h`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.h)、[`kernel/swtch.S`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/swtch.S)、および [`kernel/proc.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c) の `yield()`、`sched()`、および `scheduler()` をお読みください。

## 多重化

Xv6 は、2 つの状況で各 CPU を 1 つのプロセスから別のプロセスに切り替えることによって多重化します。まず、プロセスがブロックする (待機する必要がある) システム コール (`read` や `wait` など) を実行すると、xv6 が切り替わります。第 2 に、xv6 は、ブロックせずに長時間計算するプロセスに対処するようにスイッチを定期的に強制します。前者は自発的スイッチと呼ばれ、後者は非自発的スイッチと呼ばれます。

多重化の実装にはいくつかの課題があります。まず、あるプロセスから別のプロセスに切り替えるにはどうすればよいでしょうか?基本的な考え方は CPU レジスタを保存および復元することですが、これは C では表現できないため扱いが難しくなります。次に、ユーザー プロセスに対して透過的な方法で切り替えを強制するにはどうすればよいでしょうか? Xv6 は、ハードウェア タイマーの割り込みによってコンテキスト スイッチを駆動する標準的な手法を使用します。 3 番目に、すべての CPU が同じプロセスのセット間で切り替わるため、2 つの CPU が同じプロセスを同時に実行することを決定するなどの間違いを避けるために、ロック プランが必要です。第 4 に、プロセスのメモリとその他のリソースは、プロセスが終了するときに解放する必要がありますが、プロセス自体がすべてを完了することはできません。第 5 に、システム コールが正しいプロセスのカーネル状態に影響を与えるように、マルチコア マシンの各 CPU は、実行中のプロセスを記憶する必要があります。

## コンテキストスイッチの概要

「コンテキストスイッチ」という用語は、CPU が 1 つのカーネル スレッドの実行を中止し (通常は後で再開するため)、別のカーネル スレッドの実行を再開する手順を指します。この切り替えが多重化の核心です。 Xv6 は、あるプロセスのカーネル スレッドから別のプロセスのカーネル スレッドにコンテキストを直接切り替えません。代わりに、カーネル スレッドは、その CPU の「スケジューラ スレッド」にコンテキストを切り替えることで CPU を放棄し、スケジューラ スレッドは実行する別のプロセスのカーネル スレッドを選択し、そのスレッドにコンテキストを切り替えます。

## コード: コンテキストの切り替え

`kernel/swtch.S` の関数 `swtch()` には、スレッド コンテキスト切り替えの核心が含まれています。これは、切り替え元のスレッドの CPU レジスタを保存し、切り替え先のスレッドの以前に保存されたレジスタを復元します。これで十分な基本的な理由は、スレッドの状態がメモリ内のデータ (スタックなど) と CPU レジスタで構成されるためです。異なるスレッドはデータを RAM の異なる領域に保持するため、スレッド メモリを保存したり復元したりする必要はありません。ただし、CPU にはレジスタのセットが 1 つしかないため、スレッド間でレジスタを切り替える (保存および復元する) 必要があります。

各スレッドの `struct proc` には、スレッドが実行されていないときに保存されたレジスタを保持する `struct context` が含まれています。 CPU のスケジューラ スレッドの `struct context` は、その CPU の `struct cpu` 内にあります。スレッド X がスレッド Y に切り替えたい場合、スレッド X は `swtch(&X’s context, &Y’s context)` を呼び出します。 `swtch()` は、現在の CPU レジスタを X のコンテキストに保存し、Y のコンテキストの内容を CPU レジスタにロードしてから戻ります。

`swtch` の短縮コピーを次に示します。

    swtch:
            sd ra, 0(a0)
            sd sp, 8(a0)
            sd s0, 16(a0)
            ...
            sd s11, 104(a0)

            ld ra, 0(a1)
            ld sp, 8(a1)
            ld s0, 16(a1)
            ...
            ld s11, 104(a1)

            ret

`a0` は関数の最初の引数を保持し、`a1` は 2 番目の引数を保持します。この場合、2 つの `struct context` ポインターです。 `16(a0)` は、`a0` が指すメモリ内の 16 バイトのオフセットを指します。 [`kernel/proc.h`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.h#L2) の `struct context` の定義を参照すると、これは `s0` と呼ばれる構造体フィールドです。

`swtch`の`ret`はどこに戻るのでしょうか？ `ra`レジスタが指す命令に戻ります。スレッド X が `swtch()` を呼び出して Y に切り替える例では、`ret` が実行されると、`ra` は Y の `struct context` からロードされたばかりです。そして、Y の `struct context` 内の `ra` は、もともと Y が過去に CPU を手放したときに、Y が `swtch` を呼び出したことによって保存されました。したがって、`ret` は、Y が `swtch()` を呼び出した時点の後の命令に戻ります。つまり、X の `swtch()` 呼び出しは、Y の元の `swtch()` 呼び出しから戻ったかのように戻ります。また、`swtch` は Y の `struct context` から `sp` をロードしたため、`sp` は Y のスタック ポインタになります。したがって、戻ったときに、Y は独自のスタック上で実行されます。 `swtch()` はプログラム カウンターを直接保存または復元する必要はありません。 `ra` を保存して復元するだけで十分です。

[`swtch`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/swtch.S#L9) は呼び出し先が保存したレジスタ (`ra,sp,s0..s11`) を保存しますが、呼び出し元が保存したレジスタは保存しません。 RISC-V の呼び出し規則では、コードが関数呼び出し全体で呼び出し元が保存したレジスターの値を保持する必要がある場合、コンパイラーは関数呼び出しの前にレジスターをスタックに保存し、関数が戻ったときにスタックから復元する命令を生成する必要があります。したがって、`swtch` は、それを呼び出した関数が呼び出し元が保存したレジスターを既に保存していることを信頼できます (それか、呼び出し関数がレジスター内の値を必要としなかったかのどちらかです)。

## コード: スケジュール設定

最後のセクションでは、`swtch` の内部について説明しました。ここで、`swtch` を仮定して、あるプロセスのカーネル スレッドからスケジューラを介して別のプロセスへの切り替えを調べてみましょう。スケジューラは CPU ごとに特別なスレッドの形式で存在し、それぞれが `scheduler` 関数を実行します。この関数は、次に実行するプロセスの選択を担当します。複数の CPU が同時に実行するものを探している可能性があるため、各 CPU には独自のスケジューラ スレッドがあります。プロセスの切り替えは、あるプロセスから別のプロセスに直接ではなく、常にスケジューラー スレッドを経由して行われます。これは、スケジューラーを実行するスタックがない状況（古いプロセスが終了した場合や現在実行する他のプロセスが存在しない場合など）を避けるためです。

CPU を放棄したいプロセスは、自身のプロセス ロック `p->lock` を取得し、保持している他のロックを解放し、自身の状態 (`p->state`) を更新してから、`sched` を呼び出す必要があります。このシーケンスは [`yield`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L501)、`sleep`、`kexit` で確認できます。 `sched` は `swtch` を呼び出して、現在のコンテキストを `p->context` に保存し、`cpu->context` のスケジューラ コンテキストに切り替えます。 `swtch` は、`scheduler` の `swtch` が [(proc.c:453)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L453) を返したかのように、スケジューラのスタックに戻ります。

[`scheduler`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L429) はループを実行します。実行するプロセスを見つけて、そこに `swtch()` を送り、最終的にスケジューラに `swtch()` を戻し、ループを継続します。スケジューラは、プロセス テーブルをループして、`p->state` `==` `RUNNABLE` を持つ実行可能なプロセスを探します。プロセスが見つかると、CPU ごとの現在のプロセス変数 `c->proc` を設定し、そのプロセスを `RUNNING` としてマークし、`swtch` を呼び出して実行を開始します [(proc.c:448-453)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L448-L453)。過去のある時点で、ターゲット プロセスは `swtch()` を呼び出したはずです。スケジューラによる `swtch()` の呼び出しは、以前の呼び出しから事実上戻ります。図 [8.2](#fig:inout) はこのパターンを示しています。

xv6 は、`swtch` への呼び出し全体で `p->lock` を保持します。`swtch` の呼び出し元はロックを取得しますが、`swtch` が返された後にターゲットでロックが解放されます。この配置は異例です。ロックを取得したスレッドがロックを解放することの方が一般的です。 Xv6 のコンテキスト切り替えは、`p->state` と `p->context` を同時にアトミックに更新する必要があるため、この規則を破ります。たとえば、`swtch` を呼び出す前に `p->lock` が解放された場合、状態が `RUNNABLE` であるため、別の CPU $c$ がプロセスの実行を決定する可能性があります。 CPU $c$ は `swtch` を呼び出し、元の CPU が `p->context` に保存している間に `p->context` から復元します。その結果、CPU $c$ 上で部分的に保存されたレジスタを使用してプロセスが復元され、両方の CPU が同じスタックを使用することになり、混乱が発生します。 `yield` が実行中のプロセスの状態を `RUNNABLE` に変更し始めたら、プロセスがすべてのレジスタを保存し、スケジューラがスタック上で実行されるまで、`p->lock` は保持されたままでなければなりません。最も早い正しいリリース ポイントは、`scheduler` (独自のスタック上で実行) が `c->proc` をクリアした後です。同様に、`scheduler` が `RUNNABLE` プロセスを `RUNNING` に変換し始めると、プロセスのカーネル スレッドが完全に実行されるまで (`swtch` の後、たとえば `yield` で) ロックを解放できません。

スケジューラの `swtch` 呼び出しが `sched` に終わらない場合が 1 つあります。 `allocproc` は、新しいプロセスのコンテキスト `ra` レジスタを [`forkret`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L513) に設定し、その最初の `swtch` がその関数の先頭に「戻る」ようにします。 `forkret` は、`p->lock` を解放し、ユーザー空間に戻るために必要ないくつかの制御レジスタとトラップフレーム フィールドをセットアップするために存在します。最後に、`forkret` は、システム コールからユーザー空間に戻る通常のリターン パスをシミュレートします。

## コード: mycpu と myproc

Xv6 では、多くの場合、現在のプロセスの `proc` 構造体へのポインターが必要になります。ユニプロセッサでは、現在の `proc` を指すグローバル変数を持つことができます。各 CPU が異なるプロセスを実行するため、これはマルチコア マシンでは機能しません。この問題を解決する方法は、各 CPU に独自のレジスタ セットがあるという事実を利用することです。

特定の CPU がカーネル内で実行されている間、xv6 は、CPU の `tp` レジスタが常に CPU の hartid を保持することを保証します。 RISC-V は CPU に番号を付け、それぞれに固有の *hartid* を与えます。 [`mycpu`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L74) は、`tp` を使用して `cpu` 構造体の配列にインデックスを付け、現在の CPU の配列を返します。 [`struct cpu`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.h#L22) は、その CPU (存在する場合) で現在実行中のプロセスの `proc` 構造体へのポインタ、CPU のスケジューラ スレッド用に保存されたレジスタ、および割り込みの無効化を管理するために必要なネストされたスピンロックの数を保持します。

ユーザーコードは `tp` を自由に変更できるため、CPU の `tp` が CPU の hartid を保持していることを確認するのは少し複雑です。 `start` は、まだマシン モード [(start.c:48)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/start.c#L48) である間に、CPU のブート シーケンスの早い段階で `tp` レジスタを設定します。ユーザー空間に戻る準備中に、ユーザー コードによって `tp` が変更された場合に備えて、`prepare_return` は  をトランポリン ページに保存します。最後に、`uservec` は、ユーザー空間 [(trampoline.S:78)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trampoline.S#L78) からカーネルに入るときに、保存された `tp` を復元します。コンパイラは、カーネル コード内の `tp` を決して変更しないことを保証します。 xv6 が必要なときにいつでも RISC-V ハードウェアに現在の hartid を問い合わせることができればもっと便利ですが、RISC-V ではそれができるのはマシン モードのみであり、スーパーバイザ モードではできません。

`cpuid` と `mycpu` の戻り値は脆弱です。タイマーが割り込み、スレッドを放棄し、後で別の CPU で実行を再開した場合、以前に返された値は正しくなくなります。この問題を回避するために、xv6 では、`cpuid()` または `mycpu()` を呼び出す前に割り込みを無効にし、戻り値の使用が終了した場合にのみ割り込みを有効にするコードが必要です。

関数 [`myproc`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L83) は、現在の CPU で実行されているプロセスの `struct proc` ポインターを返します。 `myproc` は割り込みを無効にし、`mycpu` を呼び出し、`struct cpu` から現在のプロセス ポインター (`c->proc`) をフェッチしてから、割り込みを有効にします。 `myproc` の戻り値は、割り込みが有効になっている場合でも安全に使用できます。タイマー割り込みによって呼び出しプロセスが別の CPU に移動された場合、その `struct proc` ポインタは同じままになります。

## 現実世界

xv6 スケジューラは、各プロセスを順番に実行する単純なスケジューリング ポリシーを実装します。このポリシーは *ラウンドロビン* と呼ばれます。実際のオペレーティング システムでは、プロセスに優先順位を付けるなど、より高度なポリシーが実装されています。この考え方は、実行可能な優先度の高いプロセスが、実行可能な優先度の低いプロセスよりもスケジューラによって優先されるということです。これらのポリシーは、多くの場合、競合する目標があるため、複雑になる可能性があります。たとえば、オペレーティング システムは、公平性と高スループットの保証も必要とする場合があります。

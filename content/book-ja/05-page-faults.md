ページテーブルにマッピングがない仮想アドレスが使用される場合、`PTE_V` フラグがクリアされているマッピングがある場合、または許可ビット (`PTE_R`、`PTE_W`、`PTE_X`、`PTE_U`) が試行中の操作を禁止しているマッピングがある場合、RISC-V CPU はページフォールト例外を生成します。RISC-V は、ロードページフォールト (ロード命令によって引き起こされる)、ストアページフォールト (ストア命令によって引き起こされる)、および命令ページフォールト (実行される命令のフェッチによって引き起こされる) の 3 種類のページフォールトを区別します。`scause` レジスタはページフォルトのタイプを示し、`stval` レジスタには変換できなかったアドレスが含まれます。

ページテーブルとページフォルトの組み合わせは強力なツールです。ページテーブルは、カーネルに仮想アドレスと物理アドレス間の間接的なレベルを提供し、カーネルがアドレス空間の構造と内容を制御できるようにします。ページフォールトにより、カーネルはロードとストアをインターセプトし、ページテーブルを変更することで、それらの参照がどのデータを参照しているかをオンザフライで指定できるようになります。

カーネルはこれらの機能を使用して効率を高めることができます。たとえば、コピーオンライトフォークを使用すると、カーネルは親と子の間でメモリを透過的に共有できるため、どちらにも書き込まれないページをコピーするコストを回避できます。アプリケーションプログラマーにもメリットがあります。可能性の 1 つは、カーネルがページングを使用してファイルの内容をアプリケーションのアドレス空間に表示させ、ページフォールトに応じてファイルブロックを透過的に読み取るメモリマップトファイルです。

もう 1 つは遅延メモリ割り当てです。これにより、プログラムは巨大な仮想アドレス空間を要求できますが、支払うコストはプログラムが実際に読み書きするページに物理メモリを割り当てるだけです。xv6 は、遅延割り当てという 1 つの目的でのみページフォールトを使用します。

続行する前に、[`kernel/sysproc.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/sysproc.c) の関数 `sys_sbrk()` と [`kernel/vm.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/vm.c) の `vmfault` を読んでください。[`kernel/trap.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c) および [`kernel/vm.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/vm.c) で `vmfault` への通話を検索します。

## 遅延割り当て
xv6 の *遅延割り当て* には 2 つの部分があります。まず、アプリケーションがフラグ `SBRK_LAZY` を指定して `sbrk` を呼び出してメモリを要求すると、カーネルはサイズの増加を記録しますが、物理メモリを割り当てず、仮想アドレスの新しい範囲に PTE を作成しません。次に、これらの新しいアドレスの 1 つでページフォールトが発生すると、カーネルは物理メモリのページを割り当て、それをページテーブルにマップします。カーネルはアプリケーションに対して透過的に遅延割り当てを実装します。利点を得るためにアプリケーションを変更する必要はありません。

遅延割り当ては、必要なメモリ量を正確に予測する必要がないため、アプリケーションにとって便利です。たとえば、アプリケーションは入力を処理する可能性がありますが、入力がどのくらいの大きさになるかは事前にわかりません。遅延割り当てを使用すると、アプリケーションは最悪の場合に備えてメモリを要求できますが、この最悪の場合の費用を支払う必要はありません。カーネルは、アプリケーションが使用しないページに対して作業を行う必要がなく、他のアプリケーションが未使用のページを割り当てることができます。

さらに、アプリケーションがアドレス空間の大幅な拡大を要求している場合、遅延割り当てを使用しない `sbrk` はコストが高くなります。アプリケーションがギガバイトのメモリを要求している場合、カーネルは 262,144 個の 4096 バイトの物理ページをゼロに割り当てなければなりません。遅延割り当てにより、このコストを時間の経過とともに分散できます。一方、遅延割り当てでは、ユーザー/カーネルの移行を伴うページフォールトの余分なオーバーヘッドが発生します。

オペレーティングシステムは、ページフォールトごとに 1 ページではなく連続したページのバッチを割り当て、そのようなページフォールト用にカーネルの入口/終了コードを特殊化することによって、このコストを削減できます (ただし、xv6 はどちらも行いません)。

一方、遅延割り当てされたページでページフォールトが発生した場合、カーネルは、割り当てるための空きメモリがないことが判明する場合があります。この場合、カーネルにはメモリ不足エラーをアプリケーションに返す簡単な方法がなく、代わりにアプリケーションを強制終了します。割り当て失敗時のエラーを優先するアプリケーションの場合、xv6 では、フラグ `SBRK_EAGER` を指定して `sbrk` を呼び出すことで、アプリケーションがメモリを積極的に割り当てることができます。

## コード

システムコール `sbrk(n)` は、プロセスのメモリサイズを `n` バイトずつ拡大し (`n` が負の場合は縮小し)、新しく割り当てられた領域の先頭 (つまり、古いサイズ) を返します。カーネル実装は [`sys_sbrk`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/sysproc.c#L40) です。

アプリケーションが `SBRK_EAGER` を指定した場合、システムコールは関数 [`growproc`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L236) によって実装されます。`growproc` は `uvmalloc` を呼び出します。[`uvmalloc`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/vm.c#L218) は、`kalloc` で物理メモリを割り当て、割り当てられたメモリをゼロにし、`mappages` でユーザーページテーブルに PTE を追加します。

アプリケーションがメモリを遅延的に割り当てる場合、`sys_sbrk` はプロセスのサイズ (`myproc()->sz`) を `n` ずつ増分し、古いサイズを返します。物理メモリを割り当てたり、プロセスのページテーブルに PTE を追加したりしません。

プロセスが有効なページテーブルマッピングのない仮想アドレスにロードまたはストアすると、CPU は *ページフォールト例外* を発生させます。`usertrap` は、このケース [(trap.c:74)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c#L74) をチェックし、[`vmfault`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/vm.c#L459) を呼び出してページフォールトを処理します。

`vmfault` は、障害のあるアドレスが `sbrk` によって以前に許可された領域内にあることを確認し、`kalloc` で物理メモリのページを割り当て、割り当てられたページをゼロにし、`mappages` でユーザーページテーブルに PTE を追加します。xv6 は、新しいページの PTE に `PTE_W`、`PTE_R`、`PTE_U`、および `PTE_V` フラグを設定します。

その後、`usertrap` はフォールトの原因となった命令からプロセスを再開します。PTE が有効になっているため、再実行されたロードまたはストア命令はフォールトなしで実行されます。

アプリケーションが負の `n` を指定して `sbrk` を呼び出してメモリを解放する場合、`sys_sbrk` は `growproc` を呼び出し、は `uvmdealloc` を呼び出します。実際の作業は [`uvmunmap`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/vm.c#L194) によって行われ、`walk` を使用して PTE を検索します。

一部のページはプロセスによって使用されたことがなく、したがって `vmfault` によって割り当てられたこともないため、`uvmunmap` は `PTE_V` フラグなしで PTE をスキップします。PTE マッピングが有効な場合、`uvmunmap` は `kfree` を呼び出して、参照する物理メモリを解放します。

xv6 は、プロセスのページテーブルをハードウェアにユーザー仮想アドレスのマッピング方法を指示するためだけでなく、そのプロセスにどの物理メモリページが割り当てられているかを示す唯一の記録としても使用することに注意してください。これが、(`uvmunmap` で) ユーザーメモリを解放するときにユーザーページテーブルの検査が必要になる理由です。

## 現実世界: コピーオンライト (COW) フォーク

多くのカーネル (xv6 ではありません) は、ページフォルトを使用して *コピーオンライト (COW) フォーク* を実装します。`fork` システムコールは、フォーク時の初期内容が親のメモリと同じであるメモリを子が参照することを保証します。これを実装する 1 つの方法は、親のメモリ全体を、子に新しく割り当てられた物理メモリにコピーすることです。これが xv6 の機能です。

コピーは遅くなる可能性があるため、子が親の物理メモリを共有できればより効率的になります。ただし、これを直接実装すると、親と子が共有スタックとヒープへの書き込みによって互いの実行を中断することになるため、機能しません。

コピーオンライトフォークでは、ページテーブルのアクセス許可とページフォールトを適切に使用することで、親と子が物理メモリを安全に共有します。基本的な計画では、最初は親と子がすべての物理ページを共有しますが、それぞれが読み取り専用でマップします (`PTE_W` フラグはクリア)。その後、親と子は共有物理メモリから読み取ることができます。どちらかが共有ページに書き込むと、RISC-V CPU はページフォールト例外を発生させます。

COW をサポートするカーネルは、物理メモリの新しいページを割り当て、共有ページをその新しいページにコピーすることで応答します。次に、カーネルは、障害が発生したプロセスのページテーブル内の関連する PTE を変更して、コピーをポイントし、読み取りだけでなく書き込みも許可し、障害を引き起こした命令で障害が発生したプロセスを再開します。PTE で書き込みが許可されるようになったので、再実行されたストア命令はフォールトなしで実行され、共有ページではなくページのプライベートコピーが変更されます。

コピーオンライトでは、フォーク、ページフォールト、実行、および終了の履歴に応じて、各ページがさまざまな数のページテーブルによって参照される可能性があるため、物理ページをいつ解放できるかを決定するためにブックキーピングが必要です。このブックキーピングにより、重要な最適化が可能になります。プロセスでストアページフォールトが発生し、物理ページがそのプロセスのページテーブルからのみ参照される場合、コピーは必要ありません。

`fork` はメモリをコピーする必要がないため、コピーオンライトにより `fork` が高速になります。メモリの一部は後で書き込むときにコピーする必要がありますが、メモリの大部分はコピーする必要がないことがよくあります。一般的な例は、`fork` の後に `exec` が続く場合です。`fork` の後に数ページが書き込まれる可能性がありますが、その後、子の `exec` が親から継承したメモリの大部分を解放します。

コピーオンライト `fork` では、このメモリをコピーする必要がなくなります。さらに、COW フォークは透過的です。利点を得るためにアプリケーションを変更する必要はありません。

## 現実世界: デマンドページング

ページフォールトを悪用するもう 1 つの広く使用されている機能は、*デマンドページング* です。`exec` システムコールでは、xv6 はアプリケーションを開始する前に、アプリケーションのすべてのテキストとデータをメモリにロードします。アプリケーションは大きくなり、ディスクからの読み取りに時間がかかるため、この起動コストはユーザーにとって顕著になる可能性があります。

起動時間を短縮するために、最新のカーネルは最初に実行可能ファイルをメモリにロードせず、すべての PTE が無効とマークされたユーザーページテーブルを作成するだけです。カーネルはプログラムの実行を開始します。プログラムが初めてページを使用するたびにページフォールトが発生し、それに応答してカーネルはディスクからページのコンテンツを読み取り、それをユーザーアドレス空間にマップします。

COW フォークや遅延割り当てと同様に、カーネルはこの機能をアプリケーションに対して透過的に実装できます。

コンピュータ上で実行されるプログラムには、コンピュータに搭載されている RAM よりも多くのメモリが必要な場合があります。適切に対処するために、オペレーティングシステムは *ディスクへのページング* を実装する場合があります。このアイデアは、ユーザーページの一部のみを RAM に保存し、残りをディスク上の *ページング領域* に保存するというものです。カーネルは、ページング領域 (つまり RAM ではない) に格納されているメモリに対応する PTE を無効としてマークします。

アプリケーションがディスクに *ページアウト* されたページの 1 つを使用しようとすると、アプリケーションでページフォールトが発生し、そのページを *ページイン* する必要があります。カーネルトラップハンドラーは物理 RAM のページを割り当て、そのページをディスクから RAM に読み取り、RAM を指すように関連する PTE を変更します。

ページをページインする必要があるが、空き物理 RAM がない場合はどうなりますか?その場合、カーネルはまず物理ページをディスク上のページング領域にページアウトまたは「追い出し」、その物理ページを参照している PTE を無効としてマークすることによって物理ページを解放する必要があります。エビクションにはコストがかかるため、ページングが頻繁に行われない場合、つまりアプリケーションがメモリページのサブセットのみを使用し、サブセットの和集合が RAM に収まる場合に、ページングが最適に実行されます。

このプロパティは、参照の局所性が良好であるとよく言われます。多くの仮想メモリ技術と同様に、カーネルは通常、アプリケーションに対して透過的な方法でディスクへのページングを実装します。

多くの場合、コンピューターは、ハードウェアが提供する RAM の量に関係なく、「空き」物理メモリがほとんど、またはまったくない状態で動作します。たとえば、クラウドプロバイダーは、ハードウェアをコスト効率よく使用するために、多数の顧客を 1 台のマシンに多重化します。別の例として、ユーザーはスマートフォン上の少量の物理メモリで多くのアプリケーションを実行します。

このような設定では、ページを割り当てるには、最初に既存のページを削除する必要がある場合があります。したがって、空き物理メモリが不足している場合、割り当てにはコストがかかります。

遅延割り当てとデマンドページングは、空きメモリが不足しており、プログラムが割り当てられたメモリの一部のみを積極的に使用している場合に特に有利です。これらの手法により、ページが割り当てられたりロードされたりしたものの、一度も使用されなかったり、使用前に削除されたりした場合の無駄な作業を回避することもできます。

## 現実世界: メモリマップされたファイル

ページングとページフォールト例外を組み合わせる他の機能には、スタックと *メモリマップファイル* の自動拡張が含まれます。これらのファイルは、プログラムが `mmap` システムコールを使用してアドレス空間にマップするファイルで、プログラムがロード命令とストア命令を使用して読み書きできるようにします。

## 演習

1. `sbrk(1)` を呼び出して、アドレス空間を 1 バイトずつ拡張するユーザープログラムを作成します。プログラムを実行し、`sbrk` の呼び出し前と `sbrk` の呼び出し後のプログラムのページテーブルを調査します。カーネルにはどれくらいのスペースが割り当てられていますか?新しいメモリの PTE には何が含まれますか?

2. COW フォークを実装します。

3. `mmap`を実装します。

スケジュールとロックは、あるスレッドのアクションを別のスレッドから隠すのに役立ちますが、スレッドが意図的に対話できるようにする抽象化も必要です。たとえば、xv6 のパイプのリーダーは、書き込みプロセスがデータを生成するまで待機する必要がある場合があります。親による `wait` の呼び出しは、子が終了するまで待つ必要がある場合があります。また、ディスクを読み取るプロセスは、ディスク ハードウェアが読み取りを完了するまで待つ必要があります。 xv6 カーネルは、これらの状況 (およびその他の状況) でスリープおよびウェイクアップと呼ばれるメカニズムを使用します。スリープにより、カーネル スレッドは、何らかの *条件* が true になるまで待機できます。別のスレッドまたは割り込みハンドラーは、(通常はいくつかの変数を変更することによって) 条件を true にし、条件を待っているスレッドを再開する必要があることを示すために wakeup を呼び出すことができます。スリープとウェイクアップは、*シーケンス調整* または *条件付き同期* メカニズムと呼ばれることがよくあります。

先に進む前に、[`kernel/proc.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c) の関数 `sleep_prepare()`、`sleep()`、および `wakeup()`、およびファイル [`kernel/pipe.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c) のすべてをお読みください。

## 概要

スリープ/ウェイクアップ インターフェイスは次のようになります。

    void sleep_prepare(void *chan)
    void sleep()
    void wakeup(void *chan)

プロセスは条件が true になるのを待つためにスリープし、`chan` 引数 (*wait チャネル*) で目的の条件を指定します。 `sleep_prepare(chan)` は、指定された待機チャネルを待つためにプロセスがすぐにスリープする可能性があることを宣言します。それはすぐに戻ってきます。 `wakeup(chan)` は、`chan` で指定された条件が true になった (または true になった可能性がある) ときに呼び出されます。 `sleep_prepare(chan)` を呼び出した後、同じ `chan` で `sleep()` を呼び出したすべてのプロセスを起動します。 (必須の) 前回の `sleep_prepare(chan)` 呼び出しの後に `wakeup(chan)` がすでに呼び出されている場合、`sleep()` はすぐに戻ります。そうでない場合、`sleep()` は呼び出しプロセスを `SLEEPING` (`RUNNABLE` ではない) としてマークし、スケジューラーへのコンテキスト切り替えによって CPU を解放し、他のプロセスが実行できるようにします。 `sleep_prepare()` と `sleep()` は同じプロセスによって呼び出されます (通常は互いに数行以内)。 `wakeup()` は、別のプロセスまたは割り込みハンドラーによって呼び出されます。

これらの関数は、`chan` を不透明な 64 ビット値として扱います。彼らがそれを使って行う唯一のことは、等しいかどうかを比較することです。通常のパターンは、呼び出し元が便利なオブジェクトのアドレスを `chan` 引数として渡すことです。カーネル プログラマは、待機チャネル規則を選択し、同じ `chan` を相互作用する `sleep_prepare()` および `wakeup()` 呼び出しに渡す責任があります。

カーネル コードは、何らかの条件が true になるのを待つためにスリープします。たとえば、パイプ バッファーが現在空の場合、パイプから読み取るカーネル コードはスリープします。この場合の条件は、(別のプロセスがパイプに書き込むため) パイプ バッファーが空ではなくなることです。 `sleep_prepare()` と `sleep` は条件を確認する方法を知りません。呼び出し元のコードだけが知っています。通常のパターンは、スリープしている可能性のあるプロセスが最初に状態を保護するロックを取得することです。次に状態を確認します。そうでない場合は、`sleep_prepare()` を呼び出し、ロックを解放して、`sleep()` を呼び出します。後で条件を true にするコードは、`wakeup` を呼び出します。

以下は、xv6 カーネル パイプ コードがどのようにスリープするかを示すスケッチです。

    piperead(pipe){
      acquire(&pipe->lock);
      while(there's no data in pipe->buffer){
        sleep_prepare(&pipe);
        release(&pipe->lock);
        sleep();
        acquire(&pipe->lock);
      }
      remove the data from the pipe;
      release(&pipe->lock);
    }

    pipewrite(pipe){
      acquire(&pipe->lock);
      append data to pipe->buffer;
      wakeup(&pipe);
      release(&pipe->lock);
    }

このコードは、パイプ データ構造のアドレスを待機チャネルとして使用します。

`sleep_prepare(chan)` は、条件をチェックする前、または条件を保護するロックを解放する前に呼び出す必要があります。この呼び出しは、プロセスが指定された `chan` でスリープする必要がある可能性があるという事実を記録します。 `sleep_prepare(chan)` と `sleep()` の呼び出しの間に別のプロセス (または割り込み) が `wakeup(chan)` を呼び出すと、`wakeup()` はスリープしようとしているプロセスに、実際にはスリープすべきではないことを示すフラグを設定します。 `sleep()` がこのフラグを認識すると、スリープせずに戻ります。

`sleep_prepare(chan)`の理由は何ですか?パイプリーダーがバッファーが空であることを確認してから `sleep` を呼び出すまでの間に、条件が true になり、`wakeup()` が呼び出される可能性があります。何らかの賢さがなければ、`wakeup()` はスリープ プロセスを検出できず、何の効果もありません。その場合、パイプ バッファーに読み取るデータがあるにもかかわらず、プロセスは `sleep()` を呼び出します。そして、もし（そうかもしれないが）パイプライターがそれ以上何も書かなかった場合、リーダーは間違って永遠に眠ってしまう可能性がある。この望ましくない状況は、*ロストウェイクアップ*と呼ばれます。前の段落で説明した動作により、この問題は回避されます。

このパイプの例には、ほとんどのスリープ コードと同様に、条件を保護し、スリープに移行するプロセスが条件をチェックしてから `sleep_prepare()` を呼び出すまでの間に `wakeup()` が呼び出されないようにするロックがあります。このロックは、*条件ロック*と呼ばれることがよくあります。プロセスは、`sleep()` を呼び出す前にロックを解放し (他のプロセスまたは割り込みハンドラーが条件を変更して `wakeup()` を呼び出せるようにするため)、`sleep()` が戻った後にロックを再取得する必要があります。

## コード: スリープとウェイクアップ

Xv6 の [`sleep_prepare`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L548)、[`sleep`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L563)、および [`wakeup`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L577) は、上記の例で使用されるインターフェイスを実装しています。基本的な考え方は、`sleep` に現在のプロセスを `SLEEPING` としてマークさせてから、`sched` を呼び出して CPU を解放することです。 `wakeup` は、指定された待機チャネルでスリープしているプロセスを検索し、それらを `RUNNABLE` とマークします。

`sleep_prepare(chan)` は待機チャネルを `p->chan` に記録してリターンします。 `sleep()` が呼び出されたときに `p->chan` がまだゼロでない場合、`sleep()` は呼び出しプロセスを状態 `SLEEPING` に変更し、`sched()` を呼び出して他のプロセスを実行できるようにします。

`wakeup(chan)` は、`chan` で同時にスリープ状態になる可能性のある他のプロセスに関する 2 つの状況を処理します。他のプロセスが自身を `SLEEPING` としてマークするまでに達した場合、`wakeup` はその状態を認識し、`RUNNABLE` に変更します。その後、`sleep()` への呼び出しが返されます。他のプロセスが `sleep_prepare(chan)` の呼び出しまでに到達した場合 (ただし、その `sleep()` が `p->lock` の取得までには到達していない)、`wakeup(chan)` は `p->chan` が `chan` に等しいことを認識し、`wakeup` は `p->chan` をゼロに設定します。その場合、他のプロセスが `sleep` を呼び出すと、ゼロを確認してすぐに戻ります。重要なのは、別のプロセスが `sleep()` を呼び出そうとしているときに `wakeup()` が呼び出された場合にウェイクアップが失われないようにすることです。

`sleep_prepare()` の使用規則により、スリープ状態にあるプロセスがまだ `sleep_prepare()` を呼び出していない状況を心配する必要がなくなります。そのプロセスは、条件チェックと `sleep_prepare()` を、関連するチャネルに対する `wakeup()` の呼び出しを防止するロックで囲むか、条件をチェックする前に `sleep_prepare()` を呼び出す必要があります。

場合によっては、複数のプロセスが同じチャネル上でスリープしていることがあります。たとえば、パイプからの複数のプロセスの読み取りなどです。 `wakeup` に 1 回電話をかけると、全員が目を覚ますことができます。そのうちの 1 つが最初に実行され、(パイプの場合) パイプ ロックを取得し、待機しているデータを読み取ります。他のプロセスは、ウェイクアップされているにもかかわらず、読み取るデータがないことがわかります。彼らの観点からすると、その目覚めは「偽り」であり、彼らは再び眠らなければなりません。このため、上記の `piperead` のように、スリープは常に条件を再チェックするループ内で発生します。

スリープ/ウェイクアップを 2 回使用するときに誤って同じチャネルを選択しても害はありません。偽のウェイクアップが表示されますが、上記のようなループ処理によりこの問題は許容されます。スリープ/ウェイクアップの魅力の多くは、軽量である (待機チャネルとして機能する特別なデータ構造を作成する必要がない) ことと、間接層を提供する (呼び出し元がどの特定のプロセスと対話しているかを知る必要がない) ことです。

## コード: パイプ

xv6 のパイプは、プロデューサーとコンシューマーを同期するためにスリープするコードの例です。パイプのインターフェイスについては [1] (/book/chapter-1/#CH:UNIX) 章で説明しました。パイプの一端に書き込まれたバイトはカーネル内のバッファにコピーされ、パイプの他端から読み取ることができます。今後の章では、パイプ周辺のファイル記述子のサポートについて検討しますが、ここでは `pipewrite` と `piperead` の実装を見てみましょう。

各パイプは `struct pipe` で表され、`lock` バッファーと `data` バッファーが含まれます。フィールド `nread` および `nwrite` は、バッファーから読み取られた、およびバッファーに書き込まれた合計バイト数をカウントします。バッファはラップアラウンドします。`buf[PIPESIZE-1]` の後に書き込まれる次のバイトは `buf[0]` です。カウントはラップしません。この規則により、実装では完全なバッファー (`nwrite` `==` `nread+PIPESIZE`) と空のバッファー (`nwrite` `==` `nread`) を区別できますが、バッファーへのインデックス作成には `buf[nread]` だけではなく `buf[nread` `%` `PIPESIZE]` を使用する必要があることを意味します (同様に、 `nwrite`）。

`piperead` と `pipewrite` への呼び出しが 2 つの異なる CPU で同時に発生すると仮定します。 [`pipewrite`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L77) は、カウント、データ、およびそれらに関連する不変式を保護するパイプのロックを取得することから始まります。 [`piperead`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L112) もロックを取得しようとしますが、取得できません。 [`acquire`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.c#L22)でロック待ちで回転します。 `piperead` が待機している間、`pipewrite` は書き込まれているバイト (`addr[0..n-1]`) をループし、各バイトを順番にパイプに追加します [(pipe.c:101)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L101)。このループ中に、バッファーが [(pipe.c:88)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L88) でいっぱいになる可能性があります。この場合、`pipewrite` は `wakeup` を呼び出して、スリープ中のリーダーにバッファ内で待機中のデータがあることを警告し、ロックを解放し、チャネル `&pi->nwrite` でスリープして、リーダーがバッファからいくつかのバイトを取得するのを待ちます。

`piperead` はパイプのロックを取得し、クリティカル セクションに入ります。 `pi->nread` `!=` [`pi->nwrite`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L119) (`pi->nwrite` `==` `pi->nread` `+` のため、`pipewrite` はスリープ状態になりました) ことがわかります。 [`PIPESIZE`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L88)) なので、`for` ループに移行し、パイプ [(pipe.c:129)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L129) からデータをコピーし、コピーされたバイト数だけ `nread` を増分します。バッファ内のそれだけのスペースが書き込みに利用できるようになったので、`piperead` は [`wakeup`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L140) を呼び出して、復帰する前にスリープ中のライターをウェイクアップします。 `wakeup` は、`&pi->nwrite` でスリープしているプロセス (`pipewrite` を実行していたが、バッファがいっぱいになったときに停止したプロセス) を見つけます。 `wakeup` は、そのプロセスを `RUNNABLE` としてマークします。

パイプ コードは、リーダーとライター (`&pi->nread` および `&pi->nwrite`) に個別の待機チャネルを使用します。これにより、同じパイプを待機しているリーダーとライターが多数存在する場合に、システムの効率が向上する可能性があります。パイプ コードは、スリープ状態をチェックするループ内でスリープします。複数のリーダーまたはライターがある場合、最初に起動するプロセスを除くすべてのプロセスが条件が false であると判断し、再びスリープします。

## コード: 待機、終了、強制終了

[`kernel/proc.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c) の関数 `kwait()`、`kexit()`、および `kkill()` のコードを読んでください。これらは、対応するシステム コールの内部実装です。

[1]章(/book/chapter-1/#CH:UNIX)で紹介されている睡眠の興味深い例は、子の `exit` とその親の `wait` の間の相互作用です。子供の死亡時に、親はすでに `wait` で眠っているか、他のことをしている可能性があります。後者の場合、その後の `wait` の呼び出しでは、おそらく `exit` を呼び出してからずっと後、子の死亡を観察する必要があります。 `wait` がそれを観察するまで xv6 が子の終了を記録する方法は、`exit` が呼び出し元を `ZOMBIE` 状態にし、親の `wait` がそれに気づくまでその状態を維持し、子の状態を `UNUSED` に変更し、子の終了ステータスをコピーし、子のプロセス ID を親に返すことです。親が子より先に終了した場合、親は子を `init` プロセスに渡し、`wait` を永続的に呼び出します。したがって、すべての子供には親が後片付けをしなければなりません。課題は、同時の親 `wait` と子 `exit`、および同時の `exit` と `exit` の間の競合とデッドロックを回避することです。

`wait` のカーネル実装である `kwait` は、[`wait_lock`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L370) を取得することから始まります。これは、`kwait` が既存の子から `wakeup` を見逃さないようにする条件ロックとして機能します。次に、`kwait` はプロセス テーブルをスキャンします。 `ZOMBIE` 状態の子を見つけると、その子のリソースとその `proc` 構造体を解放し、子の終了ステータスを `wait` に指定されたアドレス (0 でない場合) にコピーし、子のプロセス ID を返します。 `kwait` が子を見つけても、どれも終了していない場合は、いずれかの子が終了するまでスリープして待機し [(proc.c:414)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L414)、再度スキャンします。 `kwait` は、多くの場合、`wait_lock` と一部のプロセスの `pp->lock` という 2 つのロックを保持します。デッドロックを回避する順序は、最初に `wait_lock`、次に `pp->lock` です。

[`kexit`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L326) は、終了ステータスを記録し、一部のリソースを解放し、`reparent` を呼び出して子を `init` プロセスに渡し、親が `wait` にある場合に備えて起動し、呼び出し元をゾンビとしてマークし、CPU を永続的に譲ります。 `kexit` は、このシーケンス中に `wait_lock` と `p->lock` の両方を保持します。これは `wakeup(p->parent)` の条件ロックであり、`wait` の親がウェイクアップを失うのを防ぐため、`wait_lock` を保持します。 `kexit` は、子が最終的に `swtch` を呼び出す前に、`wait` の親が子が `ZOMBIE` 状態にあることを認識しないように、このシーケンスでも `p->lock` を保持する必要があります。 `kexit` は、デッドロックを回避するために、`kwait` と同じ順序でこれらのロックを取得します。

`kexit` が状態を `ZOMBIE` に設定する前に親をウェイクアップするのは正しくないように見えるかもしれませんが、安全です。`wakeup` によって親が実行される可能性がありますが、親の `kwait` のループは子の `p->lock` が `scheduler` によって解放されるまで子を検査できないため、`kwait` は `kexit` が終了するまで終了プロセスを確認できません。は状態を [`ZOMBIE`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L358) に設定しました。

`exit` ではプロセス自体を終了できますが、`kill` システム コール [(proc.c:602)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L602) を使用すると、あるプロセスが別のプロセスの終了を要求できます。 `kill` が被害者のプロセスを直接破壊するのは複雑すぎます。これは、おそらくカーネル データ構造に対する機密性の高い更新シーケンスの途中で被害者が別の CPU で実行されている可能性があるためです。したがって、`kkill` はほとんど何もしません。被害者の `p->killed` を設定し、スリープしている場合はウェイクアップするだけです。最終的に、被害者はカーネルに出入りすることになり、その時点で、`p->killed` が設定されている場合、`usertrap` 内のコードは `kexit` を呼び出します ([`killed`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L631) を呼び出してチェックします)。被害者がユーザー空間で実行されている場合、システムコールを行うことによって、またはタイマー (または他のデバイス) が割り込みを行うことによって、次回カーネルに入ったときに被害者が強制終了されたことがわかります。

被害者のプロセスがスリープしている場合、`kkill` はその状態を `RUNNABLE` に設定し、被害者が `sleep` から戻るようにします。待機中の条件が true ではない可能性があるため、これは潜在的に危険です。ただし、`sleep` への xv6 呼び出しは常に、`sleep` が返された後に条件を再テストする `while` ループ内にラップされます。 `sleep` への一部の呼び出しでは、ループ内で `p->killed` もテストし、設定されている場合は現在のアクティビティを放棄します。これは、そのような放棄が正しい場合にのみ行われます。たとえば、パイプ読み取りおよび書き込みコード [(pipe.c:84)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L84) は、killed フラグが設定されている場合に戻ります。最終的にコードはトラップに戻り、再び `p->killed` をチェックして終了します。

一部の xv6 `sleep` ループは `p->killed` をチェックしません。これは、コードがアトミックである必要があるマルチステップ システム コールの途中にあるためです (つまり、途中で放棄された場合は正しくありません)。 virtio ドライバー [(virtio_disk.c:287)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/virtio_disk.c#L287) はその例です。ディスク操作は、ファイル システムを正しい状態に保つために必要な一連の書き込みの 1 つである可能性があるため、`p->killed` はチェックされません。ディスク I/O の待機中に強制終了されたプロセスは、現在のシステム コールが完了し、`usertrap` が強制終了フラグを確認するまで終了しません。

## プロセスのロック

各プロセスに関連付けられたロック (`p->lock`) は、xv6 で最も複雑なロックです。 `p->lock` について簡単に考えると、`struct proc` フィールド (`p->state`、`p->chan`、`p->killed`、`p->xstate`、および `p->pid`) のいずれかの読み取りまたは書き込み中に  を保持する必要があるということです。これらのフィールドは他のプロセスや他の CPU 上のスケジューラ スレッドによって使用される可能性があるため、ロックによって保護する必要があるのは当然です。

ただし、`p->lock` のほとんどの使用法は、xv6 のプロセス データ構造とアルゴリズムの高レベルの不変条件を保護しています。 `p->lock` が行うことの完全なセットは次のとおりです。

- `p->state` とともに、新しいプロセスに `proc[]` スロットを割り当てる際の競合を防ぎます。

- プロセスの作成中または破棄中にプロセスが表示されないようにします。

- 親の `wait` が、状態を `ZOMBIE` に設定しているがまだ CPU を解放していないプロセスを収集するのを防ぎます。

- 別の CPU のスケジューラが、状態を `RUNNABLE` に設定した後、`swtch` を終了する前に、譲歩プロセスの実行を決定することを防ぎます。

- 1 つの CPU のスケジューラだけが `RUNNABLE` プロセスの実行を決定するようにします。

- `swtch` にあるときに、タイマー割り込みによってプロセスが放棄されるのを防ぎます。

- `sleep`と`wakeup`の間の競合を防ぎます。

- `kill` の被害プロセスが終了し、`kkill` による `p->pid` のチェックと `p->killed` の設定の間に再割り当てされることを防ぎます。

- `kkill` のチェックと `p->state` の書き込みをアトミックにします。

`p->parent` フィールドは、`p->lock` ではなくグローバル ロック `wait_lock` によって保護されています。 `p->parent` を変更するのはプロセスの親のみですが、フィールドはプロセス自体と、子を検索する他のプロセスの両方によって読み取られます。 `wait_lock` の目的は、`wait` が子が終了するのを待ってスリープしているときに条件ロックとして機能することです。終了する子は、状態を `ZOMBIE` に設定し、親を起動して CPU を解放するまで、`wait_lock` または `p->lock` のいずれかを保持します。また、`wait_lock` は、親と子によって同時に実行される `exit` をシリアル化するため、`init` プロセス (子を継承する) は `wait` からウェイクアップされることが保証されます。 `wait_lock` は、各親のプロセスごとのロックではなくグローバル ロックです。これは、プロセスがそれを取得するまで、その親が誰であるかを知ることができないためです。

## 現実世界

`sleep` と `wakeup` はシンプルで効果的な同期方法ですが、他にもたくさんあります。セマフォ (Dijkstra 1965) はその一例です。それらすべての最初の課題は、この章の冒頭で見た「ウェイクアップの喪失」問題を回避することです。オリジナルの Unix カーネルの `sleep` は単純に割り込みを無効にしていましたが、Unix は単一 CPU システムで実行されていたため、これで十分でした。プラン 9 の `sleep` は、スリープに入る直前にスケジュール ロックを保持した状態で実行されるコールバック関数を使用します。この機能は、ウェイクアップの失敗を避けるために、睡眠状態を直前にチェックする役割を果たします。 Linux カーネルの `sleep` は、待機チャネルの代わりに、待機キューと呼ばれる明示的なプロセス キューを使用します。キューには独自の内部ロックがあります。

`wakeup` のプロセスのセット全体をスキャンするのは非効率的です。より良い解決策は、`sleep` と `wakeup` の両方の `chan` を、その構造上でスリープしているプロセスのリストを保持するデータ構造 (Linux の待機キューなど) に置き換えることです。プラン 9 の `sleep` および `wakeup` は、その構造をランデブー ポイントと呼びます。多くのスレッド ライブラリは、同じ構造を条件変数として参照します。この文脈では、操作 `sleep` および `wakeup` は `wait` および `signal` と呼ばれます。これらのメカニズムはすべて同じ特徴を共有しています。つまり、スリープ状態は、スリープ中にアトミックにドロップされるある種のロックによって保護されます。

xv6 の `wakeup` は、特定の待機チャネルで待機しているすべてのプロセスを起動します。それらが複数ある場合、それらはすべて条件ロックを取得して条件を再チェックしようとします。多くの場合、役に立つこと (パイプ内で待機しているすべてのデータを読み取るなど) を実行できるのは 1 つだけです。残りの人は、その状態がもはや当てはまらないことに気づき、眠りに戻ります。彼らを目覚めさせるのは CPU 時間の無駄でした。その結果、ほとんどの条件変数設計では、条件変数を待機しているプロセスの 1 つをウェイクアップする `signal` と、すべてのプロセスをウェイクアップする `broadcast` という 2 つのプリミティブが提供されます。

プロセスを強制的に強制終了すると、いくつかの問題が発生します。たとえば、強制終了されたプロセスはカーネルの奥深くでスリープしている可能性があり、コール スタック上の各関数が何らかのクリーンアップを行う必要がある場合があるため、そのスタックを巻き戻すには注意が必要です。一部の言語では例外メカニズムを提供することで役に立ちますが、C ではそうではありません。さらに、待機しているイベントがまだ発生していない場合でも、スリープ状態のプロセスを目覚めさせる可能性のあるイベントが他にもあります。たとえば、Unix プロセスがスリープしているときに、別のプロセスが `signal` を送信する可能性があります。この場合、プロセスは、値 -1 およびエラー コードが EINTR に設定された状態で、中断されたシステム コールから戻ります。アプリケーションはこれらの値を確認し、何をすべきかを決定できます。 Xv6 はシグナルをサポートしていないため、このような複雑さは発生しません。

Xv6 の `kill` サポートは完全に満足のいくものではありません。おそらく `p->killed` をチェックする必要があるスリープ ループがあります。関連する問題は、`p->killed` をチェックする `sleep` ループの場合でも、`sleep` と `kill` の間に競合が存在することです。後者は、`p->killed` を設定し、被害者のループが `p->killed` をチェックした直後、`sleep` を呼び出す前に被害者をウェイクアップしようとする可能性があります。この問題が発生した場合、被害者は、待っている状態が発生するまで `p->killed` に気づきません。これは、かなり後になるか、まったく行われない場合もあります (たとえば、被害者がコンソールからの入力を待っているが、ユーザーが何も入力しない場合)。

## 演習

1. xv6 でカウント セマフォを実装します。 xv6 のスリープとウェイクアップの用途をいくつか選択し、それらをセマフォに置き換えます。結果を判断してください。

2. `sleep()` への呼び出し (おそらく追加の引数付き) だけを必要とし、`sleep_prepare()` への呼び出しのようなものを必要としないスリープ/ウェイクアップ スキームを実装できますか?

3. `kill` と `sleep` の間の上記の競合を修正し、被害者のスリープ ループが `p->killed` をチェックした後、`sleep` を呼び出す前に発生する `kill` により、被害者が現在のシステム コールを放棄することになります。

4. すべてのスリープ ループが `p->killed` をチェックするように計画を設計します。これにより、たとえば、virtio ドライバー内のプロセスが別のプロセスによって強制終了された場合に、while ループからすぐに戻ることができます。

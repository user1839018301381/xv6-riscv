スケジューリングとロックは、あるスレッドの動作が別のスレッドへ不用意に影響するのを防ぎます。一方で、スレッド同士を意図的に連携させる仕組みも必要です。

たとえば、パイプから読み取るプロセスは、書き込み側がデータを生成するまで待つことがあります。`wait` を呼び出した親プロセスは、子プロセスが終了するまで待ちます。ディスクを読み取るプロセスも、ディスクハードウェアが読み取りを終えるまで待たなければなりません。xv6 カーネルは、このような場面でスリープとウェイクアップを使います。

スリープを使うと、カーネルスレッドは何らかの *条件* が成立するまで待機できます。別のスレッドや割り込みハンドラは、通常は変数を更新することで条件を成立させ、`wakeup` を呼び出して待機中のスレッドを再開させます。このため、スリープとウェイクアップは *順序調整* または *条件同期* の仕組みと呼ばれます。

先へ進む前に、[`kernel/proc.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c) の `sleep_prepare()`、`sleep()`、`wakeup()` と、[`kernel/pipe.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c) 全体を読んでください。

## 概要

スリープ/ウェイクアップインターフェースは次のようになります。

    void sleep_prepare(void *chan)
    void sleep()
    void wakeup(void *chan)

プロセスは、条件が成立するまで待つためにスリープします。`chan` 引数（*待機チャネル*）は、その条件を識別する値です。`sleep_prepare(chan)` は、プロセスがまもなく指定の待機チャネルでスリープする可能性を記録し、すぐに戻ります。`wakeup(chan)` は、`chan` が表す条件が成立したか、成立した可能性があるときに呼び出します。

`wakeup(chan)` は、同じ `chan` に対して `sleep_prepare(chan)` と `sleep()` を呼び出したすべてのプロセスを起こします。直前の `sleep_prepare(chan)` より後に `wakeup(chan)` が呼ばれていれば、`sleep()` はすぐに戻ります。まだ呼ばれていなければ、`sleep()` は呼び出し元を `SLEEPING`（`RUNNABLE` ではない）に変更し、スケジューラへコンテキストスイッチして CPU を譲ります。

これで別のプロセスを実行できます。

`sleep_prepare()` と `sleep()` は同じプロセスによって呼び出されます (通常は互いに数行以内)。`wakeup()` は、別のプロセスまたは割り込みハンドラーによって呼び出されます。

これらの関数は `chan` を中身の分からない 64 ビット値として扱い、値が等しいかどうかだけを比較します。通常、呼び出し元は関連するオブジェクトのアドレスを `chan` に渡します。どのアドレスを待機チャネルに使うかを決め、対応する `sleep_prepare()` と `wakeup()` に同じ `chan` を渡すのは、カーネルプログラマの責任です。

カーネルコードは、何らかの条件が true になるのを待つためにスリープします。たとえば、パイプバッファが現在空の場合、パイプから読み取るカーネルコードはスリープします。この場合の条件は、(別のプロセスがパイプに書き込むため) パイプバッファが空ではなくなることです。`sleep_prepare()` と `sleep` は条件を確認する方法を知りません。呼び出し元のコードだけが知っています。

通常は、スリープする可能性のあるプロセスが、まず条件を保護するロックを取得します。次に条件を確認し、成立していなければ `sleep_prepare()` を呼び、ロックを解放してから `sleep()` を呼び出します。後で条件を成立させるコードは `wakeup` を呼び出します。

以下は、xv6 カーネルパイプコードがどのようにスリープするかを示すスケッチです。

    piperead(pipe){
      acquire(&pipe->lock);
      while(there's no data in pipe->buffer){
        sleep_prepare(&pipe);
        release(&pipe->lock);
        sleep();
        acquire(&pipe->lock);
      }
      remove the data from the pipe;
      release(&pipe->lock);
    }

    pipewrite(pipe){
      acquire(&pipe->lock);
      append data to pipe->buffer;
      wakeup(&pipe);
      release(&pipe->lock);
    }

このコードは、パイプデータ構造のアドレスを待機チャネルとして使用します。

`sleep_prepare(chan)` は、条件をチェックする前、または条件を保護するロックを解放する前に呼び出す必要があります。この呼び出しは、プロセスが指定された `chan` でスリープする必要がある可能性があるという事実を記録します。`sleep_prepare(chan)` と `sleep()` の呼び出しの間に別のプロセス (または割り込み) が `wakeup(chan)` を呼び出すと、`wakeup()` はスリープしようとしているプロセスに、実際にはスリープすべきではないことを示すフラグを設定します。

`sleep()` がこのフラグを認識すると、スリープせずに戻ります。

なぜ `sleep_prepare(chan)` が必要なのでしょうか。パイプの読み取り側がバッファの空を確認してから `sleep` を呼ぶまでの間に、条件が成立して `wakeup()` が呼ばれる可能性があるからです。対策がなければ、この時点ではまだスリープ中のプロセスが存在しないため、`wakeup()` は何も起こしません。その後、読み取れるデータがすでにあるにもかかわらず、読み取り側は `sleep()` を呼び出してしまいます。

書き込み側がその後データを書かなければ、読み取り側は誤って永久にスリープし続けます。この状態を *ロストウェイクアップ* と呼びます。前段で説明した仕組みは、この問題を防ぎます。

このパイプの例には、ほとんどのスリープコードと同様に、条件を保護し、スリープに移行するプロセスが条件をチェックしてから `sleep_prepare()` を呼び出すまでの間に `wakeup()` が呼び出されないようにするロックがあります。このロックは、*条件ロック*と呼ばれることがよくあります。プロセスは、`sleep()` を呼び出す前にロックを解放し (他のプロセスまたは割り込みハンドラーが条件を変更して `wakeup()` を呼び出せるようにするため)、`sleep()` が戻った後にロックを再取得する必要があります。

## コード: スリープとウェイクアップ

xv6 の [`sleep_prepare`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L548)、[`sleep`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L563)、および [`wakeup`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L577) は、上記の例で使用されるインターフェースを実装しています。基本的な考え方は、`sleep` に現在のプロセスを `SLEEPING` としてマークさせてから、`sched` を呼び出して CPU を解放することです。`wakeup` は、指定された待機チャネルでスリープしているプロセスを検索し、それらを `RUNNABLE` とマークします。

`sleep_prepare(chan)` は待機チャネルを `p->chan` に記録してリターンします。`sleep()` が呼び出されたときに `p->chan` がまだゼロでない場合、`sleep()` は呼び出しプロセスを状態 `SLEEPING` に変更し、`sched()` を呼び出して他のプロセスを実行できるようにします。

`wakeup(chan)` は、`chan` で同時にスリープ状態になる可能性のある他のプロセスに関する 2 つの状況を処理します。他のプロセスが自身を `SLEEPING` としてマークするまでに達した場合、`wakeup` はその状態を認識し、`RUNNABLE` に変更します。その後、`sleep()` への呼び出しが返されます。他のプロセスが `sleep_prepare(chan)` の呼び出しまでに到達した場合 (ただし、その `sleep()` が `p->lock` の取得までには到達していない)、`wakeup(chan)` は `p->chan` が `chan` に等しいことを認識し、`wakeup` は `p->chan` をゼロに設定します。

その場合、他のプロセスが `sleep` を呼び出すと、ゼロを確認してすぐに戻ります。重要なのは、別のプロセスが `sleep()` を呼び出そうとしているときに `wakeup()` が呼び出された場合にウェイクアップが失われないようにすることです。

`sleep_prepare()` の使用規則により、スリープ状態にあるプロセスがまだ `sleep_prepare()` を呼び出していない状況を心配する必要がなくなります。そのプロセスは、条件チェックと `sleep_prepare()` を、関連するチャネルに対する `wakeup()` の呼び出しを防止するロックで囲むか、条件をチェックする前に `sleep_prepare()` を呼び出す必要があります。

複数のプロセスが同じチャネルでスリープすることもあります。たとえば、複数のプロセスが同じパイプから読み取る場合です。`wakeup` を1回呼ぶと全プロセスが起きます。最初に実行されたプロセスがパイプのロックを取得し、待機中のデータを読み取ります。ほかのプロセスが実行される時点では、読み取れるデータがもう残っていないことがあります。

それらのプロセスにとっては「見せかけのウェイクアップ」であり、再びスリープしなければなりません。このため `piperead` のように、スリープは必ず条件を再確認するループ内で行います。

スリープ/ウェイクアップを 2 回使用するときに誤って同じチャネルを選択しても害はありません。偽のウェイクアップが表示されますが、上記のようなループ処理によりこの問題は許容されます。スリープ/ウェイクアップの魅力の多くは、軽量である (待機チャネルとして機能する特別なデータ構造を作成する必要がない) ことと、間接層を提供する (呼び出し元がどの特定のプロセスと対話しているかを知る必要がない) ことです。

## コード: パイプ

xv6 のパイプは、プロデューサーとコンシューマーを同期するためにスリープするコードの例です。パイプのインターフェースについては [1](/book/chapter-1/#CH:UNIX) 章で説明しました。パイプの一端に書き込まれたバイトはカーネル内のバッファにコピーされ、パイプの他端から読み取ることができます。今後の章では、パイプ周辺のファイル記述子のサポートについて検討しますが、ここでは `pipewrite` と `piperead` の実装を見てみましょう。

各パイプは `struct pipe` で表され、`lock` と `data` バッファを持ちます。`nread` と `nwrite` は、それぞれバッファから読み取った総バイト数と、バッファへ書き込んだ総バイト数です。バッファは循環して使います。`buf[PIPESIZE-1]` の次に書く位置は `buf[0]` です。

カウンタ自体は循環しません。この規則により、満杯のバッファ（`nwrite == nread + PIPESIZE`）と空のバッファ（`nwrite == nread`）を区別できます。一方、実際の配列位置を求めるときは `buf[nread]` ではなく `buf[nread % PIPESIZE]` を使います。`nwrite` も同様です。

`piperead` と `pipewrite` への呼び出しが 2 つの異なる CPU で同時に発生すると仮定します。[`pipewrite`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L77) は、カウント、データ、およびそれらに関連する不変式を保護するパイプのロックを取得することから始まります。

[`piperead`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L112) もロックを取得しようとしますが、取得できません。[`acquire`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/spinlock.c#L22)でロック待ちで回転します。

`piperead` が待機している間、`pipewrite` は書き込まれているバイト (`addr[0..n-1]`) をループし、各バイトを順番にパイプに追加します [(pipe.c:101)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L101)。このループ中に、バッファが [(pipe.c:88)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L88) でいっぱいになる可能性があります。

この場合、`pipewrite` は `wakeup` を呼び出して、スリープ中のリーダーにバッファ内で待機中のデータがあることを警告し、ロックを解放し、チャネル `&pi->nwrite` でスリープして、リーダーがバッファからいくつかのバイトを取得するのを待ちます。

`piperead` はパイプのロックを取得し、クリティカルセクションに入ります。`pi->nread` `!=` [`pi->nwrite`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L119) (`pi->nwrite` `==` `pi->nread` `+` のため、`pipewrite` はスリープ状態になりました) ことがわかります。

[`PIPESIZE`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L88)) なので、`for` ループに移行し、パイプ [(pipe.c:129)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L129) からデータをコピーし、コピーされたバイト数だけ `nread` を増分します。

バッファ内のそれだけのスペースが書き込みに利用できるようになったので、`piperead` は [`wakeup`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L140) を呼び出して、復帰する前にスリープ中のライターをウェイクアップします。`wakeup` は、`&pi->nwrite` でスリープしているプロセス (`pipewrite` を実行していたが、バッファがいっぱいになったときに停止したプロセス) を見つけます。

`wakeup` は、そのプロセスを `RUNNABLE` としてマークします。

パイプコードは、リーダーとライター (`&pi->nread` および `&pi->nwrite`) に個別の待機チャネルを使用します。これにより、同じパイプを待機しているリーダーとライターが多数存在する場合に、システムの効率が向上する可能性があります。パイプコードは、スリープ状態をチェックするループ内でスリープします。複数のリーダーまたはライターがある場合、最初に起動するプロセスを除くすべてのプロセスが条件が false であると判断し、再びスリープします。

## コード: 待機、終了、強制終了

[`kernel/proc.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c) の関数 `kwait()`、`kexit()`、および `kkill()` のコードを読んでください。これらは、対応するシステムコールの内部実装です。

第[1章](/book/chapter-1/#CH:UNIX)で触れたスリープの例に、子プロセスの `exit` と親プロセスの `wait` の連携があります。子プロセスが終了した時点で、親はすでに `wait` でスリープしているかもしれませんし、別の処理をしているかもしれません。後者の場合、親がかなり後になって `wait` を呼んでも、子の終了を確認できなければなりません。

`wait` がそれを観察するまで xv6 が子の終了を記録する方法は、`exit` が呼び出し元を `ZOMBIE` 状態にし、親の `wait` がそれに気づくまでその状態を維持し、子の状態を `UNUSED` に変更し、子の終了ステータスをコピーし、子のプロセス ID を親に返すことです。親が子より先に終了した場合、親は子を `init` プロセスに渡し、`wait` を永続的に呼び出します。

この仕組みにより、すべての子プロセスを親が後始末できます。ここでの課題は、親の `wait` と子の `exit` が同時に動く場合、および親子が同時に `exit` する場合に、競合とデッドロックを避けることです。

`wait` のカーネル実装である `kwait` は、[`wait_lock`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L370) を取得することから始まります。これは、`kwait` が既存の子から `wakeup` を見逃さないようにする条件ロックとして機能します。

次に、`kwait` はプロセステーブルをスキャンします。`ZOMBIE` 状態の子を見つけると、その子のリソースとその `proc` 構造体を解放し、子の終了ステータスを `wait` に指定されたアドレス (0 でない場合) にコピーし、子のプロセス ID を返します。`kwait` が子を見つけても、どれも終了していない場合は、いずれかの子が終了するまでスリープして待機し [(proc.c:414)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L414)、再度スキャンします。

`kwait` は、多くの場合、`wait_lock` と一部のプロセスの `pp->lock` という 2 つのロックを保持します。デッドロックを回避する順序は、最初に `wait_lock`、次に `pp->lock` です。

[`kexit`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L326) は、終了ステータスを記録し、一部のリソースを解放し、`reparent` を呼び出して子を `init` プロセスに渡し、親が `wait` にある場合に備えて起動し、呼び出し元をゾンビとしてマークし、CPU を永続的に譲ります。

`kexit` は、このシーケンス中に `wait_lock` と `p->lock` の両方を保持します。これは `wakeup(p->parent)` の条件ロックであり、`wait` の親がウェイクアップを失うのを防ぐため、`wait_lock` を保持します。`kexit` は、子が最終的に `swtch` を呼び出す前に、`wait` の親が子が `ZOMBIE` 状態にあることを認識しないように、このシーケンスでも `p->lock` を保持する必要があります。

`kexit` は、デッドロックを回避するために、`kwait` と同じ順序でこれらのロックを取得します。

`kexit` が状態を `ZOMBIE` に設定する前に親をウェイクアップするのは正しくないように見えるかもしれませんが、安全です。`wakeup` によって親が実行される可能性がありますが、親の `kwait` のループは子の `p->lock` が `scheduler` によって解放されるまで子を検査できないため、`kwait` は `kexit` が終了するまで終了プロセスを確認できません。は状態を [`ZOMBIE`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L358) に設定しました。

`exit` ではプロセス自体を終了できますが、`kill` システムコール [(proc.c:602)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L602) を使用すると、あるプロセスが別のプロセスの終了を要求できます。`kill` が被害者のプロセスを直接破壊するのは複雑すぎます。

これは、おそらくカーネルデータ構造に対する整合性が重要な更新処理の途中で被害者が別の CPU で実行されている可能性があるためです。したがって、`kkill` はほとんど何もしません。被害者の `p->killed` を設定し、スリープしている場合はウェイクアップするだけです。最終的に、被害者はカーネルに出入りすることになり、その時点で、`p->killed` が設定されている場合、`usertrap` 内のコードは `kexit` を呼び出します ([`killed`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L631) を呼び出してチェックします)。

被害者がユーザー空間で実行されている場合、システムコールを行うことによって、またはタイマー (または他のデバイス) が割り込みを行うことによって、次回カーネルに入ったときに被害者が強制終了されたことがわかります。

被害者のプロセスがスリープしている場合、`kkill` はその状態を `RUNNABLE` に設定し、被害者が `sleep` から戻るようにします。待機中の条件が true ではない可能性があるため、これは潜在的に危険です。ただし、`sleep` への xv6 呼び出しは常に、`sleep` が返された後に条件を再テストする `while` ループ内にラップされます。

`sleep` への一部の呼び出しでは、ループ内で `p->killed` もテストし、設定されている場合は現在のアクティビティを放棄します。これは、そのような放棄が正しい場合にのみ行われます。たとえば、パイプ読み取りおよび書き込みコード [(pipe.c:84)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/pipe.c#L84) は、killed フラグが設定されている場合に戻ります。

最終的にコードはトラップに戻り、再び `p->killed` をチェックして終了します。

一部の xv6 `sleep` ループは `p->killed` をチェックしません。これは、コードがアトミックである必要があるマルチステップシステムコールの途中にあるためです (つまり、途中で放棄された場合は正しくありません)。virtio ドライバー [(virtio_disk.c:287)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/virtio_disk.c#L287) はその例です。

ディスク操作は、ファイルシステムを正しい状態に保つために必要な一連の書き込みの 1 つである可能性があるため、`p->killed` はチェックされません。ディスク I/O の待機中に強制終了されたプロセスは、現在のシステムコールが完了し、`usertrap` が強制終了フラグを確認するまで終了しません。

## プロセスのロック

各プロセスに対応する `p->lock` は、xv6 で最も複雑なロックです。単純に考えるなら、`struct proc` の `p->state`、`p->chan`、`p->killed`、`p->xstate`、`p->pid` を読み書きするときは、`p->lock` を保持する必要があります。これらのフィールドは、ほかのプロセスや別の CPU 上のスケジューラスレッドも使うためです。

ただし、`p->lock` のほとんどの使用法は、xv6 のプロセスデータ構造とアルゴリズムの高レベルの不変条件を保護しています。`p->lock` が行うことの完全なセットは次のとおりです。

- `p->state` とともに、新しいプロセスに `proc[]` スロットを割り当てる際の競合を防ぎます。

- プロセスの作成中または破棄中にプロセスが表示されないようにします。

- 親の `wait` が、状態を `ZOMBIE` に設定しているがまだ CPU を解放していないプロセスを収集するのを防ぎます。

- プロセスが状態を `RUNNABLE` に設定してから `swtch` を終えるまでの間に、別の CPU のスケジューラがそのプロセスを実行するのを防ぎます。

- 1 つの CPU のスケジューラだけが `RUNNABLE` プロセスの実行を決定するようにします。

- `swtch` にあるときに、タイマー割り込みによってプロセスが放棄されるのを防ぎます。

- `sleep`と`wakeup`の間の競合を防ぎます。

- `kill` の被害プロセスが終了し、`kkill` による `p->pid` のチェックと `p->killed` の設定の間に再割り当てされることを防ぎます。

- `kkill` のチェックと `p->state` の書き込みをアトミックにします。

`p->parent` フィールドは、`p->lock` ではなくグローバルロック `wait_lock` によって保護されています。`p->parent` を変更するのはプロセスの親のみですが、フィールドはプロセス自体と、子を検索する他のプロセスの両方によって読み取られます。`wait_lock` の目的は、`wait` が子が終了するのを待ってスリープしているときに条件ロックとして機能することです。

終了する子は、状態を `ZOMBIE` に設定し、親を起動して CPU を解放するまで、`wait_lock` または `p->lock` のいずれかを保持します。また、`wait_lock` は、親と子によって同時に実行される `exit` をシリアル化するため、`init` プロセス (子を継承する) は `wait` からウェイクアップされることが保証されます。

`wait_lock` は、各親のプロセスごとのロックではなくグローバルロックです。これは、プロセスがそれを取得するまで、その親が誰であるかを知ることができないためです。

## 現実世界

`sleep` と `wakeup` はシンプルで効果的な同期方法ですが、他にもたくさんあります。セマフォ (Dijkstra 1965) はその一例です。それらすべての最初の課題は、この章の冒頭で見た「ウェイクアップの喪失」問題を回避することです。オリジナルの Unix カーネルの `sleep` は単純に割り込みを無効にしていましたが、Unix は単一 CPU システムで実行されていたため、これで十分でした。

Plan 9 の `sleep` は、スリープへ入る直前に、スケジューリング用のロックを保持したままコールバック関数を実行します。この関数がスリープ条件を最後に確認し、ロストウェイクアップを防ぎます。Linux カーネルの `sleep` は、待機チャネルの代わりに「待機キュー」という明示的なプロセスキューを使います。待機キューは専用のロックを持ちます。

`wakeup` のプロセスのセット全体をスキャンするのは非効率的です。より良い解決策は、`sleep` と `wakeup` の両方の `chan` を、その構造上でスリープしているプロセスのリストを保持するデータ構造 (Linux の待機キューなど) に置き換えることです。プラン 9 の `sleep` および `wakeup` は、その構造をランデブーポイントと呼びます。

多くのスレッドライブラリは、同じ構造を条件変数として参照します。この文脈では、操作 `sleep` および `wakeup` は `wait` および `signal` と呼ばれます。これらのメカニズムはすべて同じ特徴を共有しています。つまり、スリープ状態は、スリープ中にアトミックにドロップされるある種のロックによって保護されます。

xv6 の `wakeup` は、特定の待機チャネルで待つすべてのプロセスを起こします。複数あれば、全プロセスが条件ロックを取得して条件を再確認しようとします。しかし多くの場合、パイプ内のデータをすべて読むなど、有効な処理ができるのは 1 つだけです。残りのプロセスは条件がもう成立していないことを確認し、再びスリープします。

これらのプロセスをすべて起こすと CPU 時間を浪費します。そのため多くの条件変数は、待機中の 1 プロセスだけを起こす `signal` と、全プロセスを起こす `broadcast` の 2 つを提供します。

プロセスを強制終了すると、いくつかの問題が発生します。たとえば、強制終了されたプロセスはカーネルの奥深くでスリープしている可能性があり、コールスタック上の各関数が何らかのクリーンアップを行う必要がある場合があるため、そのスタックを巻き戻すには注意が必要です。一部の言語では例外メカニズムを提供することで役に立ちますが、C ではそうではありません。さらに、待機しているイベントがまだ発生していない場合でも、スリープ状態のプロセスを目覚めさせる可能性のあるイベントが他にもあります。

たとえば、Unix プロセスがスリープしているときに、別のプロセスが `signal` を送信する可能性があります。この場合、プロセスは、値 -1 およびエラーコードが EINTR に設定された状態で、中断されたシステムコールから戻ります。アプリケーションはこれらの値を確認し、何をすべきかを決定できます。xv6 はシグナルをサポートしていないため、このような複雑さは発生しません。

xv6 の `kill` サポートは完全に満足のいくものではありません。おそらく `p->killed` をチェックする必要があるスリープループがあります。関連する問題は、`p->killed` をチェックする `sleep` ループの場合でも、`sleep` と `kill` の間に競合が存在することです。後者は、`p->killed` を設定し、被害者のループが `p->killed` をチェックした直後、`sleep` を呼び出す前に被害者をウェイクアップしようとする可能性があります。

この問題が発生した場合、被害者は、待っている状態が発生するまで `p->killed` に気づきません。これは、かなり後になるか、まったく行われない場合もあります (たとえば、被害者がコンソールからの入力を待っているが、ユーザーが何も入力しない場合)。

## 演習

1. xv6 でカウントセマフォを実装します。xv6 のスリープとウェイクアップの用途をいくつか選択し、それらをセマフォに置き換えます。結果を判断してください。

2. `sleep()` への呼び出し (おそらく追加の引数付き) だけを必要とし、`sleep_prepare()` への呼び出しのようなものを必要としないスリープ/ウェイクアップスキームを実装できますか?

3. `kill` と `sleep` の間の上記の競合を修正し、被害者のスリープループが `p->killed` をチェックした後、`sleep` を呼び出す前に発生する `kill` により、被害者が現在のシステムコールを放棄することになります。

4. すべてのスリープループが `p->killed` をチェックするように計画を設計します。これにより、たとえば、virtio ドライバー内のプロセスが別のプロセスによって強制終了された場合に、while ループからすぐに戻ることができます。

オペレーティングシステムの重要な要件は、複数のアクティビティを同時にサポートすることです。

たとえば、第[1](/book/chapter-1/#CH:UNIX) の `fork` および `exec` システムコールを使用して、コンパイラとテキストエディタの両方をプロセスとして起動できます。オペレーティングシステムは、これらのプロセス間で CPU やメモリなどのリソースを「タイムシェア」する必要があります。オペレーティングシステムは、プロセス間の「分離」も手配する必要があります。

1 つのプロセスにバグがあり誤動作したとしても、無関係なプロセスに影響を与えることはありません。ただし、プロセスが意図的に相互作用できる必要があるため、完全な分離は強すぎます。パイプラインはその一例です。したがって、オペレーティングシステムは、多重化、分離、相互作用という 3 つの要件を満たす必要があります。

この章では、これら 3 つの要件を達成するためにオペレーティングシステムがどのように構成されるかについて概要を説明します。それには多くの方法があることがわかりましたが、このテキストでは、多くの Unix オペレーティングシステムで使用されている *モノリシックカーネル* を中心とした主流の設計に焦点を当てています。この章では、xv6 の分離単位である xv6 プロセスの概要についても説明します。

xv6 は *マルチコア *[^1] RISC-V マイクロプロセッサ上で実行され、その低レベル機能 (プロセス実装など) の多くは RISC-V に固有です。RISC-V は 64 ビット CPU で、xv6 は「LP64」C で書かれています。これは、C プログラミング言語のロング (L) とポインター (P) が 64 ビットであることを意味しますが、`int` は 32 ビットです。

この本は、読者が何らかのアーキテクチャ上でマシンレベルのプログラミングを少し行ったことがあることを前提としており、RISC-V 固有のアイデアが思いついたら紹介します。ユーザーレベルの ISA (Waterman and Asanovic 2024) および特権アーキテクチャ (Waterman et al. 2024) のドキュメントが完全な仕様です。「The RISC-V Reader: An Open Architecture Atlas」(Patterson and Waterman 2017) も参照してください。

完成したコンピューターの CPU はサポートハードウェアに囲まれており、その多くは I/O インターフェースの形式です。xv6 は、qemu の「-machine virt」オプションによってシミュレートされたサポートハードウェア用に作成されています。これには、RAM、ブートコードを含む ROM、ユーザーのキーボード/画面へのシリアル接続、およびストレージ用のディスクが含まれます。

## 物理リソースの抽象化

オペレーティングシステムに遭遇したときに最初に抱く疑問は、そもそもなぜそのシステムがあるのかということです。つまり、図[1.2](#fig:api)のシステムコールをライブラリとして実装し、アプリケーションがリンクできます。この計画では、各アプリケーションがそのニーズに合わせた独自のライブラリを持つこともできます。アプリケーションは、ハードウェアリソースと直接対話し、アプリケーションにとって最適な方法でそれらのリソースを使用できます (たとえば、高いパフォーマンスや予測可能なパフォーマンスを達成するため)。

組み込みデバイスまたはリアルタイムシステム用の一部のオペレーティングシステムは、このように構成されています。

このライブラリアプローチの欠点は、複数のアプリケーションが実行されている場合、アプリケーションが適切に動作する必要があることです。たとえば、各アプリケーションは、他のアプリケーションが実行できるように、定期的に CPU を解放する必要があります。すべてのアプリケーションが相互に信頼しており、バグがない場合、このような *協力的な* タイムシェアリングスキームは問題ありません。

アプリケーションが相互に信頼できなかったり、バグが存在したりすることはよくあることなので、連携スキームが提供するよりも強力な分離が必要になることがよくあります。

強力な分離を実現するには、アプリケーションが機密性の高いハードウェアリソースに直接アクセスすることを禁止し、代わりにリソースをサービスに抽象化することが役立ちます。たとえば、Unix アプリケーションは、ディスクを直接読み書きするのではなく、ファイルシステムの `open`、`read`、`write`、および `close` システムコールを通じてのみストレージと対話します。

これにより、アプリケーションにパス名の利便性が提供され、オペレーティングシステム (インターフェースを提供する) がディスクを管理できるようになります。分離が問題にならない場合でも、意図的に対話する (または単にお互いの邪魔をしないようにしたい) プログラムは、ディスクを直接使用するよりもファイルシステムの方が便利な抽象化であると考える可能性があります。

同様に、Unix はプロセス間でハードウェア CPU を透過的に切り替え、必要に応じてレジスタ状態を保存および復元するため、アプリケーションはタイムシェアリングを意識する必要がありません。この透過性により、一部のアプリケーションが無限ループに陥っている場合でも、オペレーティングシステムは CPU を共有できます。

別の例として、Unix プロセスは物理メモリと直接対話するのではなく、`exec` を使用してメモリイメージを構築します。これにより、オペレーティングシステムはプロセスをメモリ内のどこに配置するかを決定できるようになります。メモリが不足している場合、オペレーティングシステムはプロセスのデータの一部をディスクに保存することもあります。`exec` は、実行可能プログラムイメージを保存するためのファイルシステムの利便性もユーザーに提供します。

Unix プロセス間の対話の多くの形式は、ファイル記述子を介して発生します。ファイル記述子は、多くの詳細 (パイプやファイル内のデータが保存される場所など) を抽象化するだけでなく、対話を簡素化する方法でも定義されます。たとえば、パイプライン内の 1 つのアプリケーションが終了するか失敗すると、カーネルはパイプライン内の次のプロセスのためにEOF（ファイル終端）を自動的に生成します。

図 [1.2](#fig:api) のシステムコールインターフェースは、プログラマーの利便性と強力な分離の可能性の両方を提供するように慎重に設計されています。Unix インターフェースはリソースを抽象化する唯一の方法ではありませんが、優れた方法であることが証明されています。

## ユーザーモード、スーパーバイザーモード、およびシステムコール

強力な分離には、アプリケーションとオペレーティングシステムの間に厳密な境界が必要です。アプリケーションにバグがある場合や悪意がある場合でも、アプリケーションがオペレーティングシステムや他のプログラムの動作を妨害することは許可されるべきではありません。強力な分離を実現するには、オペレーティングシステムは、アプリケーションがオペレーティングシステムのデータ構造と命令を変更 (または読み取り) できないようにし、アプリケーションが他のプロセスのメモリにアクセスできないようにする必要があります。

CPU は、強力な分離のためのハードウェアサポートを提供します。たとえば、RISC-V には、コードで実行できる内容を制限する 3 つの特権レベル (*マシンモード*、*スーパーバイザモード*、および *ユーザーモード*) があります。マシンモードで実行される命令には完全な権限が与えられます。CPU はマシンモードで起動します。マシンモードは主に、起動時にコンピュータをセットアップすることを目的としています。xv6 はマシンモードで短時間実行され、その後スーパーバイザモードに変わります。

スーパーバイザモードでは、CPU は *特権命令* を実行できます。たとえば、割り込みの有効化と無効化、ページテーブルのアドレスを保持するレジスタの読み書きなどです。ユーザーモードのアプリケーションが特権命令を実行しようとすると、CPU は命令を実行せず、アプリケーションを終了できるスーパーバイザモードの特別なコードに「トラップ」します。[1]章(/book/chapter-1/#CH:UNIX)の図[1.1](#fig:os)は、この組織を示しています。

アプリケーションはユーザーモード命令 (数値の追加など) のみを実行でき、*ユーザー空間* で実行されていると言われますが、スーパーバイザーモードのソフトウェアは特権命令も実行でき、*カーネルスペース* で実行されていると言われます。カーネル空間 (またはスーパーバイザーモード) で実行されるソフトウェアは、*カーネル* と呼ばれます。

アプリケーションは、`read` などのシステムコールを介してカーネルと対話します。アプリケーションは、カーネル関数を直接呼び出したり、カーネルのメモリにアクセスしたりすることはできません。RISC-V は、システムコールに `ecall` 命令を提供します。CPU をユーザーモードからスーパーバイザモードに切り替え、カーネル指定のエントリポイントにジャンプします。

CPU がスーパーバイザモードに切り替わると、カーネルはシステムコールの引数を検証し (たとえば、システムコールに渡されたアドレスがアプリケーションのメモリの一部であるかどうかをチェック)、アプリケーションが要求された操作の実行を許可されているかどうかを判断し (たとえば、アプリケーションが指定されたファイルの書き込みを許可されているかどうかを確認)、それからその操作を拒否または実行できます。

カーネルがスーパーバイザモードへの移行のエントリポイントを制御することが重要です。アプリケーションがカーネルのエントリポイントを決定できる場合、悪意のあるアプリケーションは、たとえば、引数の検証がスキップされるポイントでカーネルに侵入する可能性があります。

## カーネル構成

設計上の重要な問題は、オペレーティングシステムのどの部分をスーパーバイザモードで実行するかということです。可能性の 1 つは、オペレーティングシステム全体がカーネル内に存在し、すべてのシステムコールの実装がスーパーバイザモードで実行されることです。この組織は *モノリシックカーネル * と呼ばれます。

モノリシック組織では、オペレーティングシステム全体がスーパーバイザモードで実行される単一のプログラムで構成されます。この構成が便利な理由の 1 つは、OS 設計者がスーパーバイザー特権を必要とする部分と必要としない部分にコードを分割する必要がないことです。さらに、オペレーティングシステムのさまざまな部分は 1 つのプログラムの一部であるため、簡単に連携できます。たとえば、モノリシックカーネルは、ディスクブロックキャッシュをファイルシステムおよび仮想メモリシステムと共有する場合があります。

欠点は、モノリシックカーネルが大きく複雑になる傾向があるため、コードのさまざまな部分間の相互作用をすべて理解できる開発者がいないことです。これはバグのレシピです。カーネルのバグは、コンピュータ全体がクラッシュしたり、多くのアプリケーションが誤動作したり、コンピュータ全体がセキュリティ攻撃に対して脆弱になったりする可能性があるため、特に厄介です。

*マイクロカーネル* は、カーネル内のバグの発生を減らすことを目的としています。その考え方は、カーネル自体に絶対的な最小限の機能を組み込んで、スーパーバイザーモードで小さなコードが実行されるようにし、カーネルを理解しやすく、正しいかどうか分析しやすくすることです。オペレーティングシステムの大部分は、ユーザーレベルのサーバープロセスとして実行されます。たとえば、ファイルシステムコードは、スーパーバイザモードではなくユーザーモードでサーバープロセスとして実行されます。

図 [2.1](#fig:mkernel) は、このマイクロカーネル設計を示しています。この図では、ファイルシステムはユーザーレベルのサーバープロセスとして実行されます。アプリケーションがファイルサーバーと対話できるようにするために、カーネルは、あるユーザーモードプロセスから別のユーザーモードプロセスにメッセージを送信するプロセス間通信メカニズムを提供します。たとえば、シェルのようなアプリケーションがファイルの読み取りまたは書き込みを行う場合、ファイルサーバーにメッセージを送信し、応答を待ちます。

マイクロカーネルでは、カーネルインターフェースは、アプリケーションの起動、メッセージの送信、デバイスハードウェアへのアクセスなどを行うためのいくつかの低レベル関数で構成されます。オペレーティングシステムのほとんどがユーザーレベルのサーバーに存在するため、この構成によりカーネルが比較的単純になります。

現実の世界では、モノリシックカーネルとマイクロカーネルの両方が人気があります。多くの Unix カーネルはモノリシックです。たとえば、Linux はモノリシックカーネルを備えていますが、一部の OS 機能はユーザーレベルのサーバー (ウィンドウシステムなど) として実行されます。Linux は、カーネルのサブシステムを緊密に統合できるため、OS 負荷の高いアプリケーションに高いパフォーマンスを提供します。

Minix、L4、QNX などのオペレーティングシステムは、サーバーを備えたマイクロカーネルとして構成されており、組み込み環境で広く導入されています。L4 のバリアントである seL4 は十分に小さいため、メモリの安全性やその他のセキュリティ特性が検証されています (Klein et al. 2009)。

どちらの組織が優れているかについては、オペレーティングシステムの開発者の間で多くの議論がありますが、どちらにしても決定的な証拠はありません。さらに、「より良い」とは何か、つまり、より高速なパフォーマンス、より小さいコードサイズ、カーネルの信頼性、完全なオペレーティングシステム (ユーザーレベルのサービスを含む) の信頼性などによって大きく異なります。

どの組織かという問題よりも重要な実際的な考慮事項もあります。一部のオペレーティングシステムにはマイクロカーネルが搭載されていますが、パフォーマンス上の理由から、ユーザーレベルのサービスの一部はカーネル空間で実行されます。一部のオペレーティングシステムはモノリシックカーネルを採用しています。これは、モノリシックカーネルがモノリシックカーネルの始まりであり、マイクロカーネル設計に合わせて既存のオペレーティングシステムを書き直すよりも新機能の方が重要である可能性があるため、純粋なマイクロカーネル組織に移行する動機がほとんどないためです。

本書の観点から見ると、マイクロカーネルとモノリシックオペレーティングシステムは多くの重要なアイデアを共有しています。システムコールの実装、ページテーブルの使用、割り込みの処理、プロセスのサポート、同時実行制御のためのロックの使用、ファイルシステムの実装などです。本書はこれらの中心的なアイデアに焦点を当てています。

xv6 は、ほとんどの Unix オペレーティングシステムと同様に、モノリシックカーネルとして実装されています。したがって、xv6 カーネルインターフェースはオペレーティングシステムインターフェースに対応し、カーネルは完全なオペレーティングシステムを実装します。xv6 は多くのサービスを提供しないため、そのカーネルは一部のマイクロカーネルよりも小さいですが、概念的には xv6 はモノリシックです。

## プロセスの概要

xv6 での分離の単位は (他の Unix オペレーティングシステムと同様に) *プロセス* です。プロセスの抽象化により、あるプロセスが別のプロセスのメモリ、CPU、ファイル記述子などを破壊したりスパイしたりすることが防止されます。また、プロセスがカーネル自体を破壊することも防止され、プロセスがカーネルの分離メカニズムを破壊することができなくなります。バグのあるアプリケーションや悪意のあるアプリケーションがカーネルやハードウェアをだまして何か悪いこと (分離を回避するなど) を行う可能性があるため、カーネルはプロセス抽象化を慎重に実装する必要があります。

カーネルがプロセスを実装するために使用するメカニズムには、ユーザー/スーパーバイザーモードフラグ、アドレス空間、スレッドのタイムスライスが含まれます。

分離を強化するために、プロセス抽象化により、プログラムに独自のプライベートマシンがあるかのような錯覚を与えます。プロセスは、他のプロセスが読み書きできないプライベートメモリシステム、または *アドレス空間* のように見えるものをプログラムに提供します。また、プロセスは、プログラムの命令を実行するための独自の CPU のように見えるものをプログラムに提供します。

xv6 は、ページテーブル (ハードウェアによって実装される) を使用して、各プロセスに独自のアドレス空間を与えます。RISC-V ページテーブルは、*仮想アドレス* (RISC-V 命令が操作するアドレス) を *物理アドレス* (CPU がメインメモリに送信するアドレス) に変換 (または「マップ」) します。

<figure id="fig:as" data-latex-placement="t">
<img src="/book/fig/as.svg" alt="" loading="lazy">
<figcaption>
図 2.3: プロセスの仮想アドレス空間のレイアウト
</figcaption>
</figure>

xv6 は、プロセスごとに、そのプロセスのアドレス空間を定義する個別のページテーブルを維持します。図 [2.3](#fig:as) に示すように、アドレス空間には、仮想アドレス 0 から始まるプロセスの *ユーザーメモリ*が含まれます。最初に命令があり、次にグローバル変数、次にスタック、最後にプロセスが必要に応じて拡張できる「ヒープ」領域 (malloc 用) が続きます。

プロセスのアドレス空間の最大サイズを制限する要因は数多くあります。RISC-V 上のポインターは 64 ビット幅です。ハードウェアは、ページテーブル内の仮想アドレスを検索するときに下位 39 ビットのみを使用します。xv6 はこれら 39 ビットのうち 38 ビットのみを使用します。したがって、最大アドレスは $2^{38}-1$ = 0x3fffffffff、つまり [`MAXVA`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/riscv.h#L417) になります。

アドレス空間 xv6 の先頭には、*trampoline* ページ (4096 バイト) と *trapframe* ページが配置されます。xv6 は、これら 2 つのページを使用してカーネルへの移行とカーネルへの移行を行います。[4](/book/chapter-4/#CH:TRAP) 章で説明されているように、トランポリンページにはカーネルの内外に遷移するコードが含まれており、トラップフレームはカーネルがプロセスのユーザーレジスタを保存する場所です。

xv6 カーネルは、プロセスごとに多数の状態を維持し、それらを [`struct proc`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.h#L82) に収集します。プロセスのカーネル状態の最も重要な部分は、ページテーブル、カーネルスタック、および実行状態です。`proc` 構造体の要素を参照するには、`p->xxx` という表記を使用します。たとえば、`p->pagetable` はプロセスのページテーブルへのポインタです。

この時点で、`struct proc` を定義する [`kernel/proc.h`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.h) を読んでください。xv6 コードは、この本よりも理解することが重要です。コードに優先順位を付け、必要に応じて本書を参照してコードを明確にする必要があります。一部のコードの目的は最初は明らかではないかもしれませんが、コードをさらに読んで検索すると役に立ちます。自由にコードを探索して変更してください。

各プロセスには、プロセスの実行に必要な状態を保持する制御スレッド (略して「スレッド」) があります。いつでも、スレッドは CPU 上で実行されているか、一時停止されている (実行されていないが、将来実行を再開できる) 可能性があります。プロセス間で CPU を切り替えるには、カーネルはその CPU で現在実行中のスレッドを一時停止してその状態を保存し、別のプロセスの以前に一時停止されたスレッドの状態を復元します。

スレッドの状態 (ローカル変数、関数呼び出しの戻りアドレス) の多くは、スレッドのスタックに保存されます。各プロセスには、ユーザースタックとカーネルスタック (`p->kstack`) の 2 つのスタックがあります。プロセスがユーザー命令を実行しているときは、ユーザースタックのみが使用され、カーネルスタックは空です。プロセスが (システムコールまたは割り込みのために) カーネルに入ると、カーネルコードがプロセスのカーネルスタック上で実行されます。

プロセスがカーネル内にある間、そのユーザースタックには保存されたデータが含まれていますが、アクティブには使用されません。プロセスのスレッドは、ユーザースタックとカーネルスタックを交互にアクティブに使用します。カーネルスタックは分離されている (ユーザーコードから保護されている) ため、プロセスがユーザースタックを破壊した場合でもカーネルは実行できます。

プロセスのユーザーコードは、RISC-V `ecall` 命令を実行することによってシステムコールを実行できます。この命令はスーパーバイザモードに切り替え、プログラムカウンターをカーネル定義のエントリポイントに変更します。エントリポイントのコードはプロセスのカーネルスタックに切り替わり、システムコールを実装するカーネル命令を実行します。システムコールが完了すると、カーネルは `sret` 命令を実行してユーザー空間に戻り、ユーザーモードに切り替わり、システムコール命令の直後にユーザー命令の実行を再開します。

プロセスのスレッドはカーネル内で「ブロック」して I/O を待機し、I/O が終了すると中断したところから再開できます。

`p->state` は、プロセスが割り当てられているか、実行の準備ができているか、現在 CPU 上で実行されているか、I/O を待機しているか、または終了しているかを示します。

`p->pagetable` は、RISC-V ハードウェアが予期する形式でプロセスのページテーブルを保持します。xv6 では、ユーザー空間でプロセスを実行するときに、ページングハードウェアがプロセスの `p->pagetable` を使用します。プロセスのページテーブルは、プロセスのメモリを格納するために割り当てられた物理ページのアドレスの記録としても機能します。

要約すると、プロセスには 2 つの設計アイデアがバンドルされています。1 つはプロセスにそれ自体のメモリであるかのような錯覚を与えるアドレス空間であり、もう 1 つはプロセスにそれ自体の CPU であるかのような錯覚を与えるスレッドです。xv6 では、プロセスは 1 つのアドレス空間と 1 つのスレッドで構成されます。実際のオペレーティングシステムでは、複数の CPU を利用するために、プロセスに複数のスレッドが存在する場合があります。

## コード: xv6 の開始、最初のプロセスとシステムコール

xv6 をより具体的にするために、カーネルがどのように開始して最初のプロセスを実行するかを概説します。後続の章では、この概要に示されるメカニズムについて詳しく説明します。[`kernel/entry.S`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/entry.S)、[`kernel/start.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/start.c)、[`kernel/main.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/main.c)、[`user/init.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/init.c)と読んでください。

RISC-V コンピュータの電源がオンになると、コンピュータ自体が初期化され、読み取り専用メモリに保存されているブートローダーが実行されます。ブートローダーは、xv6 カーネルを物理アドレス `0x80000000` のメモリにコピーします。カーネルを `0x0` ではなく `0x80000000` に配置する理由は、アドレス範囲 `0x0:0x80000000` に I/O デバイスが含まれるためです。

次に、ブートローダーは [`_entry`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/entry.S#L7) から始まる xv6 にジャンプします。RISC-V はページングハードウェアが無効な状態で開始されます。仮想アドレスは物理アドレスに直接マッピングされます。`_entry` の命令は、xv6 が C コードを実行できるようにスタックをセットアップします。

xv6 は、ファイル [`start.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/start.c#L11) 内でこのスタック `stack0` 用のスペースを宣言します。`_entry` のコードは、スタックポインタレジスタ `sp` にスタックの最上位であるアドレス `stack0+4096` をロードします。

これは、RISC-V 上のスタックが下方に成長するためです。カーネルにスタックができたので、`_entry` は [`start`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/start.c#L15) で C コードを呼び出します。

関数 `start` は、CPU がマシンモードでのみ許可するいくつかのセットアップを実行します。最も重要なのは、タイマー割り込みを生成するようにクロックチップをプログラミングすることです。次に、`start` は RISC-V `mret` 命令を使用してスーパーバイザモードに切り替え、[`main`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/main.c#L11) にジャンプします。

`mret` には少しセットアップが必要です。`start` は、以前の特権モードをレジスタ `mstatus` のスーパーバイザに設定し、`main` のアドレスをレジスタ `mepc` に書き込むことによって宛先アドレスを `main` に設定し、`0` をページテーブルレジスタ `satp` に書き込むことによってスーパーバイザモードでの仮想アドレス変換を無効にし、すべての割り込みと例外を委任します。

スーパーバイザモードにします。

[`main`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/main.c#L11) はいくつかのデバイスとサブシステムを初期化した後、[`userinit`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L219) を呼び出して最初のプロセスを作成します。新しく作成されたすべてのプロセスは、[`forkret`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.c#L513) のカーネルで実行を開始します。最初のプロセスの特殊なケースとして、`forkret` は `kexec` を呼び出してユーザープログラム `/init` をロードします。

`kexec` を呼び出した後、`forkret` は `/init` プロセスのユーザー空間に戻ります。[`init`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/user/init.c#L15) は、必要に応じて新しいコンソールデバイスファイルを作成し、それをファイル記述子 0、1、2 として開きます。その後、コンソール上でシェルを開始します。システムは稼働しています。

## セキュリティモデル

オペレーティングシステムがバグのあるコードや悪意のあるコードをどのように処理するのか疑問に思うかもしれません。悪意に対処することは、偶発的なバグに対処するよりも厳密に難しいため、悪意に対するセキュリティの提供に主に焦点を当てるのは合理的です。ここでは、オペレーティングシステム設計における一般的なセキュリティの前提条件と目標の概要を示します。

オペレーティングシステムは、プロセスのユーザーレベルのコードがカーネルや他のプロセスを破壊するために最善を尽くすことを想定する必要があります。ユーザーコードは、許可されたアドレス空間外のポインタを逆参照しようとする可能性があります。ユーザーコードを対象としていない命令を実行しようとする可能性があります。RISC-V 制御レジスタの読み書きを試みる場合があります。

デバイスのハードウェアにアクセスしようとする可能性があります。そして、カーネルをだましてクラッシュさせたり、愚かなことをさせようとして、巧妙な値をシステムコールに渡す可能性があります。

カーネルの目標は、各ユーザープロセスが自身のユーザーメモリにのみアクセスできるように制限し、32 個の汎用 RISC-V レジスタを使用し、システムコールが許可する方法でカーネルと他のプロセスに影響を与えることです。カーネルは他のアクションを防止する必要があります。これらは通常、カーネル設計における絶対的な要件です。

カーネル自体のコードに対する期待は異なります。カーネルコードは、善意と慎重なプログラマーによって作成され、バグがなく、悪意のあるものが含まれていないことが前提となります。この仮定は、カーネルコードの分析方法に影響します。たとえば、カーネルコードが誤って使用すると深刻な問題を引き起こす内部カーネル関数 (スピンロックなど) が多数あります。ただし、カーネルが独自の関数を正しく使用していることを前提としています。

ハードウェアレベルでは、RISC-V CPU、RAM、ディスクなどが、ハードウェアのバグがなく、ドキュメントで宣伝されているとおりに動作すると想定されます。

現実の生活はそれほど単純ではありません。カーネルで保護されたリソース (ディスク領域、CPU 時間、プロセステーブルスロットなど) を消費してシステムを使用不能にするような、不正なユーザープログラムによるシステムコールの呼び出しを防ぐことは困難です。100% バグのないカーネルコードを作成したり、バグのないハードウェアを設計したりすることは通常不可能です。悪意のあるユーザーコードの作成者がカーネルまたはハードウェアのバグを認識している場合、それらを悪用します。

Linux などの成熟した広く使用されているカーネルであっても、以前は知られていなかった脆弱性が発見されることがよくあります (*Linux Common Vulnerabilities and Exposures (CVE)*、未確認)。最後に、ユーザーコードとカーネルコードの区別が曖昧になることがあります。一部の特権ユーザーレベルのプロセスは重要なサービスを提供し、実質的にオペレーティングシステムの一部となる場合があります。

また、一部のオペレーティングシステムでは、特権ユーザーコードが新しいコードをカーネルに挿入できます (Linux のロード可能なカーネルモジュールや eBPF と同様)。

カーネルのバグに対する部分的な防御として、xv6 コードには不整合や回復不可能なエラーのチェックが含まれており、それに応じて `panic()` を呼び出して「パニック」を起こします。この関数はエラーメッセージを出力し、システムを停止します。パニックは望ましくありませんが、実行を継続するよりは望ましいです。通常、パニックは、カーネルデータが不正になるか、存在しないメモリの参照などの不正なアクションをカーネルが実行するカーネルバグによって発生します。

このような状況では、矛盾した状態で続行しようとするよりも、`panic()` で実行を停止する方が安全です。カーネル開発者は、根底にあるコードのバグを特定して修正することでパニックに対応します。

## 現実世界

ほとんどのオペレーティングシステムはプロセスの概念を採用しており、ほとんどのプロセスは xv6 に似ています。ただし、最新のオペレーティングシステムは、プロセス内で複数のスレッドをサポートし、単一のプロセスが複数の CPU を利用できるようにします。プロセス内で複数のスレッドをサポートするには、プロセススレッドのどの側面を共有するかを制御するためのインターフェースの変更 (例: Linux の `clone`、`fork` の亜種) など、xv6 にはないかなりの機構が必要になります。

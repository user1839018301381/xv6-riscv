CPU に命令の通常の実行を脇に置き、イベントを処理する特別なカーネル コードに強制的に制御を移す原因となるイベントには 3 種類あります。 1 つの状況は、ユーザー プログラムが `ecall` 命令を実行してカーネルに何かをするよう要求するシステム コールです。もう 1 つの状況は *例外* です。命令 (ユーザーまたはカーネル) が、無効な仮想アドレスからのロードなど、不正なことを実行します。 3 番目の状況は、デバイスの *割り込み* です。これは、デバイスが注意が必要であることを通知するときです。たとえば、ディスク ハードウェアが読み取りまたは書き込み要求を終了したときです。

本書では、これらの状況の総称として「トラップ」を使用します。通常、トラップ時に実行されていたコードは後で再開する必要があるため、特別なことが起こったことを認識する必要はありません。つまり、トラップを透明にしたいことがよくあります。これは、通常、中断されたコードが予期しないデバイス割り込みの場合に特に重要です。トラップはカーネルへの制御の移行を強制します。カーネルは実行を再開できるようにレジスタやその他の状態を保存します。カーネルは適切なハンドラー コード (システム コールの実装やデバイス ドライバーなど) を実行します。カーネルは保存された状態を復元し、トラップから戻ります。元のコードは中断したところから再開されます。

Xv6 はカーネル内のすべてのトラップを処理します。トラップはユーザーコードには配信されません。カーネル内でトラップを処理することは、システム コールにとって自然なことです。分離ではカーネルのみがデバイスの使用を許可される必要があり、カーネルは複数のプロセス間でデバイスを共有できるため、割り込みにとっては理にかなっています。また、カーネルはユーザー空間からの例外を処理したり (例については、[5] 章 (/book/chapter-5/#CH:PGFAULTS) を参照)、問題のあるプログラムを強制終了して応答したりできるため、例外についても意味があります。

Xv6 トラップの処理は、RISC-V CPU によって実行されるハードウェア アクション、カーネル C コードの方法を準備するいくつかのアセンブリ命令、トラップの処理方法を決定する C 関数、およびシステム コールまたはデバイス ドライバー サービス ルーチンの 4 つの段階で進行します。 3 つのトラップ タイプの共通点は、カーネルが単一のコード パスですべてのトラップを処理できることを示唆していますが、ユーザー空間からのトラップとカーネル空間からのトラップという 2 つの異なるケースに対して別個のコードを用意すると便利であることがわかりました。トラップを処理するカーネル コード (アセンブラーまたは C) は、多くの場合 * ハンドラー * と呼ばれます。最初のハンドラー命令は通常 (C ではなく) アセンブラーで書かれており、*ベクトル* と呼ばれることもあります。

続行する前に、[`kernel/trampoline.S`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trampoline.S)、および [`kernel/trap.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c) の `usertrap()` および `prepare_return()` をお読みください。

## RISC-Vトラップ機構

各 RISC-V CPU には、カーネルがトラップの処理方法を CPU に指示するために書き込むハードウェア制御レジスタのセットがあり、カーネルはこれを読み取って、発生したトラップを確認できます。 RISC-V ドキュメントには全容が含まれています (Waterman et al. 2024)。 [`riscv.h`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/riscv.h) には、xv6 が使用する定義が含まれています。最も重要なレジスタの概要は次のとおりです。

- `stvec`: カーネルはトラップ ハンドラ コードのアドレスをここに書き込みます。 RISC-V は `stvec` のアドレスにジャンプしてトラップを処理します。

- `sepc`: トラップが発生すると、RISC-V はプログラム カウンタをここに保存します (`pc` は `stvec` の値で上書きされるため)。 `sret` (トラップからの復帰) 命令は、`sepc` を `pc` にコピーします。カーネルは `sepc` を書き込んで、`sret` の行き先を制御できます。

- `scause`: RISC-V は、トラップの理由を説明する番号をここに入力します。

- `sscratch`: カーネル トラップ ハンドラ コードは `sscratch` を使用して、ユーザー レジスタを保存する前に上書きすることを回避します。

- `sstatus`: `sstatus` の SIE ビットは、デバイス割り込みを有効にするかどうかを制御します。カーネルが SIE をクリアすると、RISC-V はカーネルが SIE を設定するまでデバイスの割り込みを延期します。 SPP ビットは、トラップがユーザー モードから来たのかスーパーバイザ モードから来たのかを示し、`sret` がどのモードに戻るかを制御します。

上記のレジスタは、スーパーバイザ モード (つまり、カーネル) でのみアクセスできます。 CPU は、ユーザー コードがそれらを読み書きできないようにします。

マルチコア チップ上の各 CPU にはこれらのレジスタの独自のセットがあり、複数の CPU が常にトラップを処理する可能性があります。

トラップを強制すると、RISC-V ハードウェアは次のことを行います。

1. トラップがデバイス割り込みで、`sstatus` SIE ビットがクリアされている場合は、次のいずれも実行しないでください。

2. `sstatus` の SIE ビットをクリアして割り込みを無効にします。

3. `pc` を `sepc` にコピーします。

4. 現在のモード (ユーザーまたはスーパーバイザ) を `sstatus` の SPP ビットに保存します。

5. `scause` をトラップの原因を示す番号に設定します。

6. モードをスーパーバイザに設定します。

7. `stvec` を `pc` にコピーします。

8. 新しい `pc` で実行を開始します。

CPU はカーネル ページ テーブルに切り替えず、カーネル内のスタックにも切り替えず、`pc` 以外のレジスタを保存しません。カーネル ソフトウェアはこれらのタスクを実行する必要があります。トラップ中に CPU が最小限の作業を行う理由の 1 つは、ソフトウェアに柔軟性を提供するためです。たとえば、一部のオペレーティング システムでは、トラップのパフォーマンスを向上させるために、状況によってはページ テーブル スイッチを省略します。

おそらくより高速なトラップを探すために、上記の手順のいずれかを省略できないかどうかを検討する価値があります。より単純なシーケンスが機能する状況もありますが、一般に手順の多くを省略すると危険です。たとえば、CPU がプログラム カウンタを切り替えなかったとします。その後、ユーザー空間からのトラップは、ユーザー命令の実行中にスーパーバイザー モードに切り替わる可能性があります。これらのユーザー命令は、たとえば `satp` レジスタを変更して、すべての物理メモリへのアクセスを許可するページ テーブルをポイントすることにより、ユーザーとカーネルの分離を破壊する可能性があります。したがって、CPU がカーネル指定の命令アドレス、つまり `stvec` に切り替えることが重要です。

Xv6 は、トラップがカーネルで実行中に発生するか、ユーザー コードで実行中に発生するかに応じて、トラップの処理方法が異なります。ユーザーコードからのトラップの話は次のとおりです。セクション [4.5](/book/chapter-4/#s:ktraps) では、カーネル コードからのトラップについて説明します。

ユーザー空間での実行中に、ユーザープログラムがシステムコール（`ecall`命令）を行ったり、不正な動作をしたり、デバイスが割り込んだ場合、トラップが発生することがあります。図[4.1](#fig:usertrap)に示すように、ユーザー空間からのトラップの上位パスは[`uservec`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trampoline.S#L22)、次に[`usertrap`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c#L38)です。そしてカーネルが戻る準備ができたら、`usertrap` は [`userret`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trampoline.S#L101) に戻り、ユーザー空間に対して `sret` を実行します。

xv6 のトラップ処理の設計における主な制約は、RISC-V ハードウェアがトラップを強制するときにページ テーブルを切り替えないという事実です。これは、`stvec` のトラップ ハンドラー アドレスがユーザー ページ テーブルに有効なマッピングを持っている必要があることを意味します。ユーザー ページ テーブルは、トラップ処理コードの実行開始時に有効となるためです。さらに、xv6 のトラップ処理コードはカーネル ページ テーブルに切り替える必要があります。切り替え後も実行を継続できるようにするために、カーネル ページ テーブルには、`stvec` が指すハンドラーのマッピングも必要です。

Xv6 は、*トランポリン* ページを使用してこれらの要件を満たします。このページには、`uservec` (`stvec` が指す xv6 トラップ処理コード) が含まれています。トランポリン ページは、仮想アドレス `0x3ffffff000` (`TRAMPOLINE` と呼ばれます) の各プロセスのページ テーブルにマップされます。これは、仮想アドレス空間の最後のページであるため、プログラムが自分自身で使用するメモリの上になります。トランポリン ページは、カーネル ページ テーブル内の同じ仮想アドレスにマップされます。図[2.3](#fig:as)および図[3.3](#fig:xv6_layout)を参照してください。トランポリン ページはユーザー ページ テーブルにマップされているため、トラップはスーパーバイザ モードでそこで実行を開始できます。トランポリン ページはカーネル アドレス空間内の同じアドレスにマップされるため、トラップ ハンドラーはカーネル ページ テーブルに切り替えた後も実行を続けることができます。

`uservec` トラップ ハンドラーのコードは [`trampoline.S`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trampoline.S#L22) にあります。 `uservec` が開始すると、32 個のレジスタすべてに、中断されたユーザー コードが所有する値が含まれます。これら 32 個の値は、後でカーネルがユーザー空間に戻る前に復元できるように、メモリ内のどこかに保存する必要があります。メモリに保存するには、ストアの宛先アドレスを保持するレジスタを使用する必要がありますが、現時点では利用可能な汎用レジスタはありません。幸いなことに、RISC-V は `sscratch` レジスタの形で助けを提供します。 `uservec` の先頭にある `csrw` 命令は、`a0` を `sscratch` に保存します。これで、`uservec` には操作できるレジスタが 1 つ (`a0`) になりました。

`uservec` の次のタスクは、32 個のユーザー レジスタを保存することです。カーネルは、プロセスごとに、(とりわけ) 32 のユーザー レジスタ [(proc.h:40)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/proc.h#L40) を保存するスペースのある `trapframe` 構造体にメモリのページを割り当てます。 `satp` は引き続きユーザー ページ テーブルを参照するため、`uservec` はトラップフレームをユーザー アドレス空間にマップする必要があります。 Xv6 は、各プロセスのトラップフレームを、そのプロセスのユーザー ページ テーブル内の仮想アドレス `TRAPFRAME` (`0x3fffffe000`) にマップします。 `TRAMPOLINE` の 1 ページ下。各プロセスの `p->trapframe` には、プロセスのトラップフレームのカーネル仮想アドレスが含まれています。

`uservec` はレジスタ `a0` をアドレス `TRAPFRAME` に設定し、すべてのユーザー レジスタをそこに保存します。次に、`sscratch` からユーザー `a0` を取得し、トラップフレームに保存します。

カーネルは以前に、`uservec` に役立ついくつかの値 (現在のプロセスのカーネル スタックのアドレス、現在の CPU の hartid、`usertrap` 関数のアドレス、およびカーネル ページ テーブルのアドレス) を含むようにトラップフレームを初期化しました。 `uservec` はこれらの値を取得し、`satp` をカーネル ページ テーブルに切り替えて、C 関数である `usertrap` にジャンプします。

`usertrap` の仕事は、トラップの原因を特定し、処理して、[(trap.c:38)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c#L38) を返すことです。まず、カーネル内のトラップが `uservec` ではなく `kernelvec` によって処理されるように `stvec` を変更します。将来ユーザー空間に戻ったときに使用できるように、`sepc` レジスタ (保存されたユーザー プログラム カウンタ) を保存します。トラップがシステム コールの場合、`usertrap` はそれを処理するために `syscall` を呼び出します。デバイス割り込みの場合は、`devintr`。ページフォルトの場合は `vmfault`。それ以外の場合は例外 (無効なアドレスの使用など) となり、カーネルは障害のあるプロセスを強制終了します。 RISC-V では、システム コールの場合、プログラム ポインタは `ecall` 命令を指すままになりますが、ユーザー コードは後続の命令で実行を再開する必要があるため、システム コール パスによって保存されたユーザー プログラム カウンタに 4 が追加されます。 `usertrap` は、プロセスが強制終了されたかどうか、または CPU を解放する必要があるかどうか (このトラップがタイマー割り込みの場合) をチェックします。

ユーザー空間に戻る最初のステップは、[`prepare_return`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c#L101) を呼び出すことです。この関数は、ユーザー空間からの将来のトラップに備えて RISC-V 制御レジスタを設定します。つまり、`stvec` を `uservec` に設定し、`uservec` が依存するトラップフレーム フィールドを準備します。 `prepare_return` は、`sepc` を以前に保存したユーザー プログラム カウンタに設定します。最後に、`usertrap` はトランポリン ページ [(trampoline.S:101)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trampoline.S#L101) の `userret` に戻り、`a0` のユーザー ページ テーブルへのポインターを返します。

`userret` は、`satp` をプロセスのユーザー ページ テーブルに切り替えます。ユーザー ページ テーブルはトランポリン ページと `TRAPFRAME` の両方をマップしますが、それ以外はカーネルからマップしないことを思い出してください。ユーザー ページ テーブルとカーネル ページ テーブル内の同じ仮想アドレスでのトランポリン ページ マッピングにより、`satp` の変更後も `userret` が実行を継続できます。この時点から、`userret` が使用できるデータはレジスタの内容とトラップフレームの内容のみになります。 `userret` は、`TRAPFRAME` アドレスを `a0` にロードし、保存されたユーザー レジスタを `a0` 経由でトラップフレームから復元し、保存されたユーザー `a0` を復元し、`sret` を実行してユーザー空間に戻ります。

`uservec` および `userret` はアセンブリ言語で書かれています。これは、すべてのレジスタを保存または復元したり、ページ テーブルの切り替えに耐えたりするための C コードを書くのが難しいためです。

## コード: システムコールの呼び出し

ユーザプログラムはシステムコールを行うためにライブラリ関数を呼び出します。たとえば、シェルは次の関数呼び出し (`user/sh.c`) を含むプロンプトを表示します。

      write(2, "$ ", 2);

`user/usys.S` のライブラリ関数は次のとおりです。

    write:
     li a7, SYS_write
     ecall
     ret

C コンパイラが関数呼び出し用に生成するコードは、3 つの引数をレジスタ `a0`、`a1`、および `a2` にロードします。次に、`write()` 関数は、システム コール番号 `SYS_write` (16) を `a7` にロードします。カーネルはこれらのレジスタを調べて、どのようなシステム コールが意図されているか、および引数が何であるかを調べます。 `ecall` 命令はユーザー空間からカーネルにトラップし、`uservec`、`usertrap`、そして `syscall` を実行させます。

この時点で、[`kernel/syscall.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/syscall.c)、[`kernel/sysfile.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/sysfile.c)の`sys_write()`、[`kernel/vm.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/vm.c)の`copyout()`、`copyin()`、`copyinstr()`と読み替えてください。

[`syscall`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/syscall.c#L137) は、トラップフレームに保存された `a7` からシステム コール番号を取得し、それを使用して [`syscalls`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/syscall.c#L109) にインデックスを付けます。この例では、`a7` には [`SYS_write`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/syscall.h#L17) が含まれており、システム コール実装関数 `sys_write` が呼び出されます。

`sys_write` が戻ると、`syscall` はその戻り値を `p->trapframe->a0` に記録します。これにより、RISC-V の C 呼び出し規則では戻り値が `a0` に配置されるため、`write()` への元のユーザー空間呼び出しでその値が返されます。システムコールは通常、エラーを示す場合は負の数値を返し、成功した場合は 0 または正の数値を返します。

## コード: システムコール引数

システム コールの引数はユーザー レジスタで開始され、カーネル トラップ コードによってトラップ フレームに移動されます。カーネル関数 `argint`、`argaddr`、および `argfd` は、トラップ フレームから *n* 番目のシステム コール引数を整数、ポインター、またはファイル記述子として取得します。

一部のシステム コールではポインタを引数として渡すため、カーネルはユーザー メモリの読み取りまたは書き込みにそれらのポインタを使用する必要があります。たとえば、`write` システム コールは、書き込まれるデータへのユーザー空間ポインターをカーネルに渡します。このようなポインタは 2 つの課題を引き起こします。まず、ユーザー プログラムにバグがあるか悪意がある可能性があり、無効なポインタ、またはカーネルをだましてユーザー メモリではなくカーネル メモリにアクセスさせることを目的としたポインタをカーネルに渡す可能性があります。第 2 に、xv6 カーネル ページ テーブル マッピングはユーザー ページ テーブル マッピングと同じではないため、カーネルは通常の命令を使用してユーザー指定のアドレスからロードまたはストアすることができません。

カーネルは、ユーザーが指定したアドレスとの間でデータを安全に転送する機能を実装します。 `fetchstr` は [(syscall.c:26)](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/syscall.c#L26) の例です。 `exec` などのファイル システム呼び出しは、`fetchstr` を使用して文字列のファイル名引数をユーザー空間から取得します。 `fetchstr` は、難しい作業を行うために `copyinstr` を呼び出します。

[`copyinstr`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/vm.c#L412) は、ユーザー ページ テーブル `pagetable` の仮想アドレス `srcva` から最大 `max` バイトを `dst` にコピーします。 `pagetable` は現在のページ テーブルではないため、`copyinstr` は `walkaddr` (`walk` を呼び出す) を使用して `pagetable` 内の `srcva` を検索し、物理アドレス `pa0` を生成します。カーネルのページ テーブルは、RAM の物理アドレスと等しい仮想アドレスにすべての物理 RAM をマップします。これにより、`copyinstr` は文字列バイトを `pa0` から `dst` に直接コピーできるようになります。 [`walkaddr`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/vm.c#L122) は、ユーザーが指定した仮想アドレスがプロセスのユーザー アドレス空間の一部であることをチェックするため、プログラムがカーネルをだまして他のメモリを読み取ることができません。同様の関数 `copyout` は、カーネルからユーザーが指定したアドレスにデータをコピーします。

## カーネル空間からのトラップ
[`kernel/kernelvec.S`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/kernelvec.S)、[`kernel/trap.c`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c)は`kerneltrap()`と読み替えてください。

Xv6 は、ユーザー コードからのトラップとは異なる方法でカーネル コードからのトラップを処理します。カーネルに入るとき、`usertrap` は `stvec` に [`kernelvec`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/kernelvec.S#L12) のアセンブリ コードを指します。 `kernelvec` は、xv6 がすでにカーネル内にある場合にのみ実行されるため、`kernelvec` は、カーネル ページ テーブルに設定されている `satp` と、有効なカーネル スタックを参照するスタック ポインターに依存できます。 `kernelvec` は、呼び出し元が保存したすべてのレジスタを現在のスタックにプッシュし、後でそこからレジスタを復元して、中断されたカーネル コードを中断せずに再開できるようにします。

`kernelvec` は、中断されたカーネル スレッドのスタックにレジスタを保存します。レジスタ値はそのスレッドに属しているため、これは当然のことです。これは、トラップが別のスレッドへの切り替えを引き起こす場合に特に重要です。その場合、トラップは実際には新しいスレッドのスタックから戻り、中断されたスレッドの保存されたレジスタはスタック上に安全に残ります。

`kernelvec` はレジスタを保存した後、[`kerneltrap`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c#L137) にジャンプします。 `kerneltrap` は、デバイス割り込みという 1 種類のトラップのみに対応しています。 [`devintr`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c#L188) を呼び出してそれらを処理します。トラップがデバイス割り込みではない場合は、カーネル コードが無効なポインターを使用しようとしたなどの例外である必要があります。これはカーネル コードのバグによってのみ発生する可能性があります。カーネルにはこの状況から回復する方法がないため、`panic()` を呼び出し、エラー メッセージを出力して停止します。

タイマー割り込みによって `kerneltrap` が呼び出され、プロセスのカーネル スレッドが (スケジューラ スレッドではなく) 実行されている場合、`kerneltrap` は `yield` を呼び出して、他のスレッドに実行の機会を与えます。ある時点で、これらのスレッドの 1 つが放棄され、スレッドとその `kerneltrap` が再び再開されます。 [8](/book/chapter-8/#CH:SCHED) 章では、`yield` で何が起こるかを説明します。

`kerneltrap` の作業が完了したら、トラップによって中断されたコードに戻る必要があります。 `yield` が `sepc` と `sstatus` の以前のモードを妨害した可能性があるため、`kerneltrap` は起動時にそれらを保存します。これらの制御レジスタが復元され、[`kernelvec`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/kernelvec.S#L38) に戻ります。 `kernelvec` は、保存されたレジスタをスタックからポップし、`sret` を実行します。これにより、`sepc` が `pc` にコピーされ、中断されたカーネル コードが再開されます。

Xv6 は、CPU がユーザー空間からカーネルに入るときに、CPU の `stvec` を `kernelvec` に設定します。これは [`usertrap`](https://github.com/mit-pdos/xv6-riscv/blob/riscv/kernel/trap.c#L47) で確認できます。ただし、カーネルの実行が開始されても `stvec` が `uservec` に設定されたままになる時間枠があり、その時間枠中にデバイスの割り込みが発生しないことが重要です。幸いなことに、RISC-V はトラップを開始すると常に割り込みを無効にし、`usertrap` は `stvec` を設定するまで再び割り込みを有効にしません。

## 現実世界

カーネル メモリがすべてのプロセスのユーザー ページ テーブル (`PTE_U` クリア付き) にマップされていれば、トランポリン ページの必要性を排除できます。これにより、ユーザー空間からカーネルにトラップするときにページ テーブルを切り替える必要もなくなります。これにより、カーネル内のシステム コール実装が、マップされている現在のプロセスのユーザー メモリを利用できるようになり、カーネル コードがユーザー ポインターを直接逆参照できるようになります。多くのオペレーティング システムは、効率を高めるためにこれらのアイデアを使用してきました。 Xv6 は、ユーザー ポインターの不用意な使用によるカーネルでのセキュリティ バグの可能性を減らし、ユーザーとカーネルの仮想アドレスが重複しないようにするために必要な複雑さを軽減するために、これらを回避します。
